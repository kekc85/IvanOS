# _CANON — стандарт оформления метод-файла в mastery/

Этот файл — единый формат **хранения** метода: «один метод-мастер = один файл `mastery/<область>/<автор>.md`». Задаёт, ЧТО внутри файла и как его пишут, чтобы метод (а) авто-подхватывался по триггерам, (б) защищал от слепых зон, (в) калибровался по факту применения. Источник формата — тренинг Артемия Миллера, День 6 (mastery CANON «один метод=один файл» + how-to-apply + лог) и День 10 («мастерство X» с запрещёнными приёмами, только из реальных источников).

> CANON ≠ PROTOCOL. CANON = как ХРАНИТЬ метод (этот файл). PROTOCOL.md = как ПРИМЕНЯТЬ его (Inventory→Select→Apply→Evidence→верификатор). Раздел «Связь с PROTOCOL.md» внизу.

---

## Frontmatter (обязателен, YAML в начале файла)

```yaml
---
name: <Имя автора — короткая суть в 3-5 слов>
mastery: <область = имя папки: copywriting / decision-making / offer-design / …>
source: <реальный источник: автор + книга/статья/выступление. НЕ выдуманный>
triggers: [<ситуация-триггер 1>, <триггер 2>, <триггер 3>]   # когда AI сам ныряет в файл
---
```

- `source` — конкретный реальный носитель метода (книга с названием / статья / задокументированное выступление). Нет реального источника → файл не создаётся.
- `triggers` — фразы/ситуации, по которым метод авто-подхватывается (how-to-apply встроен в frontmatter, отдельный how-to-apply.md не плодим — один источник истины). Пример: `[пишу пост, чищу текст от воды, RU-текст для аудитории]`.

## Разделы файла (в этом порядке)

### 1. Когда применять
Триггер ситуации развёрнуто (frontmatter — коротко для машины, тут — для человека/агента). «Перед запуском», «на любом RU-тексте финальным проходом», «когда оффер туманный». Одна-две строки, без воды.

### 2. Что делать
3-7 шагов или принципов метода. Каждый — императив (глагол действия), как алгоритм автора, не пересказ «о чём он». Без оценочных прилагательных, без воды (само по Ильяхову). Если у автора несколько методов — нумеровать (Метод 1 / Метод 2 …), внутри каждого «Суть + Шаги».

### 3. Результат
Что на выходе, проверяемо. «0 оценочных прилагательных без факта», «список запретов вместо размытой цели», «оффер, от которого глупо отказаться». Это вход для Evidence Report PROTOCOL — формулировать так, чтобы можно было процитировать из готового артефакта.

### 4. Запрещённые приёмы
Что автор **сам явно ругает / запрещает** — защита от слепых зон (День 10). Не «чего вообще не делать», а именно анти-паттерны этого автора: Огилви против юмора в заголовке, Ильяхов против усилителей, Мангер против «человека с молотком». Берётся из источника, не из головы. Нет явного запрета у автора → строка «автор явных запретов не формулирует» (не выдумывать).

### 5. Лог применений
Самокалибровка. Каждое реальное применение — одна строка:
```
- ГГГГ-ММ-ДД — <что собрали с этим методом> — <сработало / переделали, почему>
```
Пустой при создании. Пополняется по факту использования (после Evidence Report PROTOCOL). Через месяц этот лог показывает, какие методы реально тянут результат, а какие лежат мёртвым грузом.

### (опц.) Связь
Wikilinks на родственные методы внутри/между областями (`[[kahneman]]`, `[[naval]]`) — как в существующих файлах. Помогает Inventory PROTOCOL.

## Правило источника (HARD)

- Только **дословные методы из реальных источников**. Метод, который автор реально сформулировал, — не «по мотивам», не «в духе автора».
- **Финальный проход перед сохранением:** пройти файл и удалить ВСЁ, что не опирается на `source`. Не можешь привязать утверждение к реальному источнику автора → вычеркнуть.
- **Выдуманный метод хуже отсутствующего:** ложный метод под именем мастера загрязняет Inventory и проходит в артефакт как «авторитет». Лучше пустой раздел, чем сочинённый.
- Совпадает с правилом проекта «нет контекста → не выдумывай» и анти-fact-invention humaniser.

---

## Обратная совместимость

Существующие метод-файлы (copywriting, decision-making и др. — собраны до CANON) остаются рабочими. CANON — стандарт для **новых** файлов и для дозаливки старых при следующем касании (добавить frontmatter + разделы «Запрещённые приёмы» и «Лог применений», если их нет). Массовая разовая миграция не требуется — не ломать то, что уже тянет PROTOCOL.

## Связь с PROTOCOL.md

Два файла — две разные оси, не дублируют и не противоречат друг другу:

| | _CANON.md (этот файл) | PROTOCOL.md |
|---|---|---|
| Отвечает на | как **ХРАНИТЬ** метод | как **ПРИМЕНЯТЬ** методы |
| Уровень | один файл одного метода | работа над одним артефактом |
| Содержит | frontmatter + 5 разделов + правило источника | Discover→Inventory→Select→Apply→Prove + 5 слоёв чекинга + верификатор |

Связки:
- **Inventory (PROTOCOL, Шаг 2)** выписывает всех авторов области — читает файлы, оформленные по CANON; единый формат делает Inventory механическим, без «угадай, где метод».
- **Triggers (CANON frontmatter)** — то, по чему PROTOCOL понимает, какие файлы вообще релевантны задаче (вход в Discover/Select).
- **Результат (CANON, разд.3)** формулируется так, чтобы стать строкой Evidence Report (PROTOCOL, Слой 3): «метод → цитата из артефакта».
- **Лог применений (CANON, разд.5)** пополняется ПОСЛЕ того, как PROTOCOL прогнал Apply+Prove+верификатор — это обратная петля: применение калибрует хранение.
- **Запрещённые приёмы (CANON, разд.4)** — материал для адверсариального верификатора (PROTOCOL, Слой 4): нарушил явный запрет автора → FAIL.

Приоритет при конфликте: правило источника CANON (только реальные методы) и анти-частичность PROTOCOL — союзники, оба бьют по выдумке/имитации. Противоречий нет by design.
