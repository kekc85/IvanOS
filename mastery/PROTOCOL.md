# PROTOCOL — как применять mastery, чтобы это реально работало

Этот файл — обязательный регламент обращения к любой папке `mastery/<область>/`. Действует и для меня в чате, и для скиллов-писателей, и для skill-craft при создании новых скиллов. Цель — чтобы методы мастеров **реально использовались**, а не «я написал, что использовал».

> Проблема, которую этот протокол закрывает: на интеллектуально-ёмких задачах есть склонность применять методы частично или имитировать применение. Поэтому ниже — не «рекомендация подумать о мастерах», а пять слоёв с доказательством и независимой проверкой.

---

## 1. Когда срабатывает

Перед любым артефактом/ответом проверь: есть ли в `mastery/` область под эту задачу.
- Текст для аудитории (пост / письмо / лендинг / сценарий / caption) → `mastery/copywriting/`.
- Финансовый вопрос → `mastery/financial-analysis/` (когда собрана).
- Переговоры / оффер / возражения → `mastery/negotiations/`, `mastery/sales/`.
- Решение / стратегия → `mastery/decision-making/`.
- Есть область → протокол обязателен. Нет → работаешь как обычно (и фиксируешь в `inbox`, что области не хватает).

---

## 2. Пять шагов обращения (Discover → Inventory → Select → Apply → Prove)

**Шаг 1. Discover.** Определи область, открой её `INDEX.md`.

**Шаг 2. Inventory — ВСЕХ, не выборку.** Выпиши **каждого** автора папки и его методы. Молча пропустить автора нельзя. Если в папке 12 авторов — в инвентаре 12 строк. Это защита от «взял первого, кого вспомнил».

**Шаг 3. Select с обоснованием.** По каждому методу пометка: `применяю` / `не применяю` + одной строкой почему. Правило автора дословно: *рассмотреть всех → подумать, что подходит → выбрать подходящие*. Подходящих может быть много. Но «рассмотреть всех» ≠ «впихнуть всех»: метод, который не служит этой конкретной задаче, осознанно отсекается с причиной, а не игнорируется.

**Шаг 4. Apply.** Каждый выбранный метод вплетается в работу по его собственному алгоритму (шаги из файла автора), а не упоминается для галочки.

**Шаг 5. Prove.** Собери **Evidence Report** — таблицу `метод → дословная цитата из готового артефакта, где он реализован`. Нет цитаты = метод не применён = вернуться на Шаг 4. Это вход в систему чекинга ниже.

---

## 3. Система глубокого чекинга — 5 слоёв

**Всегда полный, со всеми 5 слоями, включая независимого верификатора.** Облегчённого режима / `--fast` НЕТ (решение автора): для публикуемого контента качество важнее скорости, время не аргумент.

### Слой 1 — Inventory-gate (до написания)
Выписаны ВСЕ авторы+методы области с пометкой apply/skip+причина. Нет полного списка → стоп, не начинать.

### Слой 2 — Draft-binding (во время)
Черновик строится с явной внутренней привязкой блоков к методам (какой блок какой метод реализует). Привязка ведётся по ходу, не задним числом.

### Слой 3 — Evidence Report (после черновика)
Таблица `метод → цитата`. Каждый выбранный (Шаг 3 = «применяю») метод обязан иметь цитату. Пустая строка = брак, возврат.

### Слой 4 — Независимый верификатор (отдельный проход/субагент)
Агент, который **НЕ писал** текст, получает: (а) готовый артефакт, (б) список методов, заявленных как применённые. По каждому методу выносит адверсариальный вердикт: *«реально присутствует? процитируй конкретный фрагмент. если не находишь — FAIL»*. Установка верификатора — скептик: при сомнении ставит FAIL.
- Любой FAIL → метод дорабатывается или честно переводится в «не применяю» с причиной (не остаётся ложным «применено»).
- Зачем отдельный агент: тот же контекст, что писал, склонен подтверждать себя. Независимый — нет. Это ядро анти-фабрикации.

### Слой 5 — Структурный хук (детерминированный пол)
Хук проверяет, что вывод writer-скилла содержит Evidence Report нужной структуры (grep-able маркеры). Проверяет **наличие** отчёта, не качество — качество на слое 4. Забыть нельзя.
> Хук ставится ТОЛЬКО после того, как формат Evidence Report стабилизирован на пилоте (правило: механизм валидируем на реальном прогоне до деплоя).

---

## 4. Контракт независимого верификатора

Вход:
- `artifact` — готовый текст/результат.
- `claimed_methods[]` — `{author, method, claimed_quote}` из Evidence Report.

Выход (по каждому методу):
- `verdict`: PASS | FAIL
- `found_quote`: фрагмент артефакта, доказывающий применение (для PASS) — должен совпадать/перекрывать `claimed_quote`.
- `reason`: для FAIL — почему метод не считается применённым.

Правила:
- Скептик по умолчанию: нет явного доказательства → FAIL.
- Не оценивает «нравится/не нравится» — только факт присутствия механики метода.
- Итог: список FAIL → обратно в работу; всё PASS → артефакт проходит.

---

## 5. Анти-частичность (свод запретов)

- ❌ Взять 1-2 авторов «по памяти», не открыв папку. → Шаг 2 обязателен.
- ❌ Заявить «применил методы X, Y» без цитат. → Слой 3.
- ❌ Самому себе поставить «применено». → Слой 4, независимый.
- ❌ Впихнуть все методы в кашу ради галочки. → Шаг 3, осознанный select.
- ❌ Поставить хук до стабилизации формата. → Слой 5, после пилота.

---

## 6. Связь с системой

- Протокол читается каждую сессию (пойнтер в `CLAUDE.md`).
- skill-craft при создании нового скилла: ищет тематический mastery → есть = вшивает обращение по этому протоколу; нет/неполон = дополняет мастера (web-ресёрч концепций, обогащение файлов авторов) ДО сборки; использует методы мастеров при проектировании.
- writer-скиллы (post / email / longform / carousel / tweet …): фаза «consult mastery по протоколу + Evidence Report + верификатор» перед финальным humaniser.
- Лестница эскалации (память → CLAUDE.md → хук) применена: правило в CLAUDE.md (мягко-твёрдо) + Evidence Report в скилле (твёрдо) + независимый верификатор (твёрдо) + структурный хук (детерминированно).
