# Вайбкодинг — промпт-плейбуки

> Это библиотека **дословно копируемых промптов** для работы с кодом через Claude Code.
> Методология (когда какая стадия, контекст-менеджмент, TDD) живёт в skill `вайбкодинг` и `plans/README.md` — здесь НЕ дублируется.
> Каждый плейбук = **название · когда применять · дословные промпты по шагам**. Копировать как есть, подставив `<…>`.

**Сквозные принципы всех плейбуков (из Дней 4/5/10 Миллера):**
- **«Предложи, не правь сразу»** — раздели «найди» и «исправь» на ДВЕ итерации. Сначала агент только находит и предлагает, ты решаешь, потом отдельным промптом чинишь. Режет over-engineering.
- **«AI с первого раза никогда не делает нормально»** — первый ответ поверхностный (Anthropic под нагрузкой 80×, «AI-подхалим»). Гони глубже, требуй прецеденты, не верь первому проходу.
- **Каждая остановка = новая think-итерация** — не сваливать диагноз+решение+план в один промпт. Разрывы между промптами = точки, где агент думает заново, а не защищает уже сказанное.
- **«1 кейс ≠ паттерн»** — прежде чем чинить, посчитать частоту.

## Плейбук 1. Цикл «5 ходов» ПОСЛЕ каждой фичи

**Когда:** сразу после того как фича/фаза написана и базово работает. Прогнать 5 ходов ДО того как считать фичу готовой. Каждый ход — отдельный промпт; между «найди» и «исправь» — пауза (ты смотришь предложения, решаешь, потом отдельным промптом чинишь).

**Ход 1 — поиск ошибок + точки слома под нагрузкой:**
```
Не правь ничего. Только найди. Пройди по коду этой фичи и найди ошибки. Отдельно назови 3 места, которые сломаются при ×100 нагрузки (×100 пользователей / записей / запросов). По каждому: где именно, что именно сломается, при каком объёме. Список, без правок.
```

**Ход 2 — что упустил + горизонт месяца:**
```
Не правь. Что я упустил в этой фиче? Что будет с ней через месяц реального использования — какие данные накопятся, какие состояния появятся, что начнёт деградировать? Назови конкретные сценарии, которых сейчас не видно, но они придут через месяц.
```

**Ход 3 — доказательство релевантности (анти-выдумка):**
```
По каждому пункту из найденного докажи, что это РЕАЛЬНАЯ проблема именно в нашем проекте, а не теоретическая. Открой реальный код и данные. Где не можешь доказать на нашем коде — честно скажи «это теория, у нас не воспроизводится». Не раздувай список ради списка.
```

**Ход 4 — свежий взгляд после правок (регресс):**
```
Правки внесены. Теперь свежим взглядом, как будто видишь этот код впервые: что мы сломали в том, что РАНЬШЕ работало? Пройди по соседнему коду, который трогали правки. Назови регрессии — где рабочее поведение могло измениться.
```
> Ход 4 запускать в ОТДЕЛЬНОМ чистом окне (читающем папку), не в окне-где-чинил — там агент защищает свои правки.

**Ход 5 — security review:**
```
Security review этой фичи. Проверь: валидацию ввода, авторизацию/права, утечки данных наружу, инъекции (SQL/команд/промпт), секреты в коде, опасную тройку (личные данные + чужой контент + отправка наружу). По каждой находке: severity (low→critical), где, как эксплуатируется. Не правь — только отчёт.
```
> Усиление (День 7): прогнать этот же ход через 3 ИИ параллельно (Claude + ChatGPT + Gemini) — у каждого свои слепые зоны, «Claude не видит баги в своём коде».
> Усиление (забрано у Мари/ЛАБС): после авто-ревью прогнать РУЧНОЙ само-пентест «стань хакером сам» — 4 теста руками: (1) слабый пароль `123456` при регистрации — должен отлететь; (2) сменить чужой id в URL → должно дать 403, не чужие данные; (3) 10–15 быстрых кликов на отправку → должно дать 429 (rate-limit); (4) открыть `/admin` без входа → должно требовать пароль. + финальный промпт агенту: «проведи финальный аудит проекта как эксперт по кибербезопасности по стандартам OWASP».

## Плейбук 2. Цикл «диагноз → решение → план» (4 ОТДЕЛЬНЫХ промта)

**Когда:** что-то сломалось / пользователь жалуется / метрика просела / непонятный баг. НЕ сваливать в один промпт «разберись и почини» — агент выдаст подхалимский поверхностный ответ. Четыре промпта, четыре остановки, между ними ты читаешь и решаешь.

**Промт 1 — только факты, без выводов:**
```
Сейчас нужны ТОЛЬКО факты, выводы и решения запрещены. Собери что реально произошло: логи, конкретные значения, последовательность событий, числа. Без интерпретаций «наверное», «похоже», «обычно». И помни: 1 кейс ≠ паттерн — посчитай частоту, сколько раз это случилось из скольких, прежде чем называть это проблемой.
```

**Промт 2 — только диагноз, без решений:**
```
Теперь только диагноз, решения предлагать нельзя. По фактам определи природу: это баг в коде / поломка процесса / пользователь не понял интерфейс / ожидаемое поведение? Назови корневую причину, а не симптом. Если данных на однозначный диагноз не хватает — скажи чего не хватает, не угадывай.
```

**Промт 3 — решения С ПРЕЦЕДЕНТАМИ из интернета:**
```
Теперь решения. По каждому — кто УЖЕ решал эту проблему и как: найди в интернете реальные прецеденты (issue, статьи, обсуждения, репозитории), не пиши «обычно делают так». Минимум 2-3 варианта с источником-ссылкой, трейд-офф каждого. Без прецедента вариант не предлагай.
```

**Промт 4 — план + честная самопроверка:**
```
Собери план из выбранного решения: шаги, порядок, что меняем в каких файлах, как проверим. И в конце — честная самопроверка: назови чего ты НЕ знаешь в этой задаче, какие допущения делаешь, где можешь ошибаться. Без «всё под контролем».
```

## Плейбук 3. Окно-оркестратор (само НЕ пишет код)

**Когда:** план разбит на фазы, фаз несколько, хочешь держать общую картину и параллелить. Заводишь отдельное окно Claude Code, которое НЕ пишет код — только держит план, генерит промпты запуска фаз для других окон, проверяет diff, размечает параллелизм. Код пишут окна-исполнители.

**Установочный промт окна-оркестратора:**
```
Ты окно-оркестратор. Ты НЕ пишешь код сам — никогда. Твои задачи: держать в голове весь план из <путь к plans/файлу>, генерить мне промпт для запуска конкретной фазы (его я отнесу в окно-исполнитель), проверять присланный diff на соответствие плану, и говорить какие фазы можно делать параллельно. Прочитай план и подтверди одной строкой, что готов. Не начинай ничего, жди команды.
```

**Запросить промпт запуска фазы:**
```
Сгенерь промпт для запуска фазы <N> в отдельном окне-исполнителе. Включи: цель фазы, какие файлы трогать, критерий готовности, что НЕ трогать (границы), и требование проставить статус-маркер в файле плана. Только промпт, готовый к копированию.
```

**Проверка diff:**
```
Вот diff из окна-исполнителя по фазе <N>: <вставить diff>. Проверь против плана: сделано ли ровно то, что в фазе (не больше — не меньше), не задеты ли границы, нет ли drive-by правок соседнего кода. Вердикт: принять / вернуть с замечаниями. Не правь сам.
```

**Разметка параллелизма:**
```
Глядя на оставшиеся фазы плана: какие можно запускать ПАРАЛЛЕЛЬНО (не зависят друг от друга, не трогают одни файлы), а какие строго последовательно? Дай граф зависимостей и разметь в файле плана у каждой фазы тег [parallel] или [seq-after: N].
```

**Статус-маркеры внутри файла плана** (вписывать в `plans/*.md` руками или промптом исполнителю):
```
## Фаза N: <название>   [взял: окно-2 · 14:30] → [закончил: 15:10] → [принято оркестратором]
```
> Маркеры живут ВНУТРИ файла плана, не в отдельном трекере — один источник истины. (NB: формальный статус подфаз ЗАПУСКА — отдельная история, только через `launch-status.py`, эти маркеры — про код-фазы.)

## Плейбук 4. Микро-протоколы дисциплины (однострочники)

**Когда:** вставлять точечно в любой код-диалог, когда агент начинает своевольничать, торопиться, дрейфовать от замысла или плодить лишний код.

**Стоп-самоволка (агент рвётся писать код):**
```
Не пиши код, пока я явно не скажу «окей». Сначала покажи план / варианты / вопросы. Жди моего «окей».
```

**Вопросы по одному:**
```
Задавай вопросы по одному, не списком. Задал — жди ответ — задавай следующий. Список вопросов сразу не нужен.
```

**Пауза перед сложным шагом (Рич Хики, 15 мин):**
```
Это сложный/архитектурный шаг. Не начинай. Сформулируй решение, выпиши 2-3 альтернативы и трейд-офф каждой, и остановись — я возьму паузу 15 минут на подумать, потом вернусь с выбором.
```

**Фильтр «ошибки или код ради кода» (отсев самопридуманных правок):**
```
Прежде чем чинить найденное: по каждому пункту скажи честно — это правда ошибка, которая бьёт по работе, или это «код ради кода» / красивости / абстракция на будущее, которая не нужна? Вычеркни всё, что не реальная ошибка. Чиним только то, что осталось.
```

**Отлов дрейфа (опиши человеческим языком):**
```
Опиши человеческим языком, простыми словами, что делает этот код — что на вход, что на выход, зачем. Без терминов. Я сверю с тем, что мы вообще-то задумывали.
```

**Самооценка 0–100% (добивка до полноты, приём забран у Мари/ЛАБС):**
```
Оцени свою работу от 0 до 100%. Что конкретно не хватает до 100%? Перечисли пробелы по пунктам — потом скажу, что из этого закрываем.
```
> Дёшево вытаскивает то, что агент сам недоделал и не сказал. Ставить ПОСЛЕ того как агент отчитался «готово» — почти всегда находит 10–20% недоделок.

**«Как было / как стало» в 2 строки ДО изменения:**
```
Прежде чем менять — в 2 строки: «как было сейчас» и «как станет после правки». Если разница не укладывается в 2 строки или ты сам её не формулируешь — стоп, значит правка непродуманная.
```

## Плейбук 5. Вписать методологию в СУЩЕСТВУЮЩИЙ проект (без переписывания)

**Когда:** есть готовый код (свой или унаследованный), хочешь накатить методологию (idea/ + architecture/ + plans/), но НЕ переписывать рабочий код. Большинство приходит с готовым проектом — это не «строй заново», а «опиши что построено».

**Промт 1 — установка рамки (не переписать, а записать):**
```
У нас уже есть рабочий проект. Задача — НЕ переписать его, а ЗАПИСАТЬ что построено: реконструировать idea/ и architecture/ из реального кода. Код не трогаем. Ты археолог, а не архитектор с нуля. Подтверди, что понял рамку, и жди.
```

**Промт 2 — заполнить idea/ и architecture/ из кода:**
```
Пройди по реальному коду и заполни разделы idea/ (суперидея, аудитория, MVP-сцена, принципы) и architecture/ (сущности, схема данных, границы, права) ровно тем, что ВИДНО в коде. Где раздела в коде не прослеживается — напиши честно «пусто / не прослеживается из кода», НЕ выдумывай и не достраивай логику, которой нет. Лучше пустой раздел, чем сочинённый.
```

**Промт 3 — расхождения по ОДНОЙ за раз:**
```
Теперь найди ОДНО (одно, не все) самое важное расхождение между тем, как код написан, и тем, как по-хорошему должно быть по методологии. Опиши его, предложи что с ним делать. Не правь. Разберём это одно — потом попрошу следующее.
```
> Категорически НЕ просить «найди все расхождения» — агент вывалит гору и наломает. По одной проблеме за итерацию.

## Плейбук 6. Ретро как разблокировка (при застревании)

**Когда:** застрял на задаче, ходишь по кругу, подходы не работают. Прежде чем пробовать новое — поднять, что УЖЕ пробовали и что не сработало (в retrospectives/ и памяти feedback_*), чтобы не повторять круг.

**Промт:**
```
Я застрял на <задача/проблема>. Прежде чем предлагать новое — просканируй мои ретроспективы (retrospectives/) и память feedback_*: что мы по похожим задачам УЖЕ пробовали и что НЕ сработало, с причиной почему. Дай список «пробовали → не сработало → почему», и только ПОТОМ предложи подход, который этот список ещё не закрывает.
```
