# email-voronka - ниша и оффер в готовый build-sheet email-воронки для EN-рынка

Называешь нишу и оффер - скилл выдаёт `email-voronka-<slug>.md`: полный лист ручной сборки
воронки в UI Kit (или Beehiiv). Внутри - сущности платформы по порядку создания с настройками,
брифы всех писем дуги, чеклист deliverability и double opt-in для EU, чеклист проверки
собранной воронки. Дуга воронки (вход → welcome W1-W5 → nurture → монетизационные петли) -
универсальный каркас, брифы писем пишутся ПОД ТВОЮ нишу и оффер

Почему build-sheet, а не файл под импорт: ни Kit, ни Beehiiv не поддерживают импорт
автоматизации файлом (JSON и т.п.) - автоматизация строится вручную в UI визуальным
конструктором (R2, help.kit.com). У Kit есть share-link Visual Automation: владелец включает
шаринг и отдаёт публичную ссылку, по которой автоматизация копируется целиком в чужой
Kit-аккаунт вместе с тегами, sequences и формами (R2,
[help.kit.com/…/how-to-share-a-visual-automation](https://help.kit.com/en/articles/2502664-how-to-share-a-visual-automation)) -
это способ отдать ГОТОВУЮ собранную воронку ученику, но не способ собрать её из файла.
У Beehiiv аналога share-link в открытых источниках не найдено (R2)

## Когда применять

Триггеры:
- «сделай email-воронку под X» / «email-воронка для зарубежки»
- «воронка на Kit» / «воронка на ConvertKit» / «воронка на Beehiiv»
- «welcome-серия под нишу X» / «EN-воронка на email-list»
- `/email-voronka <ниша или слаг>`

## НЕ этот скилл

- Одиночное письмо или разовая рассылка → `email`
- Статья-лид-магнит (гайд за код-слово) → `lead-magnit`
- RU-воронка в Telegram под код-слово → `tg-voronka`
- IG-директ воронка: RU → `chatplace-voronka`; EN → ManyChat вручную по build-sheet
  (отдельного скилла под ManyChat пока нет, кандидат в v2)
- Лендинг или страница захвата сверх штатных Kit Landing pages → `website`

Сами ТЕКСТЫ писем этот скилл не пишет - он выдаёт брифы. Каждый бриф исполняет скилл
`email` с флагом `--en` (у него Subject + Preheader + Body + CTA, гейты EMAIL-G1-10,
spam-trigger scan, mobile preview). Дублировать его работу здесь запрещено

Мостик «бриф дуги → v1-тип скилла email» (v1 умеет ровно три типа:
nurture-letter / launch-sequence-email / sales-letter):

| Бриф дуги | Тип для скилла email (v1) |
|---|---|
| W1-W5 welcome | nurture-letter по каркасу Soap Opera из брифа |
| Промо клуба (петля 1) | sales-letter |
| Запуск high-ticket (петля 2) | launch-sequence-email + sales-letter на окно продаж |
| Renewal и win-back (петли 3-4) | по функции письма: мягкие ценностные касания (value recap, early renewal, превью выгод, первые касания win-back) - nurture-letter с retention-целью из брифа; дедлайновые ступени (последние renewal-письма перед истечением, win-back «last chance») - sales-letter |

Когда в `email` появится тип welcome-email (v2) - W1-W5 переключить на него

## 🌉 ШАГ 0 - ПРОФИЛЬ ПРОЕКТА (единый мостик, обязателен)

Не переспрашивай всё заново на каждой воронке:
1. Есть `~/.business/profile.json` и заполнен - читай его: ниша, аудитория, бренд, оффер уже там
2. Нет или пуст - спроси ТОЛЬКО недостающее, по одному вопросу за раз

⚠️ У действующих учеников `~/.business/profile.json` RU-специфичен: рублёвые цены, RU-URL,
RU-ниша. Для EN-воронки данные из него как есть НЕ тащить - спроси EN-оффер, цену в $,
EN-ссылки; из профиля брать только суть ниши и голос

Входы, без которых не идём дальше:
- **Ниша и аудитория** - для кого воронка, какой главный результат обещаем
- **Оффер** - куда монетизационные петли ведут деньги: подписка-комьюнити и/или high-ticket
  продукт с ценой. Нет оффера - воронка строится в режиме прогрева: welcome + nurture без
  питч-петель, появится оффер - в build-sheet дописывается петля, каркас не перестраивается
- **Лид-магнит** - что человек получает за подписку. Годится и файл (PDF, чек-лист, шаблон - его
  отдаёт incentive-письмо формы), и статья-гайд по ссылке. Совсем нет магнита - СТОП: сначала
  сделать его (статью собирает скилл `lead-magnit`, ему нужен свой хостинг под публикацию; файл
  быстрее и хостинга не требует), потом воронка. Требование к магниту - конгруэнтность: тема совпадает
  с темой контента, из которого приходит трафик, это принцип Dan Koe - чем точнее совпадение
  темы поста и темы магнита, тем выше клик и opt-in (R4, growthinreverse.com разбор)
- **ESP** - Kit (дефолт: free-тир до 10 000 подписчиков, double opt-in включён по умолчанию,
  share-link для передачи воронки) или Beehiiv (автоматизации только со Scale $43/мес).
  Новичку по умолчанию рекомендуй Kit: автоматизации есть уже на Free, double opt-in
  включён по умолчанию. Сравнение и тарифы - `references/kit-build-sheet.md`
- **Вход** - откуда трафик и какой мостик: код-слово в IG через ManyChat, ссылка mid-video
  на YouTube, pinned comment, first reply на X, Featured на LinkedIn, content upgrade в статье.
  Детали мостиков по площадкам - `references/funnel-arc.md`

## Архитектура дуги (что генерится)

Полная дуга с функцией каждого блока - `references/funnel-arc.md`. Скелет:

```
Площадка → мостик (код-слово ManyChat / ссылка / pinned comment)
 → Opt-in (Kit Form или Landing page + лид-магнит)
 → W1-W5 welcome-серия по Soap Opera Sequence (Brunson, DotCom Secrets)
     W1 Set the Stage → W2 High Drama → W3 Epiphany → W4 Hidden Benefits → W5 Urgency + CTA
     W5 = мостик к первому питчу комьюнити
 → Nurture 1-2 письма/нед (измеренный оптимум MailerLite, R1)
 → Монетизационные петли:
     (1) промо комьюнити-подписки
     (2) launch-цепочка high-ticket на сегмент (делегируется email)
     (3) retention/renewal - 8 писем от -90 дней до дня истечения (R3)
     (4) win-back 24ч / 7д / 30д (R3)
 → Сегментация тегами: cold / engaged / member / buyer + служебный welcome-in-progress
   (на время welcome-серии) + правила «кому что не слать»
```

Каркас welcome-серии по письмам (функция, день, суть, куда CTA) -
`references/welcome-soap-opera.md`. Порядок сборки сущностей в Kit, тарифы, double opt-in,
deliverability - `references/kit-build-sheet.md`

## Workflow

### 1. Мостик (ШАГ 0) - собрать нишу / оффер / лид-магнит / ESP / вход

Без пяти входов не идём дальше. Совсем нет магнита - СТОП, сначала магнит (файл или статья через `lead-magnit`)

### 2. Суть лид-магнита - только из живого артефакта

Прочитай сам лид-магнит (файл или `curl -sL <url>`): что внутри, какие обещания, какой
первый шаг. Брифы W1-W5 и nurture опираются ТОЛЬКО на реальное содержимое магнита, нишу и
оффер из мостика. Выдумывать «что внутри» запрещено

### 3. Сборка build-sheet

Прочитай `references/funnel-arc.md`, `references/welcome-soap-opera.md`,
`references/kit-build-sheet.md` и собери файл `email-voronka-<slug>.md` из четырёх блоков:

**(а) Сущности Kit по порядку создания, с настройками каждой** - канон порядка сборки =
`references/kit-build-sheet.md`:
1. Form или Landing page - точка входа; в настройках формы - confirmation email
   (подтверждение подписки + выдача лид-магнита) и проверка double opt-in
2. Visual Automation - Entry point «подписка через эту форму» → Action Add Tag
   (тег лид-магнита + служебный `welcome-in-progress`) → Action Subscribe to Sequence
3. Sequence - welcome-серия W1-W5 с таймингами
4. Финальный шаг автоматизации - после завершения Sequence снять служебный тег
   `welcome-in-progress` действием «убрать Tag» (точное название действия смотрим в живом
   конструкторе, логика: убрать тег), иначе подписчик навечно выпадает из nurture-сегмента
5. Опционально - Condition-ветвления по поведению (открыл/кликнул) внутри той же
   автоматизации, ведущие к Tags/Segments для последующих Broadcasts
Дальше - Segments под nurture-рассылки Broadcasts и петли. Kit-путь в v1 - основной и
единственный пошаговый. Выбравшим Beehiiv: тарифы и double opt-in - в kit-build-sheet.md,
порядок сборки автоматизации ведём по живому интерфейсу Beehiiv с правилом «названия кнопок
не выдумываем, ученик присылает скрины». Формулировка настроек - «создай Sequence с
настройками X», названия кнопок и пункты меню НЕ выдумывать

**(б) Брифы всех писем дуги:** W1-W5 по каркасу welcome-soap-opera.md, nurture-принципы и
каденс, письма петель 1-4 по funnel-arc.md. Каждый бриф: позиция в дуге, функция письма,
день отправки, суть под нишу, куда ведёт CTA, кому НЕ отправлять (сегмент), тип для
`email --en` - по таблице-мостику из шапки. В брифе явно:
исполнитель текста - скилл `email --en`

**(в) Чеклист deliverability и double opt-in для EU** - из kit-build-sheet.md: SPF/DKIM/DMARC,
one-click unsubscribe, spam rate, прогрев домена, double opt-in под юрисдикции EU

**(г) Чеклист проверки собранной воронки** - прогон глазами после ручной сборки: тестовая
подписка проходит всю цепочку, лид-магнит доставляется, теги вешаются, тайминги Sequence
совпадают с build-sheet, отписка работает, сегменты-исключения не получают чужие письма

### 4. Гейты (все обязательны)

- **Гейт фактов платформы.** Все утверждения про UI Kit - только сущности, подтверждённые R2:
  Forms, Landing pages, Broadcasts, Sequences, Visual Automations, Tags, Segments. Конкретные
  названия кнопок, вкладок и пункты меню в build-sheet не попадают. Экран не видел - маршрут
  не выдумываю
- **Гейт плейсхолдеров.** В финальном build-sheet ни одного `{{...}}` и ни одного
  «[вставь сюда]»: каждое поле заполнено данными мостика или помечено как вход ученика с
  точным описанием, откуда взять
- **Гейт humaniser.** Каждый текст, который пишется при исполнении брифов (через `email --en`
  или руками в build-sheet), гонится через `~/.claude/skills/humaniser/prompt.md`. Для EN это
  тоже действует: без клише-tells (delve / unlock / game-changer и весь блок категории 15),
  без em-dash, без triple-X parallel
- **Гейт источников.** Каждый метод в build-sheet - с автором и источником. Цифра, которую
  ресёрч пометил вендорской или неподтверждённой, несёт эту пометку и в build-sheet

### 5. Доставка

Показать в чат: слаг, выбранный ESP, скелет дуги, 1-2 брифа для примера, статус гейтов.
Файл `email-voronka-<slug>.md` - назвать полный путь. Следующий шаг ученика - один: собрать
воронку в UI по блоку (а) и заказать тексты через `email --en` по брифам блока (б)

## Принципы

1. Каркас дуги (opt-in → W1-W5 → nurture → петли → теги) универсален, не трогаем. Под нишу
   меняются брифы, оффер и лид-магнит
2. Build-sheet без плейсхолдеров: всё под конкретную нишу из мостика
3. Тексты писем - только через `email --en`, скилл-воронка выдаёт брифы
4. Метод мастера - всегда с именем и источником (Brunson, Settle, Chaperon, Porterfield,
   Barry, Welsh - все с URL в references)
5. Единственное действие читателя в питч-письмах = переход по офферу. Другую «домашку»
   не давать
6. Правила сегментации «кому что не слать» - часть каждого брифа, не приложение

## Anti-patterns

- Выдумать «что внутри лид-магнита», цену, кнопку в UI Kit или цифру бенчмарка без источника
- Обещать ученику «импортируешь файл в Kit» - импорта файлом нет, есть только share-link
  готовой автоматизации Kit → Kit (R2)
- Написать тексты писем внутри build-sheet, минуя `email --en` и его гейты
- Отдать build-sheet с плейсхолдером или с вендорской цифрой без пометки
- Слать launch-цепочку по всей базе без сегмента - правила исключений обязательны
- Пропустить мостик и генерить «вообще»: воронка обязана быть под конкретную нишу и оффер
