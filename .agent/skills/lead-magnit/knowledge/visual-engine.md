# Движок визуала: как картинка ВЫВОДИТСЯ из статьи

> Генераторы картинок и сборщики запросов в пакет НЕ входят: ниже описан их интерфейс,
> по которому Клод соберёт такой же инструмент на твоём проекте. Команды даны как описание
> интерфейса, а не как готовый запуск

> **Когда читать:** на Этапе 2 (раскладка) - визуальные задачи ставятся вместе со структурой;
> на Этапе 3 (контент) - визуалы производятся и принимаются по осям. Технические правила файлов
> (alt, имена, вес, lazy, CLS) живут в `visual-layer.md`, здесь - методология вывода изображения
> из смысла. Машина движка - `visual_engine.py` в наборе генераторов из `config.image`
>
> **Закон одной строкой:** изображение ВЫВОДИТСЯ из содержания раздела, а не подбирается
> красивой сценой под тему

## 🔒 Закрытые каналы для SEO-статей (с этой редакции)

Закон владельца: картинка в SEO-статье имеет право быть ТОЛЬКО ультра-реалистичной и
ТОЛЬКО ценной. Вывод из смысла раздела больше не сцена (сгенерированная композиция), а
ДОКАЗАТЕЛЬНЫЙ КАДР одного из четырёх легальных классов:

- **result** - кейс-превью: результат функции сервиса в реальном интерфейсе, не «скрин главной»
- **step** - путь клика: реальный интерфейс, прохождение пути клиента, рамка-аннотация «жми сюда»
- **own-run** - свой прогон: окно-чат Claude Code (панель VS Code) или веб-панель результата;
  окно оболочки/терминала в этот класс НЕ входит
- **inherited** - унаследованный кадр: перенесён с уже существующей страницы при её ревизии,
  съёмку инструмент не подтверждал, класс переходный. Только РЕАЛЬНЫЙ скрин интерфейса со
  старой страницы; кадр генеративного происхождения (сцена, предмет, руки, плашка, мем,
  код-рендер) НЕ наследуется никогда - он снимается заново `shot.py` или снимается со страницы
  совсем, ось закрывает `.vizblock`

Генеративный канал НЕ производит НОВЫХ кадров нигде в SEO-контуре - ни в новой статье, ни при
ревизии легаси-страницы. Разделы ниже не удалены по двум причинам: канал живёт для
`carousel`/`post` (их файлы этот раздел не трогает), а в SEO-контуре по нему только ЧИТАЮТ уже
стоящий кадр - понять, по каким правилам он собран. Новый кадр на ревизии = съёмка `shot.py`
или `.vizblock`. Закрыты для SEO-статей целиком:

| Канал | Где в этом файле | Что делал |
|---|---|---|
| Генеративный фото-канал | раздел 11 (`gpt_render.py` / `chatgpt_cover.py` / `prompt_compiler.py` / `codex_image.py`) | собирал промпт и рендерил сцену через ChatGPT/Codex |
| Арт-дирекшн слоями | раздел 4 (8-слойный стек, «Читаемый чужой интерфейс») | делал сгенерированный кадр похожим на предмет |

Вне этого файла (канон - `visual-layer.md`) тем же законом для SEO-статей закрыты: код-рендер
сцены обложки (`cover.py`), мем-шаблоны (`meme.py`), `og_hero.py` целиком - и заголовочная плашка (`--variant paper|dark|emoji|grid` по умолчанию), и `--illustration`.

Генеративная декоративная сцена, «скрин главной» вместо функции и кадр ради пола плотности -
брак класса «декорация/нейрослоп» (`visual-defects-catalog.md`), даже если формально прошёл
остальные оси приёмки (раздел 6, A1-A13). Нет доказательного кадра под факт раздела - кадр не
ставится, ось закрывает `.vizblock`

## 0. Почему «понятно ли, о чём статья» - плохой критерий

Старый критерий приёмки звучал так: «поймёт ли человек по картинке, о чём статья». Он завалил
работу трижды подряд, и вот почему:

- **Он бинарный.** Ответ «да/нет» не говорит, ЧТО править. Приёмщик говорит «непонятно»,
  исполнитель гадает: сцену менять, свет, объект, подпись
- **Он проходится метафорой.** Обложка с абстрактной оконной рамой формально «про окна»,
  то есть про Windows. Критерий пройден, читатель не узнал ничего
- **Он ничего не требует от кадра.** Картинка может не содержать ни одного факта статьи и всё
  равно «быть про тему». Так рождается декорация: красиво, дорого, пусто
- **Он не масштабируется.** Пятнадцать визуалов в статье, семь статей в кластере - на сотне
  картинок «понятно/непонятно» превращается в настроение приёмщика в конкретный день

Движок заменяет один вкусовой вопрос на цепочку, где каждое звено проверяемо:

```
раздел статьи -> якоря раздела -> тип визуальной задачи -> спецификация визуала
             -> производство -> замер по осям (A1-A13) -> переделка по провалившейся оси
```

## 1. Карта визуальных задач

Статья разбирается на смысловые единицы, и каждая получает СВОЙ тип визуала по назначению.
Тип выбирается не по вкусу и не по тому, что легче отрисовать, а по тому, что читателю нужно
сделать с этим куском текста

> 🔴🔴 **ТЕРМИНАЛЬНЫЕ СЦЕНЫ ВЫВЕДЕНЫ ИЗ ПРОИЗВОДСТВА по решению автора** (закон владельца, канон -
> `knowledge/novice-standard.md` §5). Новые статьи не производят ни терминал-скринов, ни
> терминал-мокапов: их читатель-новичок не понимает. Всё, что ниже описано про среду «терминал»
> (приметы, спецификации, примеры), остаётся в файле для РЕВИЗИИ легаси-страниц, где мокап уже
> стоит, и для аудита старого корпуса. Планируя визуал новой статьи, выбирай скрин реального UI
> или HTML-блок `.vizblock.vizsteps`

> 🔴 **Инструмент «карточка-*» ниже - ЛЕГАСИ.** HARD-запрет владельца на текст-картинку
> («зачем генерировать текст картинкой - это ухудшает загрузку и не даёт пользы») исключает рендер
> схемы/сравнения/чек-листа изображением. Три типа ниже используют вместо картинки HTML-блок
> `.vizblock` (легче картинки, читается в тёмной теме, индексируется поиском) - канон `visual-layer.md`

| Тип | Что делает читатель | Каноническая форма | Класс кадра | Якорей / классов | Инструмент |
|---|---|---|---|---|---|
| **действие-шаг** | повторяет за статьёй | скрин реального UI с аннотацией «жми сюда» ИЛИ HTML-блок `.vizblock.vizsteps` (терминал-мокап - ЛЕГАСИ, см. врезку ниже) | step (или `.vizblock`, если реального клика нет) | 3 / 2 | `shot.py --scenario`, разметка vizsteps |
| **устройство системы** | понимает, как оно работает | схема с подписанными узлами и явным направлением потока | `.vizblock`, не кадр | 3 / 2 | HTML-блок `.vizblock.vizsteps` (картинка-карточка ЗАПРЕЩЕНА) |
| **сравнение** | выбирает | две колонки + ЯВНЫЙ вердикт кому что брать | `.vizblock`, не кадр | 4 / 2 | HTML-блок `.vizblock.vizcompare` (картинка-карточка ЗАПРЕЩЕНА) |
| **состояние-результат** | видит, ради чего всё | до/после одной и той же сущности, два РЕАЛЬНЫХ скрина | result | 3 / 2 | `shot.py` до и после |
| **предостережение** | опознаёт свою беду | как выглядит ошибка + что нажать | step / result (или `.vizblock` с текстом ошибки) | 2 / 2 | `shot.py` реального окна с ошибкой ИЛИ `.vizblock` |
| **данные** | верит цифре | цифры с источником, видимые в реальном интерфейсе | result (или `.vizblock` с источником в футере) | 3 / 2 | `shot.py` ИЛИ HTML-блок `.vizblock` с источником в футере (картинка-карточка ЗАПРЕЩЕНА) |
| **памятка** | сохраняет себе | чек-лист под шаринг | `.vizblock`, не кадр | 4 / 2 | HTML-блок `.vizblock.vizcheck` (картинка-карточка ЗАПРЕЩЕНА) |
| **обложка (hero)** | решает, читать ли | кейс-превью: результат функции сервиса в реальном интерфейсе (для тем без стороннего UI - own-run «окно-чат») | result / own-run | 2 предметных / 1 | `shot.py --url` или `--scenario` |

Читается так: «якорей / классов» = сколько реальных фактов раздела обязано попасть в кадр и из
скольких РАЗНЫХ классов (одна и та же команда, повторённая пять раз, - это один класс, а не пять
якорей). «Класс кадра» - один из четырёх легальных по закону по решению автора (раздел «Закрытые
каналы» выше); строки без класса собираются HTML-блоком `.vizblock`, не картинкой. Машинная карта
типов с порогами живёт в коде: `visual_engine.py --types`

**Правило выбора типа.** Не «какой визуал сюда красивее», а три вопроса к разделу подряд:
что читатель должен СДЕЛАТЬ после него (действие-шаг) → что он должен ПОНЯТЬ (устройство,
сравнение) → что он должен ЗАПОМНИТЬ (памятка, данные). Первый вопрос, на который есть внятный
ответ, и задаёт тип

**Обложка - отдельный тип.** Она не иллюстрирует статью, она несёт её ОБЕЩАНИЕ, и несёт
предметно. «Про технологии вообще» обещанием не является. Обещание обложки = самая конкретная
вещь, которую читатель получит: ровно тот экран, ровно тот предмет, ровно та среда

## 2. Извлечение конкретики - ядро движка

Это и есть «ультра-релевантность»: не настроение «в тему», а факты раздела, физически
присутствующие в кадре

### 2.1 Что считается якорем

| Класс | Что это | Примеры формы |
|---|---|---|
| `cmd` | команда целиком, с флагами и пайпами | `tool --flag`, `a \| b` |
| `path` | путь, папка, имя файла с расширением | `%VAR%\dir\file.exe`, `~/.config`, `install.ps1` |
| `url` | адрес, домен, страница документации | `docs.example.com/page` |
| `ui` | горячая клавиша, пункт меню, подпись кнопки | `Win + X`, «Открыть папку» |
| `err` | точный текст ошибки | `is not recognized`, `permission denied` |
| `ver` | версия, номер сборки | `2.1.211`, `v18.0` |
| `num` | цифра с единицей, номер шага | `4 ГБ`, `82%`, `Шаг 3` |
| `prod` | имя продукта, имя окна, имя режима | `Windows Terminal`, `PowerShell` |

Не якорь: «нейросеть», «технологии», «код», «интерфейс», «быстро», «удобно», «современный
подход». Проверка одна: **это можно увидеть глазами и сверить со своим экраном?** Нет - не якорь

### 2.2 Как извлекать

Машинно, а не «на глаз»:

Ниже - ОПИСАНИЕ ИНТЕРФЕЙСА, а не готовый запуск: этого скрипта в пакете нет, ты собираешь его на своём проекте по этой спеке

```text
visual_engine.py --text razdel.txt                 # якоря раздела по классам
visual_engine.py --text razdel.txt --type compare  # + вердикт по типу визуала
```

Экстрактор работает по универсальным формам (словарь оболочек, формы путей, горячие клавиши,
латинские фразы-ошибки), а не по списку конкретных продуктов, поэтому переносится на любую тему
без переписывания. Один кусок текста уходит ровно в ОДИН класс: иначе `install.ps1` считается и
путём, и командой, и счётчик якорей врёт в свою пользу

### 2.3 Норма: картинка без якоря - брак ПО ПОСТРОЕНИЮ

Это ключевая замена вкусовой приёмки. Раньше картинку заворачивал приёмщик, если ему «не
читалось». Теперь визуал без единого якоря своего раздела **не собирается вообще** - генератор
падает с кодом 5 и печатает, какие поля спецификации надо заполнить. Спорить не с кем: это не
мнение, это отсутствие входных данных

Для доказательного кадра (result/step/own-run/inherited) правило работает иначе, чем для
код-генератора: не «падает с кодом 5», а «не снимается вообще» - нет реального клика/экрана под
этот факт, значит кадр не ставится, ось закрывает `.vizblock` (закон по решению автора). Сочинить кадр
вместо отсутствующего запрещено безусловно

### 2.4 Машинная цепочка проверки

Три звена, каждое проверяется отдельно:

```
1. ЯКОРЯ РАЗДЕЛА        visual_engine.py --text razdel.txt        -> список фактов
2. ПОЛЯ СПЕЦИФИКАЦИИ    тип визуала диктует обязательные поля     -> заполнены или нет
3. ПРИСУТСТВИЕ В ФАЙЛЕ  по данным генератора / по манифесту съёмки -> вердикт
```

**Звено 3 работает по-разному для двух семейств визуалов, и это принципиально:**

- **Код-рендер** (vizblock-карточки: схема / сравнение / чек-лист; легаси терминал-мокапы живут
  на старых страницах): текст визуала = данные генератора, поэтому якоря проверяются прямо в
  них. Плюс проверка ВЫВЕДЕННОСТИ: не меньше 60% якорей карточки обязаны реально стоять в
  тексте своего раздела. Иначе визуал сочинён РЯДОМ с разделом, а не выведен ИЗ него -
  формально якоря есть, а связи с текстом нет
- **Доказательный кадр** (result / step / own-run / inherited - закон по решению автора, раздел
  «Закрытые каналы» выше): в кадре нет ничего нарисованного, есть только то, что физически
  стоит на реальном экране сервиса. Якоря раздела здесь не переводятся в предметы для
  генератора - они питают СЦЕНАРИЙ СЪЁМКИ: какая функция, какой вход, какой выход, какой клик
  нужен, чтобы это оказалось на экране. Текстовый якорь раздела превращается в вопрос к сценарию:

| Текстовый якорь раздела | Что фиксирует сценарий съёмки |
|---|---|
| команда / параметр, который вводит читатель | реальный интерфейс в момент ввода этого значения, курсор/фокус на поле |
| путь / расположение результата | окно (файловый менеджер, настройки, дашборд), где этот путь виден как есть |
| код ошибки | тот же интерфейс с этим текстом ошибки на экране в момент сбоя |
| версия / номер сборки | номер, видимый как реальная UI-надпись (about/settings), не бутафория |
| результат функции | экран ПОСЛЕ действия - готовый выход, а не форма ввода |

Проверяемым следом у доказательного кадра остаётся **манифест съёмки** - `shots-manifest.json`
лежит рядом с `index.html` статьи (`$WORK/<slug>/shots-manifest.json`) и в `assets/` не кладётся
никогда: каталог `assets/` уезжает на прод целиком, служебной записи там не место. В манифесте -
список кадров, их класс, URL/сценарий и дата съёмки. Приёмка сверяет кадр с записью манифеста и с
гейтом `frame-provenance`, а не с настроением приёмщика

## 3. Реализм и узнаваемость среды

Реализм - не «красиво», а «читатель опознаёт свою среду за полсекунды и верит картинке». Для
каждой платформы есть обязательные приметы; их отсутствие = брак по оси реализма, даже если кадр
прекрасен

| Среда | Обязательные приметы |
|---|---|
| **Windows** | хром окна с тремя кнопками справа · полоса задач вдоль нижнего края · синее поле консоли · реальные названия пунктов меню |
| **macOS** | светофор из трёх кружков слева · верхняя строка меню · системный шрифт интерфейса · док снизу |
| **окно-чат / панель ассистента в редакторе** (класс `own-run`) | боковая панель диалога с историей сообщений · дерево файлов проекта · поле ввода промпта внизу панели · один опорный элемент хрома окна (заголовок с именем проекта, вкладки редактора или светофор/кнопки системы). Кроп панели обязан сохранить хотя бы один опорный элемент хрома, иначе среда неопознаваема |
| 🔒 **терминал** (легаси) | строка приглашения с курсором · моноширинный набор · реальный вывод прогона · полоса заголовка окна. Терминальные сцены выведены по решению автора (`novice-standard.md` §5), новые статьи их не снимают - Claude Code показываем окном-чатом |
| **веб-интерфейс** | шапка продукта · адресная строка · полоса вкладок · узнаваемая типографика |
| **мобильное** | физический корпус телефона · статус-бар сверху · полоса жеста снизу |
| 🔒 **предметная сцена** (легаси) | предметы темы на реальной поверхности · следы использования · один источник света. Среда генеративная, доказательным кадром быть не может: для SEO-статей это класс 16 каталога (декорация/нейрослоп), канал живёт у `carousel`/`post`. В SEO-контуре новых предметных сцен не производим ни в новой статье, ни на ревизии - по этой строке только читаем уже стоящий кадр |

Строки без 🔒 - живые среды доказательного кадра, их приметы проверяет ось A3. Строки с 🔒
остаются в таблице ради ЧТЕНИЯ уже стоящих страниц (новый кадр по ним не собирается даже на
ревизии), у новой статьи такой кадр = брак

### 3.1 Запрещено как класс

Абстрактная геометрия ВМЕСТО интерфейса: голые скруглённые прямоугольники на месте окон, парящие
панели, светящиеся каркасы, обобщённый sci-fi HUD, платы, голограммы, неоновые сетки,
декоративные частицы, изображающие данные. Если в кадре есть экран, устройство или документ - у
него настоящая физическая форма этой вещи. У доказательного кадра запрет выполняется по
построению: снимается реальный интерфейс, рисовать нечего - поэтому проверка идёт глазами по
живым строкам таблицы выше плюс запись `class` и `url` в `shots-manifest.json`

> 🔒 **Механика в этой врезке закрыта для SEO-статей с этой редакции** (раздел «Закрытые каналы» в начале
> файла). Правило было вшито в каждый фото-промпт отдельным блоком и продублировано машинным
> стоп-листом клише: промпт с клише не уходил в генерацию. У съёмки промпта не существует вовсе,
> проверять по нему нечего. Туда же абзац про предметные фото: «конкретные предметы ЭТОЙ темы, а
> не что-то техническое вообще, кабель на бетоне в целом про доступ - декорация, а не якорь» -
> для новой статьи предметная сцена целиком легаси-канал и кадром быть не может, формулировка
> сохранена для ревизии старого корпуса

### 3.2 Конфликт «бренд против реализма» и как он решается

Бренд-палитра обычно запрещает холодное синее свечение. А примета Windows - это ровно синее поле
консоли. Если оставить запрет как есть, он стирает примету среды, и кадр возвращается к
абстракции: именно так «брендовая» обложка становится ни о чём

**Закон движка: палитра правит СРЕДОЙ кадра, примета платформы правит ЭКРАНОМ.** Экран держит
родной цвет своего интерфейса и остаётся островом света; стол, стены, предметы и воздух вокруг -
в бренд-палитре, холодный свет на них не разливается. Для доказательного кадра закон выполняется
сам собой: снимаем как есть, интерфейс на снимке уже в своих родных цветах, перекрашивать его под
бренд запрещено

> 🔒 **Легаси-механика того же закона** (генеративный канал, для SEO-статей закрыт): разрешение
> «экран в родном цвете, среда в бренд-палитре» было вшито в промпт-сборщик (`prompt_compiler.py`,
> раздел «Закрытые каналы») и включалось автоматически, когда в промпте объявлена платформа. У
> съёмки промпта нет, включать нечего - сам закон выше остаётся живым

## 4. Арт-дирекция слоями

> 🔒 **Закрыто для SEO-статей с этой редакции** (закон владельца, раздел «Закрытые каналы» в начале
> файла). Слоистый арт-дирекшн ниже - для ГЕНЕРАТИВНЫХ сцен (фото-обложка, код-рендер сцены).
> SEO-статьи такие сцены больше не производят: кадр = доказательство (result/step/own-run/inherited),
> а не композиция. Раздел не удалён: слоистый арт-дирекшн живёт у `carousel`/`post`, а в SEO-контуре
> по нему только ЧИТАЮТ уже стоящую сцену. Новых сцен он не производит ни в новой статье, ни на
> ревизии легаси-страницы - там новый кадр это съёмка `shot.py` или `.vizblock`

Плоский кадр читается как иконка, слоистый - как предмет. Обязательный стек (он уже работает в
код-рендере обложек, движок переносит его и в фото-промпты):

```
1 фон-градиентная сетка (никогда одна заливка)
2 атмосфера: дымка + мягкое свечение вокруг объекта
3 объект в перспективе (никогда в лоб, малые углы по трём осям)
4 свет: ОДИН источник -> контактная тень, средняя, дальняя + контровой блик по кромке
5 отражение объекта на поверхности под ним
6 передний план слегка не в фокусе
7 зерно поверх всего
8 виньетка по краям
```

Порядки величин, доказавшие себя в код-рендере: три тени вместо одной (одна тень = иконка, три =
предмет), отражение с блюром и маской-затуханием, зерно в три прохода (мелкое overlay + screen +
крупные пятна против бандинга), перспектива тремя малыми углами сразу

Девятый слой - типографика, вписанная в композицию, а не поставленная по центру пустого поля.
Отсюда требование к кадру: у фото-обложки заранее резервируется спокойная зона под текст (для
широкого формата - левые 45% кадра), и главный объект в неё не заходит

### 4.1 Читаемый чужой интерфейс - зона вранья генератора (правило от этой редакции)

Генератор никогда не воспроизведёт НАШУ команду и НАШ экран точно, а мелкая деталь бьёт по
релевантности статьи сильнее, чем красота кадра. Улики, на которых правило родилось: на обложке
гайда по Claude Code в терминале читалось `brew install ripgrep`, хотя реальная установка идёт
через `curl -fsSL https://claude.ai/install.sh | bash`; на обложке про память ChatGPT читались
устаревшие `chat.openai.com` и `ChatGPT 4o` в статье 2026 года

Правило. ФОРМА интерфейса остаётся настоящей (иначе включается абстракция, которую движок
запрещает как класс), а ТЕКСТ внутри неё читается как текстура. Три законных решения, в порядке
предпочтения:

1. экран уводится в лёгкий расфокус, боковой угол или полосу отблеска - строки видны, слова не
   разбираются
2. кадр строится на предмете и руках, экран остаётся боковым планом
3. 🔒 строка, которая ОБЯЗАНА читаться, кладётся сверху НАШЕЙ типографикой (заголовок, кикер), а
   не просится у модели - решение ЛЕГАСИ-канала. На доказательный кадр типографика не кладётся
   вообще (закон по решению автора): читаться обязан сам интерфейс на снимке, заголовок несёт H1
   страницы

В негатив-лист промпта добавлены жёстко: читаемые URL и домены, читаемые названия моделей и
версий, читаемые подписи пунктов меню, выдуманные названия продуктов на экране. В компиляторе это
`SCREEN_EXCEPTION` и `BAN` (`prompt_compiler.py`), в приметах среды - формулировки
`ENV_TELLS[*]["prompt"]` (`visual_engine.py`)

## 5. Читаемость в реальном слоте

Картинка живёт не в файле, а в колонке статьи на телефоне. Это самая недооценённая ось: визуал,
который «отлично смотрится» при просмотре файла, в вёрстке превращается в кашу

**Формула.** Колонка статьи на экране 390px - около 350 CSS-px. Кегль в файле сжимается в
`350 / ширина_файла` раз:

```
кегль_в_слоте = кегль_в_файле × (350 / ширина_файла)
порог          = 11 CSS-px
```

| Ширина файла | Минимальный кегль в файле |
|---|---|
| 1080 | 34px |
| 1200 | 38px |
| 1600 | 50px |

**Потолок элементов на кадр - 7.** Больше семи смысловых элементов (узлов схемы, пунктов списка,
строк колонки) на мобиле не читаются в любом кегле: даже если каждый разборчив, кадр перестаёт
читаться как целое

**Правило кропа.** Якорный объект занимает не меньше 40% площади кадра. Скрин интерфейса режется
до зоны действия ПЛЮС один опорный элемент вокруг неё для контекста (заголовок окна, соседняя
вкладка) - без опоры читатель не понимает, где он находится. Мелкий скрин НИКОГДА не растягивается
на всю колонку интерполяцией: файл отдаётся не меньше двойной ширины бокса, но и не увеличивается
из меньшего. Мелкий бокс - мелкий файл, крупный бокс - исходник нужного размера или другой кадр

**Практический вывод.** Горизонтальные карточки 1600px под текст-инструкцию на мобиле не работают:
типовой кегль 19-22px даёт 4.2-4.8 CSS-px в слоте. Для визуала в тело статьи рабочая связка -
вертикальный или квадратный холст, не больше 7 элементов и зум типографики до порога. В
референсной реализации это флаг `--fit-slot`: он пропорционально увеличивает всю типографскую
систему карточки (кегли, отступы, бейджи, радиусы), не трогая габариты холста, и карточка просто
становится выше - на мобиле это ровно то, что нужно

**Правило компенсации.** A1, A3, A8 и A9 не компенсируются ничем: красивый, оригинальный,
идеально читаемый кадр без якорей, без узнаваемой среды или декоративный вместо доказательного -
это и есть та обложка, из-за которой движок написан (закон по решению автора добавил A8/A9 к тому же
правилу). Остальные оси взаимозаменяемы в пределах одного балла

**Что значит «информативность» (A2) на практике.** Картинка обязана нести то, чего в соседнем
абзаце НЕТ или что там дано хуже: взаимное расположение элементов на экране, форму окна, порядок
шагов одним взглядом, вид ошибки, соотношение чисел. Если картинку можно удалить и абзац ничего
не потеряет - это декорация, и она снимается, а не переделывается

## 7. Цикл переделки

- **Провалила ось - переделка ИМЕННО по этой оси.** Не «сделай покрасивее», а «A4: кегль 22px даёт
  4.8 CSS-px, нужно 34 - зум типографики и минус два пункта». Каждый круг фиксируется одной
  строкой: какая ось, что изменили, какой замер стал
- **Минимум два круга.** Первый круг чинит провалы, второй ловит то, что первый сломал: поднял
  кегль - проверь, что элементы не полезли за край; добавил якорь - проверь, что не появилось
  клише; сменил сцену - прогони оригинальность заново. Собственная починка = кандидат в новый дефект
- **Контактный лист в конце.** Все визуалы статьи выкладываются рядом на одном листе и смотрятся
  глазами вместе. Три вопроса к листу:
  1. Не повторяют ли они друг друга (форма, композиция, доминирующий объект)
  2. Рассказывают ли они статью БЕЗ текста - от обещания обложки до финального чек-листа
  3. Есть ли в ряду дырка: раздел, где читатель делает что-то руками, а картинки нет
- **Контактный лист кластера.** То же самое для обложек всех статей серии сразу: две статьи с
  одинаковой сценой = дефект, читатель решает, что попал на ту же страницу

```yaml
приёмка:       A1 ≥3/2 · выведенность ≥60% · A4 ≤7 элементов
```

## 10. Сводка: что считается браком

- визуал без якорей своего раздела - брак по построению, генератор не собирает его вообще
- якоря есть, но их нет в тексте раздела - визуал сочинён рядом, а не выведен
- сравнение без явного вердикта - таблица, а не визуал
- абстрактная геометрия на месте интерфейса - запрещённый класс
- ни одной приметы платформы - читатель не опознал среду
- кегль ниже 11 CSS-px в слоте или больше 7 элементов - на мобиле не читается
- картинку можно удалить, и абзац ничего не теряет - декорация, снимается
- выдуманный вывод команды или нарисованный «по мотивам» чужой интерфейс - потеря доверия ко
  всей статье
- та же сцена, что у соседней статьи кластера, - читатель решает, что попал на ту же страницу
- **(закон по решению автора)** кадр без легального класса в `shots-manifest.json` - не `result`, не
  `step`, не `own-run`, не `inherited`: декорация/нейрослоп, класс 16 каталога
  (`visual-defects-catalog.md`), ось A8 не компенсируется ничем
- **(закон по решению автора)** «скрин главной» вместо результата функции - обложка сервиса вместо
  экрана ПОСЛЕ действия, ось A9
- **(закон по решению автора)** кадр поставлен только чтобы добить пол плотности (Порог 1,
  `visual-layer.md`), без единого факта своего раздела в кадре - декорация, снимается
- 🔒 легаси-канал (генеративное фото, для SEO-статей закрыто по решению автора, раздел 11): предмет
  фото-кадра выбран за созвучие с именем темы, а не за то, что о нём говорит статья («window»
  под Windows) - брак по оси каламбура
- 🔒 легаси-канал (там же): промпт фото собран короче коридора корпуса, без блока оптики/света
  числами или без следов использования - брак по построению даже с верным предметом

## 11. Компилятор промптов - фото не собирается из вдохновения, а СОБИРАЕТСЯ из блоков

> 🔒 **Закрыто для SEO-статей с этой редакции.** Компилятор промптов и генеративный фото-канал ниже
> (`prompt_compiler.py`, `gpt_render.py`, `chatgpt_cover.py`, `codex_image.py`) SEO-статьи больше
> не вызывают - кадр в SEO-статье обязан быть реальной съёмкой (`shot.py`, доказательные классы
> result/step/own-run/inherited). Раздел живёт для `carousel`/`post` и других скиллов, их файлы
> не трогаем; содержимое ниже не удалено, чтобы не сломать эти каналы

Разделы 1-9 выше держат ВЫВОД предмета из статьи (что должно быть в кадре). Этот раздел -
про ДРУГОЙ слой брака: даже с правильным предметом промпт может быть слишком куцым, чтобы
модель его удержала, или содержать ловушку, которую видно только когда знаешь, куда смотреть.
Разбор корпуса по решению автора (22 сырых кадра до кропа и типографики) дал ровно эту находку: и
эталон, и провал ссылались на один и тот же предмет темы («Windows» → «window»), но один
превратил созвучие в предмет статьи, а другой - в предмет со звуком имени темы. Разница была
не во вкусе, а в том, из скольких блоков и какой длины состоял промпт. Отсюда - машина, а не
чек-лист: `prompt_compiler.py` в `.business/scripts/seo/images/`

**Закон.** Промпт фото-обложки - не свободный текст, а девять обязательных блоков. Промпт без
любого блока не собирается вообще; собранный промпт не уходит в генерацию, пока не прошёл
машинный гейт по 14 осям. Это применение того же принципа раздела 2.3 («визуал без якоря - брак
по построению»), только на уровень ниже: не только якорь обязан быть, но и промпт вокруг него
обязан быть достаточно плотным и непротиворечивым, чтобы модель этот якорь удержала

**Девять блоков** (`Subject:` / `Scene:` / `What is happening:` / `Optics:` / `Light:` /
`Materials and wear:` / `Composition:` / `Colour:` / `Do not include:`) - порядок = порядок
приоритетов, модель тянется к началу. Полная роспись каждого блока и почему он обязателен -
`prompt_compiler.py --blocks`

**Гейт мерит числом, не вкусом**, по 14 осям: все девять блоков на месте и не куцые · длина
авторской части и всего промпта в коридоре, снятом с корпуса эталонов · ≥2 предметных якоря
темы статьи, и каждый ДОЕХАЛ в текст промпта дословно · доля предметных существительных против
абстрактных ≥0.90 · названы поверхность, помещение и ≥2 соседних предмета · ≥3 следа
использования (потёртости, пыль, отпечатки) · фокусное и диафрагма заданы ЧИСЛОМ, не словами ·
свет расписан пятёркой источник+направление+время/температура+качество+глагол эффекта ·
анти-слоп словарь (штампы вроде «cinematic lighting», «8k», «stunning») · **каламбуры по имени
темы** (см. ниже) · предметы, которые онтологически носят текст (вывеска, этикетка, обложка
книги) · внутренние противоречия (лежит и стоит одновременно, ночь и залито светом одновременно)
· воздух под типографику задан долей кадра числом, а не словом «есть место» · субъект - вещь с
материалом и возрастом, а не голая категория. Провал = промпт печатает, какая именно ось не
прошла и чем её добить, и НЕ уходит в генерацию (exit 5)

**Ось каламбуров - отдельная находка разбора корпуса.** `PUN_TRAPS` в компиляторе - таблица
пар «слово темы → предмет-ловушка»: Windows→оконная рама, Python→змея, Java→кофейные зёрна,
cookies→печенье, память→мозг, firewall→огонь, порт→морской порт, и так далее. Гейт включает
тему статьи в проверку и рубит промпт, если предмет кадра выбран за созвучие с именем темы, а
не выведен из того, что читатель реально делает по разделу (раздел 2 этого файла). Проверка
одна: «этот предмет назван потому, что о нём буквально говорит статья, или потому, что его имя
рифмуется с именем темы?»

**Библиотека сцен (`FAMILIES`)** - НЕ готовые промпты, а заготовки среды под повторяющиеся типы
тем сайта: `ustanovka` (установка софта), `dostup` (доступ и блокировки), `model` (работа с
моделью), `pamyat` (память и данные), `poisk` (поиск и проверка), `dengi` (деньги и тарифы),
`obuchenie` (обучение). Каждая семья даёт поверхность, свет, материалы и характер события со
слотами `{a1}`/`{a2}` под предметные якоря КОНКРЕТНОЙ статьи - без якорей семья не собирается,
сюжет всегда приносит статья, не библиотека (та же дисциплина, что в разделе 1 про обложку:
тема даёт среду, а не сюжет). У каждой семьи есть свой список типовых ловушек-декораций (карта
- `prompt_compiler.py --families`)

🔴 Правка направления по решению автора. Прежняя версия переводила темы в АНТИКВАРНЫЕ предметы-аналоги
(латунный тумблер, картотечный ящик, лупа, перфолента) - владелец забраковал: «мы не занимаемся
ремонтом помещений», к нейросетям и вайбкодингу это отношения не имело. Новая версия - СЕГОДНЯШНЯЯ
техника: ноутбук, монитор, терминал, код, чат с ассистентом. Ремесло (свет числом и направлением,
оптика числами, следы использования, аномалия-деталь, воздух под типографику) не менялось - только
предметы. Экран теперь - это и есть тема, поэтому запрет букв больше не глобальный: `SCREEN_EXCEPTION`
разрешает на экране легитимный английский текст (команда, код, интерфейс, цена), потому что читателю
нужно его узнать. Кириллица по-прежнему запрещена везде, вне экрана текст по-прежнему нечитаем/от руки.

**Использование:**

Ниже - ОПИСАНИЕ ИНТЕРФЕЙСА, а не готовый запуск: этого скрипта в пакете нет, ты собираешь его на своём проекте по этой спеке

```text
# спека статьи (тема, якоря с исходной сущностью раздела, семья сцен, платформа) -> промпт + гейт
prompt_compiler.py --spec specs/claude-code-windows.json

# режим доработки: не ругается, а показывает, чем добить каждый непройденный блок
prompt_compiler.py --spec specs/claude-code-windows.json --refine

# гейт по чужому/готовому промпту тем же мерилом
prompt_compiler.py --gate-file /tmp/prompt.txt --topic "тема статьи"

# сохранить скомпилированный промпт для генератора
prompt_compiler.py --spec specs/x.json --out /tmp/x.compiled.json
gpt_render.py --spec /tmp/x.compiled.json --slug x --title "..."
```

**Интеграция с генератором - гейт нельзя обойти.** Точка входа для рендера - `gpt_render.py`,
не `chatgpt_cover.py`. Промпт в генерацию уходит только двумя путями: `--spec` (скомпилированный
JSON, уже прошедший гейт при сборке) или сырой `--prompt`, который ПЕРЕД отправкой в генератор
прогоняется через тот же `PC.gate()` - провал печатает тот же отчёт по осям и отменяет генерацию
кодом 5. Штатный путь один: `prompt_compiler.py --spec ... --out ...`, дальше
`gpt_render.py --spec ...`

🔴 Правка канала по решению автора (причина: окна браузера мешали владельцу работать за компьютером).
`gpt_render.py` по умолчанию рендерит тихим headless-каналом (`--engine codex`, значение по
умолчанию): внутри `codex exec` → системный скилл imagegen → встроенный инструмент image_gen,
логин тот же ChatGPT-аккаунт владельца, ключ API не нужен, окно браузера не открывается вообще.
Тот же канал доступен и напрямую, без гейта промпт-компилятора, простым вызовом:

```bash
python3 .business/scripts/codex_image.py --prompt "<промпт>" --out cover.png --size og
```

Размеры: `og` = 1536×1024, `square` = 1024×1024, `slide` = 1024×1280, `story` = 1024×1536, плюс
до 5 файлов-референсов через `--ref`. Проверка готовности канала без расхода генераций:
`python3 .business/scripts/codex_image.py --selftest`. Изолированный дом `~/.codex-image`
обязателен и держится движком сам - обычный `codex` подтягивает `~/.codex/AGENTS.md` (навигацию
системы) и вместо картинки уходит проводить онбординг, это проверено живьём

Живой браузер (кастомка `render-config.json`/`custom_gpt_url`, библиотека `chatgpt_cover.py` -
`LiveChrome`, детектор отказа, гейт уникальности) остаётся ЗАПАСНЫМ путём под явным флагом
`gpt_render.py --spec ... --engine browser`. Держать браузер основным путём запрещено - именно
открытые окна мешали владельцу работать. Предупреждения из старых версий этого файла про «один
прогон за раз», «жди пока откроется окно» относились к общему живому Chrome и на тихий канал не
распространяются: у него нет общего ресурса, прогоны параллелятся свободно
