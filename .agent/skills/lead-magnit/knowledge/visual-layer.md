# Визуальный слой статьи-гайда (канон)

> Генераторы картинок и сборщики запросов в пакет НЕ входят: ниже описан их интерфейс,
> по которому Клод соберёт такой же инструмент на твоём проекте. Команды даны как описание
> интерфейса, а не как готовый запуск

> **Когда читать:** на Этапе 2 (раскладка) - визуалы планируются вместе со структурой, не «потом»;
> на Этапе 3 (контент) - визуалы производятся вместе с текстом. Приёмка - `checklists/visual.md`.
>
> **Зачем:** статья без иллюстраций проигрывает и читателю (сплошная простыня, шаг «куда нажать»
> без картинки непонятен новичку), и поиску (картиночная выдача, дольше время на странице, og-превью
> при репосте). Визуальный слой - обязательная часть статьи, а не украшение.
>
> Инструменты рендера берутся из `config.image` (`image.tool`). Файл переносимый: конкретный набор
> скриптов и путь к нему - у каждого проекта свой, в конфиге. Пример локального набора «из конфига»:
> `og_hero.py` (типографская hero/OG-обложка 1200x630; для новых SEO-статей закрыт ЦЕЛИКОМ
> по решению автора - и заголовочная плашка `--variant paper|dark|emoji|grid` по умолчанию, и
> `--illustration`, `visual-engine.md`; живёт для `carousel`/`post`), `meme.py` (мем-шаблоны для
> шапки; для новых SEO-статей закрыт по решению автора, место занимает `own-run`-кадр), `shot.py`
> (скрин UI с аннотациями и сценарная съёмка; режим терминал-мокапа в нём легаси - новых
> терминал-мокапов не собираем ни в новой, ни
> в ревизуемой статье), `cards.py` (карточки: схема / сравнение / чек-лист / до-после), `convert.py`
> (webp+jpg, валидация alt и слага, готовый сниппет figure)

## 🔴 Страницу собирает ОДИН скрипт, обвязку решает он

Страница кластера руками не верстается и не патчится. Вход - JSON-спека с содержанием,
выход - готовый `index.html`, между ними ровно один скрипт:

```
python3 article-template/build_page.py spec.json -o index.html
```

Автор статьи отвечает ТОЛЬКО за содержание: заголовки, абзацы, картинки, FAQ, чек-лист,
источники, тексты CTA, мета. Всю обвязку - крошки, шапку, подвал, оглавление, классы, якоря,
порядок хвоста, `picture+srcset+sizes`, зум, время чтения, Метрику, favicon, JSON-LD -
принимает сборщик. Полный список решений живёт в шапке `build_page.py`, раздел
«КАНОН ОБВЯЗКИ», и здесь не дублируется, чтобы не разъехаться.

**Почему так.** по решению автора семь живых страниц кластера собирались разными агентами разными
скриптами и разъехались сразу по 14 признакам: у одной были свои классы
(`nav.crumbs`, `.relgrid`) и мёртвый дубль старых правил в CSS, якорь блока «Читайте также»
существовал в трёх вариантах, зум стоял на 3 картинках из 12 у одной страницы и на 0 из 21 у
другой, время чтения считалось шестью разными константами (разброс 24%), у страницы «Об авторе»
вообще не было счётчика Метрики, а `head` одной страницы был пересобран парсером. Чинить это
поштучно бессмысленно: следующая статья принесёт разъезд заново. Убирается только КЛАСС
дефекта - тем, что решение принимает одно место.

Спорные места разложены один раз и переспрашивать их не нужно:

| Место | Решение |
|---|---|
| «Источники» | `section#istochniki > h3#istochniki-h` с текстом «Источники». В оглавление не идут НИКОГДА |
| «Читайте также» | `section#related` + `.related-grid > a.related-card`. Якорь `chitayte-takzhe` и классы `.relgrid/.relcard` запрещены |
| Зум картинок | на ВСЕХ контентных `<figure>` (включая `.partfig`), кроме hero и мема |
| Hero | `<picture>` c webp-источником и `<img>` с jpeg-фолбэком. Голый `<img>` запрещён, нет jpeg - сделать jpeg |
| `sizes` | один на кластер: `(min-width:1200px) 720px, (min-width:760px) 680px, calc(100vw - 40px)` |
| Время чтения | одна константа 200 слов/мин; база счёта - лид + быстрый ответ + тело + чек-лист + FAQ |
| Порядок хвоста | Источники → чек-лист → FAQ → «поделиться» → автор → Читайте также → CTA-бот → подвал |
| Последний CTA | ВСЕГДА бот с код-словом, и он ниже блока «Читайте также» |
| Person в JSON-LD | один на весь сайт, из `DEFAULT_PERSON` в `schema-generator.py` (богатый: jobTitle, knowsAbout, sameAs, alumniOf). Постраничное переопределение запрещено |
| Якорь раздела | `id` секции-обёртки, и только если его нет - `id` самого h2 |
| Промо в теле | блок `.cta` - не раздел: заголовок опускается до h3, в оглавление не идёт |
| Эйрбров над hero | текст авторский (есть не у всех статей), обёртка каноническая `p.eyebrow.eyebrow-accent`, классы анимации не едут |

Приёмка перед заливкой - три гейта подряд, все на всех страницах сразу:

Ниже - ОПИСАНИЕ ИНТЕРФЕЙСА, а не готовый запуск: этого скрипта в пакете нет, ты собираешь его на своём проекте по этой спеке


## Норма плотности - гейт, не пожелание

Ось разложена на **два независимых порога**, оба проверяет `tools/structure-check.py <page> --visual`,
пороги живут в `seo-engine/seo-config-reference.yaml`, секция `tools.visual`.

### Порог 1 - пол иллюстраций

- **Пол = `<figure>` + `.vizblock` вместе**, порог задаёт `min_images` в конфиге (дефолт 3),
  независимо от длины статьи. Старая формулировка «минимум 3 настоящих `<figure>`» отменена
  (закон по решению автора): `.vizblock` (HTML-блок schema/compare/check) закрывает пол наравне с
  картинкой, канон синхронизирован с кодом: `floor_units = figures + vizblocks` в
  `check_visual_html` (page-ветка) и в `check_visual` (md-ветка), `tools/structure-check.py`
- Таблицы и код-листинги пол НЕ закрывают - именно он ловит голое полотно текста и страницу-заглушку.
  Если `<figure>` и `.vizblock` на странице нет вовсе, в счёт идут голые `<img>`
- Считается: hero, доказательные кадры (result/step/own-run/inherited), `.vizblock.*`
  (schema/compare/check), легаси-терминал-мокапы и легаси-мем на старых страницах. Не считается:
  иконки, аватар автора, декоративные элементы шаблона

### Порог 1-бис - ПОЛ СОБСТВЕННЫХ КАДРОВ, только `<figure>` (по решению автора)

🔴 Это ТРЕТИЙ порог оси, и он считает НЕ ТО ЖЕ, что порог 1. Пол иллюстраций выше закрывается
`.vizblock`-блоком наравне с картинкой, и это оставило дыру: страница с одним hero и восемью
HTML-блоками формально проходила визуальную ось целиком, а глазами читалась как заготовка.
Живой замер 245 собранных страниц корпуса: медиана `<figure>` = 3, p25 = 2, p75 = 5, max 13,
у эталона того же жанра 5-6 кадров на статью

- **Считаются ТОЛЬКО `<figure>` собранной страницы.** `.vizblock`, таблица, листинг этот порог
  НЕ закрывают - иначе он вернулся бы к порогу 1 и перестал ловить свой предмет
- **Норма - 3 собственных содержательных кадра** (hero + минимум 2 кадра тела). Число - медиана
  СВОЕГО корпуса, а не эталона: оно достижимо без выдумывания кадров
- **Судится только НОВОЕ производство** - страница, рядом с которой лежит манифест съёмки
  `shots-manifest.json`. У старого корпуса манифеста нет, и пол ему задним числом не выставляется
- **Кто ловит:** гейт `frame-density` стадии `page` производственного модуля, константа
  `FRAME_COUNT_MIN`. Ниже пола - стадия падает, публикация не едет
- **Как добирается недостающий кадр:** та же лестница деградации, что у hero (закон 22
  `seo-engine/ZAKONY-SEO.md`): съёмка публичной функции инструментом съёмки → чужой реальный
  кадр класса `sourced` с паспортом источника → `own-run` свой прогон → и только если ни одна
  ступень не дала кадра, ось закрывается блоком `.vizblock`, а пол остаётся непройденным честно,
  со строкой причины. Шага «взять hero второй раз под другим именем» в лестнице нет: два
  одинаковых байта - это один кадр, а не два

### Порог 2 - плотность

```
нужно = min( max(3, слов_прозы // 350), потолок 10 )
есть  = иллюстрации + .vizblock + таблицы + код-листинги
```

🔴 **Наборы у двух порогов РАЗНЫЕ, это не описка.** Пол считает только `figures + vizblocks`
(`check_visual_html`, `check_visual`), плотность считает `total` = иллюстрации + `.vizblock` +
таблицы + листинги (`visual_blocks_html`, `tools/structure-check.py`). То есть таблица и листинг
закрывают ПЛОТНОСТЬ, но не закрывают ПОЛ, а `.vizblock` закрывает оба. Эталон формулировки -
`knowledge/article-anatomy.md`, раздел «Визуальный слой»

- **База - объём ПРОЗЫ, не полный текст страницы.** Из тела `<article>` вычитаются: таблицы,
  код-листинги (`<pre>`), фигуры вместе с подписями, служебный хвост (FAQ, чек-лист, «Источники»,
  «Читайте также», финальный CTA, шаринг, карточка автора), навигация (`nav`, оглавление, крошки,
  промо-врезка). Остаются абзацы, списки, врезки, цитаты, заголовки разделов
- **Плотность закрывается визуальными блоками** - иллюстрацией, `.vizblock`-блоком, таблицей ИЛИ
  код-листингом. Каждый из них сам разбивает полотно текста не хуже картинки, требовать ещё и
  иллюстрацию к таблице избыточно
- **Делитель не менялся** - 1 визуальный блок на ~350 слов прозы, это число владельца
- **Потолок требования - 10 блоков.** Без потолка длинная опорная статья требовала бы 15-16 блоков,
  а единственный законный способ добить такую цифру - текст-карточки, которые запрещены (см. ниже)

### Ключи конфига (`tools.visual` в `seo-engine/seo-config-reference.yaml`)

| Ключ | Дефолт | Что делает |
|---|---|---|
| `words_per_image` | 350 | делитель плотности |
| `min_images` | 3 | пол иллюстраций (`figures` + `.vizblock` вместе) |
| `frame_count_min` | 3 | пол СОБСТВЕННЫХ кадров: только `<figure>`, `.vizblock` его не закрывает (порог 1-бис) |
| `density_basis` | `prose` | `prose` - считать от прозы (норма) · `full` - от полного объёма страницы (легаси) |
| `max_images_required` | 10 | потолок требуемых блоков, `0` = без потолка |
| `count_visual_blocks` | `true` | плотность закрывается иллюстрацией + `.vizblock` + таблицей + кодом (ключ `total` функции `visual_blocks_html`) · `false` - только иллюстрациями (ключ `figures`, `.vizblock` при этом из плотности выпадает, из ПОЛА - нет) |

Комбинация `density_basis: full` + `count_visual_blocks: false` возвращает старое поведение (от
полного объёма страницы, закрывает только `<figure>`) - аварийный откат, не норма по умолчанию.

### Что изменилось по решению автора

До этой даты объём считался от ПОЛНОГО тела статьи (проза + таблицы + код + FAQ + чек-лист +
источники + навигация), а закрывал требование только `<figure>`. На длинных табличных статьях
это красило гейт красным независимо от качества: `guide-karta` (6 иллюстраций при требуемых 10)
и `guide-smeta` (6 при 12) считались дефектом статьи, хотя половину визуальной нагрузки несли
таблицы, которые гейт не видел вообще. Обе страницы сейчас зелёные по новой норме без единой
новой картинки - причина была в формуле, не в контенте.

**Красный гейт по-прежнему не закрывать галочкой.** Если пол иллюстраций пройден, а плотность всё
ещё красная - не занижать порог под конкретную статью и не добивать цифру текст-карточками
(запрещены отдельным правилом, см. ниже). Пункт остаётся открытым с явной причиной в чек-листе и
ретро; порог в конфиге меняется только осознанным решением владельца, не задним числом под статью.

### Текст на карточках проходит те же гейты, что тело

Карточки рисуются из своих `assets/_src/*.json`, а не из `draft.md`, поэтому мимо Этапа 8 и
хуманизации проходит целый пласт текста. На guide-smeta карточка-вердикт родила закрывающую
антитезу «..., а не до них» - ровно тот шаблон, который вычищен из тела. Правило: перед рендером
прогонять текст карточек по `checklists/anti-ai.md` (разделы 2.1-2.3) наравне с телом.

Отдельно: подпись-футер карточки набирается моноширинным шрифтом, и обычный дефис в нём
визуально неотличим от длинного тире. Байтовый юникод-гейт этого не ловит - это рендер, а не
символ. В подписях и футерах карточек разделителем ставить `·`, а не дефис.

## 🔴 Шапка сайта - канонический состав

Шапка одинаковая на ВСЕХ страницах кластера, разночтений быть не может: читатель ходит между
гайдами и по шапке узнаёт, что это один сайт. Канон ровно один:

| Слот | Что стоит | Правило |
|---|---|---|
| обёртка | `<header class="site-header"><div class="inner">…</div></header>` | классы шаблона, НЕ утилитарные наборы вроде `sticky top-0 z-40 bg-paper/85` |
| логотип | `<ИМЯ>&nbsp;<ФАМИЛИЯ>` автора, неразрывный пробел между именем и фамилией | href всегда `/` (корень), не `/index.html` и не `index.html` |
| пункт 1 | `Гайды` -> `/blog/` | класс `.only-wide` (на узком экране уходит в бургер) |
| пункт 2 | `Об авторе` -> `/about/` | тот же класс; название ровно «Об авторе», вариант «Обо мне» запрещён |
| кнопка | ровно ОДНА `a.btn-nav`, текст **«На <ОФФЕР>»**, где `<ОФФЕР>` = имя продукта из `config.md` → `target_product` | текст на своём сайте ОДИН на все страницы кластера (не переписывается под статью); адрес - точка входа текущей воронки: `{{cta_url}}` у сборщика, у автора - `config.md` → `cta.invites_map` / `target_url` |
| бургер | `input.nav-toggle` + `label.nav-burger` + `div.nav-drop` | работает БЕЗ JS, виден только ниже 640px; пункты выпадашки дублируют шапку и берут ТОТ ЖЕ адрес воронки |

Копировать как есть, меняется один адрес в кнопке (он же в `.nav-drop-cta`):

```html
<header class="site-header">
  <div class="inner">
    <a class="site-logo" href="/"><ИМЯ>&nbsp;<ФАМИЛИЯ></a>
    <nav class="site-nav">
      <a class="only-wide" href="/blog/">Гайды</a>
      <a class="only-wide" href="/about/">Об авторе</a>
      <a class="btn-nav" href="<адрес воронки>">На <ОФФЕР></a>
      <input class="nav-toggle" type="checkbox" id="nav-toggle" aria-label="Меню" />
      <label class="nav-burger" for="nav-toggle" aria-hidden="true"><span></span><span></span><span></span></label>
      <div class="nav-drop">
        <a href="/blog/">Гайды</a>
        <a href="/about/">Об авторе</a>
        <a class="nav-drop-cta" href="<адрес воронки>">На <ОФФЕР></a>
      </div>
    </nav>
  </div>
</header>
```

Бургер держится на чекбоксе: состояние хранит браузер, селекторы `.nav-toggle:checked ~
.nav-drop` открывают выпадашку, скрипт не участвует и меню живо при выключенном JS. Порядок
узлов `input -> label -> div` ломать нельзя (`~` смотрит только вперёд), `id="nav-toggle"` и
`for="nav-toggle"` обязаны совпадать. Ниже 640px инлайн-пункты и пилюля скрыты, выпадашка -
единственный вход в «Гайды», «Об авторе» и воронку.

Адрес кнопки для кластера гайдов - лендинг воронки с меткой страницы (домен и путь
воронки берутся из конфига проекта, здесь они подставляются, а не хардкодятся):
`https://<домен>/<путь-воронки>/?utm_source=guide&utm_content=<slug>` (в HTML амперсанд
пишется `&amp;`). Исключение ровно одно и оно уже стоит: если у страницы есть СВОЯ бот-ссылка
со `start=<код-слово>` и она зафиксирована в `protected.md` байт-в-байт, кнопка ведёт на неё и
адрес не трогаем (так живёт любая страница-дверь под своё код-слово: конкретные `start=` и
слаг берутся из `protected.md` ТВОЕГО проекта, здесь они не называются - у каждого проекта
свои). Меняется адрес - состав и текст шапки не меняются.

CSS-пилюля - `.site-header .site-nav a.btn-nav` из `tokens.css`: ОДНО правило на обе темы,
заливка `var(--accent)`, текст `#FAF6EF`, ховер `filter: brightness(1.08)`. До этой редакции
правил было два (чернила на светлой + акцент в `@media prefers-color-scheme: dark`), копии
расходились при правке и пилюля уезжала в разный цвет по страницам кластера. Второе правило
не возвращать. Селектор обязан быть той же весомости, что и `.site-header
.site-nav a`, иначе цвет ссылки перебивает цвет кнопки и текст сливается с заливкой.
Страница на утилитарных классах (Tailwind-легаси) канон держит через override
`header nav a.bg-ink` в тёмной теме - саму разметку `<a>` при этом не трогаем.

Жёсткие правила:

- **все href корневые** (`/blog/`, `/about/`), никогда относительные: относительный
  `blog/` со страницы `/guide-x/` уводит на несуществующий `/guide-x/blog/`
- **кнопка не дублирует пункт меню.** Кнопка «Все гайды» на `/blog/` рядом с пунктом
  «Гайды» на тот же адрес - брак: два одинаковых выхода, ни одного в воронку
- **кнопка либо есть на всех страницах кластера, либо ни на одной.** Страница без кнопки
  теряет единственный платный выход и живёт как чужая
- **utm в ссылке кнопки** - только в query, сам адрес одинаковый на всех страницах

Почему гейт: на срезе по решению автора четыре живые страницы одного кластера дали четыре разные
шапки - двухпунктовая без кнопки (страница 1), трёхпунктовая на ОТНОСИТЕЛЬНЫХ ссылках
(страница 2), тот же набор на утилитарных классах со своей вёрсткой (страница 3) и
трёхпунктовая, где кнопка вела туда же, куда первый пункт (страница 4). Корень расхождения -
плейсхолдер `%%NAV_CTA_TEXT%%` в шаблоне: текст кнопки был переменной, и каждая волна
подставляла свой. Плейсхолдер убран, текст зашит.

Свод по решению автора: все четыре приведены к канону, замер по живому проду - пилюля `rgb(28,24,21)`
в светлой и `rgb(224,105,60)` в тёмной на всех четырёх, на 390px на всех четырёх остаются
логотип и пилюля, горизонтального переполнения нет. Приёмка - скрин шапки 1440 и 390 рядом
с эталонной страницей кластера, светлая и тёмная тема обе

## 🔴 Подвал сайта - канонический состав

Подвал живёт по тому же закону, что и шапка: он одинаковый на ВСЕХ страницах кластера.
Читатель дочитал гайд, и низ страницы обязан дать ему один и тот же набор выходов, а не
случайную вёрстку той волны, которая эту страницу собирала. Канон ровно один:

| Слот | Что стоит | Правило |
|---|---|---|
| обёртка | `<footer class="site-footer"><div class="inner">…</div></footer>` | классы шаблона, НЕ утилитарные наборы вроде `bg-ink text-paper border-t border-paper/15` |
| строка 1 | имя-ссылка на `/` + позиционирование одной фразой | фраза общая для кластера, не переписывается под страницу |
| строка 2 | ровно ПЯТЬ выходов через `·`: `Гайды` · `Об авторе` · `<ОФФЕР>` (имя продукта из `config.md` → `target_product`) · `Telegram` · `Политика` | порядок фиксированный; «Все гайды», «Обо мне», «Блог» запрещены; `Политика` всегда последняя |
| строка 3 | `<p class="muted">© ГОД Имя</p>` | последняя строка всегда копирайт |

```html
<footer class="site-footer">
  <div class="inner">
    <p><a href="/">Имя Фамилия</a> · <позиционирование одной фразой></p>
    <p><a href="/blog/">Гайды</a> · <a href="/about/">Об авторе</a> · <ссылка воронки> · <a href="<канал>" target="_blank" rel="noopener">Telegram</a> · <a href="/politika/">Политика</a></p>
    <p class="muted">© ГОД Имя Фамилия</p>
  </div>
</footer>
```

Адрес пункта воронки - тот же лендинг воронки с меткой страницы, что и в шапке:
`https://<домен>/<путь-воронки>/?utm_source=guide&utm_content=<slug>` (в HTML `&amp;`).
Исключение ровно одно и оно то же, что у шапки: если у страницы есть СВОЯ бот-ссылка со
`start=<код-слово>`, зафиксированная в `protected.md` байт-в-байт, пункт ведёт на неё и
разметка `<a>` не трогается вообще (страница-дверь под своё код-слово; конкретные `start=`
и слаг живут в `protected.md` твоего проекта, не здесь).

Жёсткие правила:

- **подвал не заменяет финальный CTA.** Ссылка на воронку в подвале - это утилитарный
  выход, а не призыв. Последним БЛОКОМ перед `<footer>` всегда стоит секция финального CTA
  с кнопкой в бота, и внутри неё ссылка на лендинг идёт ВЫШЕ кнопки. Порядок хвоста
  канона: `share -> author-card -> Читайте также -> section.cta.cta-final -> footer`
- **все href корневые**, как и в шапке: относительный `blog/` со страницы `/guide-x/`
  уводит на несуществующий `/guide-x/blog/`
- **страница на утилитарных классах** (Tailwind-легаси) получает не свою вёрстку, а те же
  `.site-footer > .inner`; нет `tokens.css` - объявить блок `.site-footer` в инлайн-стилях
  страницы на её же переменных (`--surface-invert` / `--on-invert`), состав разметки при
  этом обязан совпасть с каноном символ в символ
- **🔴 ссылка на политику обработки данных обязательна на КАЖДОЙ странице, где есть CTA
  со сбором контакта** (кнопка в бота, форма, подписка). Это требование 152-ФЗ: страница
  собирает контакт - читатель обязан видеть, по каким правилам данные обрабатывают, не
  уходя на другую страницу. Пункт `Политика` -> `/politika/`, корневой href, последним
  в строке 2. Гейт приёмки: `curl -s <URL> | grep -c "/politika/"` возвращает >= 1 на
  ВСЕХ страницах кластера, не только на странице об авторе
- **подвал либо у всех страниц кластера одинаковый, либо это брак.** Диагностика в одну
  команду: выдернуть `<footer …>…</footer>` со всех живых страниц и сравнить

Почему гейт: на срезе по решению автора четыре живые страницы одного кластера дали четыре разных
подвала - «имя · все гайды» из двух пунктов (страница 1), своя вёрстка
`.foot-in` с био и тремя ссылками (страница 4), утилитарные классы
`bg-ink text-paper border-t border-paper/15` без Telegram (страница 3) и канон
из четырёх выходов (страница 2). Эталон - страница 2, три остальные
приведены к нему в тот же день. Приёмка - скрин подвала 1440 и 390 рядом с эталонной
страницей кластера + grep, что во всех подвалах ровно пять пунктов в том же порядке.
Второй срез по решению автора: `/politika.html` и `/oferta.html` на проде живые (200), а ссылку
на политику давал только `/about.html` - шесть статей с CTA в бота собирали контакт без
неё. Пункт `Политика` добавлен в канон, шаблон и все страницы кластера

## 🔴 Оглавление (TOC) - единый стандарт страниц 2.0

Навигация - часть визуального слоя, и она одинаковая на ВСЕХ страницах кластера. Стандарт 2.0
ровно один: **липкая колонка на десктопе + сворачиваемый блок на мобиле**, оба из одного
списка пунктов.

| Экран | Что стоит | Поведение |
|---|---|---|
| ≥1200px | липкая колонка-сайдбар (`aside.toc-desktop`, sticky) | scroll-spy: текущий раздел подсвечен классом `.is-current` |
| <1200px | сворачиваемый блок (`details.toc-mobile`, атрибут `open`) | раскрыт по умолчанию, стоит после компактной CTA и до первой секции |

Пункты оглавления = все контентные h2 плюс чек-лист и FAQ. Оба списка собираются из ОДНОГО
источника, расходиться не могут. Первые 12 пунктов нумеруются CSS-счётчиком в такт нумерации
шаговых h2.

**Что считается контентным h2 и где живёт его якорь** (однозначно, это же читает гейт):

- контентный h2 - любой h2 в теле `<article>`, кроме служебных блоков шаблона: FAQ, чек-лист,
  «читайте также» / «соседние», «источники», финальный CTA, карточка автора, шаринг
- служебный блок опознаётся по `id`/`class` своей секции (`#faq`, `#chitayte-takzhe`,
  `.cta`, `#chek-list`, `#istochniki`) - размечать эти секции обязательно, иначе гейт
  посчитает их за разделы статьи и вилка длины поедет
- у каждого контентного h2 обязан быть якорь: **`id` на самом h2 ИЛИ `id` на секции-обёртке**.
  Второй случай - легальный: у баннеров-«частей» (`<section class="partbanner" id="part-vpn">`)
  якорь висит на секции, а h2 внутри голый
- контентный h2 без якоря вообще = брак: он не попадает в TOC. Гейт называет его текстом

Машинная приёмка - `tools/structure-check.py <index.html> --visual`: он печатает честную
строку `H2: в теле N · контентных M (с якорем …, без якоря …) · служебных K` и ругается на
каждый контентный h2 без якоря.

Запрещено: статичный инлайн-блок `<nav class="toc">` в теле статьи, оглавление руками мимо
шаблона, страница вообще без оглавления. Разметка и CSS - канон шаблона статьи
(`article-template/page-template.html` + `tokens.css`, раздел «Оглавление (TOC)» в
`components.md`), верстать TOC заново не нужно.

Почему гейт, а не пожелание: на ретрофите в даты запуска.2026 четыре живые страницы одного кластера
разъехались по трём разным реализациям (липкая колонка / статичный `class="toc"` / ничего).
Для читателя это три разных сайта, для поиска - скачущие поведенческие. Приёмка: скрины
1440 и 390 - на первом видна колонка и подсветка едет за скроллом, на втором список раскрыт
сразу и колонки нет

> 🔴🔴 **ВИЗУАЛ ШАГА СМЕНЁН по решению автора** (закон владельца, полный текст - `knowledge/novice-standard.md` §5):

> (перенесён со старой страницы при её ревизии). Строки таблицы ниже размечены классом; там, где класса нет - визуал НЕ
> картинка, а HTML-блок `.vizblock`

| Тип блока в статье | Какой визуал ставить | Класс кадра |
|---|---|---|

| Концепт / архитектура / «как это устроено» | HTML-блок `.vizblock.vizsteps` (нумерованные шаги со стрелками). Картинкой НЕ рендерить | `.vizblock`, не кадр |
| Чек-лист / памятка | HTML-блок `.vizblock.vizcheck`. Картинкой НЕ рендерить | `.vizblock`, не кадр |

Hero едет ОДНИМ файлом, обязательный мобильный файл-кроп отменён; вес держим под `config.image.max_kb` (`convert.py` печатает вес в КБ и даёт рычаг `--quality`, сам не режет), ключ `webp_srcset` у сборщика - ОПЦИЯ под ступень, положенную руками | result / own-run |
| «До / после» | Карточка before-after (два РЕАЛЬНЫХ скрина рядом), не текст-карточка | result |

| Кадр со старой страницы при её ревизии | Легально унаследованный кадр: съёмку инструмент не подтверждал, запись заводится руками - `shot.py --register-external <файл> --manifest $WORK/<slug>/shots-manifest.json --class inherited --mode relay --shot-at <дата старой съёмки>`, счётчик в отчёте гейта. Только РЕАЛЬНЫЙ скрин интерфейса со старой страницы: генеративная сцена, предмет, руки, плашка, мем и код-рендер НЕ наследуются никогда - на пересборке кадр снимается заново или ось закрывает `.vizblock` | inherited |

### 🔴 HARD: plain text в картинки не запекаем (правка владельца)

Текст-карточка (schema / checklist / compare, отрендеренная в PNG/JPG) в теле статьи -
ЗАПРЕЩЕНА. Причины владельца: картинка на сотни килобайт грузится дольше, чем стилизованный
текст; текст в картинке не выделяется, не индексируется и не адаптируется к тёмной теме.
Такие блоки живут HTML-компонентами `.vizblock` (vizsteps / vizcheck / vizcompare,
CSS - tokens.css раздел 14б), они же засчитываются гейтом плотности как визуальные блоки.
Картинкой в статье остаются ТОЛЬКО: доказательные кадры интерфейсов (result/step/own-run/inherited),
hero/og того же кадра, «до-после» из реальных скринов. 🔴 Терминал-мокап из этого списка ВЫВЕДЕН
по решению автора (`novice-standard.md` §5): на существующих страницах он живёт как легаси, в новых
статьях не производится.
Эталон ВИЗУАЛА - статья, где все иллюстрации это реальные скрины интерфейса; эталоном ТЕКСТА
такая статья не является автоматически, подача судится отдельно по `novice-standard.md`.
Прецедент по решению автора: 103 текст-карточки в 14 гайдах, владелец увидел с телефона и остановил;
49 из них при разборе оказались дублями соседнего текста/таблицы и удалены совсем.

Правило выбора для шапки (обновлено): hero = кейс-превью (`result`), для тем без
стороннего UI - `own-run` «окно-чат». Мем шапки для новых SEO-статей закрыт (`visual-engine.md`,
«Закрытые каналы»; легаси-канон мокапа переписки живёт ниже для существующих страниц). Шапка без
визуала не проходит приёмку

## 🔴 Палитра чат-мокапов - только брендовая

> 🔒 **Закрыто для новых SEO-статей с этой редакции** (`visual-engine.md`, «Закрытые каналы»):
> `meme.py` в SEO-статьях больше не вызывается - место чат-мокапа занимает `own-run`-кадр:
> реальный скрин окна-чата Claude Code (панель VS Code) или веб-панели результата. Раздел ниже -
> легаси-канон для существующих страниц и для ревизии старого корпуса, палитра и правила
> остаются нормой ТАМ, где мокап уже стоит на живой странице

Мокап переписки с нейросетью - самый частый визуал кластера, и именно он первым уезжает в
чужой стиль: рисовать «как в мессенджере» = взять синие пузыри на тёмно-синем, и страница
перестаёт быть твоей. Палитра чат-мокапа - та же, что у всей серии, других цветов в нём нет:

| Элемент | Тёмный вариант | Светлый вариант |
|---|---|---|
| фон панели | чернила `#1C1815` | бумага `#FAF6EF` |
| пузырь машины | нейтральный на тон светлее фона (`#272220`) | бумага на тон темнее (`#F1ECE2`) |
| пузырь человека | акцент терракота `#BE4A24`, текст бумагой | тот же акцент, текст бумагой |
| аватар «ИИ» | круг акцентом, инициалы бумагой | так же |
| подписи, «печатает…», хром UI | моно-шрифт, приглушённый тон | моно-шрифт, приглушённый тон |
| нижняя полоса | точка акцентом + имя автора слева, домен моно справа | так же |

Запрещено: синий/navy фон и синие пузыри (телеграм-стиль), зелёные пузыри (whatsapp-стиль),
градиенты, любой цвет вне палитры серии. Реплики внутри мокапа - живой текст, не выдуманный
вывод команд (см. раздел «реальный вывод» ниже).

Нижняя полоса с именем автора и доменом - обязательная часть мокапа, а не украшение: без
неё картинку невозможно опознать как нашу, когда её утащат в чужой пост. Мокап без полосы
приёмку не проходит.

Легаси-способ собрать мокап - `meme.py --template chat`
(шаблон уже несёт и палитру, и полосу). НОВЫХ мокапов не собираем ни на новой, ни на ревизуемой
странице: команда ниже оставлена, чтобы читать уже стоящие кадры, а место чат-мокапа в SEO-статье
занял `own-run`-кадр:

Интерфейс `meme.py` (в пакет НЕ входит, собираешь сам по этой спеке):

- `--template` chat
- `--top` "реплика человека|вторая реплика|третья"
- `--bottom` "ответ нейросети"
- `--out` <каталог статьи>/assets/<slug>-720.png


Холст подстраивается под число реплик, поэтому высота у каждого мокапа своя - `width`/`height`
у `<img>` брать из готового файла, а не копировать из соседней статьи (квадрат 1080x1080 по
инерции = растянутая картинка и скачок вёрстки).

Замер по решению автора: мокапы двух страниц кластера держат канон

## 🔴 HARD: обложка каждой статьи уникальна (гейт попарного diff)

**Закон.** Hero и og:image каждой статьи несут СВОЙ кадр. Повтор одного и того же кадра на
другой статье с подменённой подписью (пилюля, кикер, заголовок) = дефект, а не «единый стиль».
Норма с этой редакции - свой кадр результата на статью (`result`, для тем без стороннего UI -
`own-run`): у каждой статьи своя функция сервиса и свой экран, повтор экрана = повтор смысла.
🔒 Типографская og-карточка с общей брендовой рамкой и своим заголовком («её содержание и есть
текст») для новых SEO-статей ЗАКРЫТА вместе с каналом `og_hero.py` целиком - и заголовочная
плашка `--variant` по умолчанию, и `--illustration` (`visual-engine.md`, «Закрытые каналы»);
нормой она остаётся только легаси-исключением - на уже
стоящих страницах и при ревизии старого корпуса. Кадр, переиспользованный на чужой теме, - брак
в обоих мирах. Читатель видит два разных материала с одной картинкой и решает, что попал на ту
же страницу; в поиске и в соцпревью обе статьи теряют узнаваемость

og-кроп страницы с её же hero не сравнивается вообще: это одна съёмка в двух раскладках и слаг
у них общий (пороги ниже, очередь гейта - там же)

**Гейт перед публикацией.** Собрать hero и og всех страниц кластера в одну папку и прогнать
попарный `mean_abs_diff` по пикселям (Pillow + numpy, привести к одному размеру):

```python
from PIL import Image
import numpy as np, itertools, os
def load(p): return np.asarray(Image.open(p).convert('RGB').resize((600, 315), Image.LANCZOS)).astype(np.float32)
a = {f: load(os.path.join(d, f)) for f in sorted(os.listdir(d))}
for x, y in itertools.combinations(a, 2):
    print(round(float(np.abs(a[x] - a[y]).mean()), 2), x, 'vs', y)
```

Пороги (шкала 0-255):
- `< 6` между РАЗНЫМИ страницами = клон, публикация запрещена, обложку переделать
- `6-15` = один шаблон с подменой текста, глазами проверить, что смысловая нагрузка картинки
  это текст (og-карточка) - иначе тоже переделать. 🔒 Для новых SEO-статей ветка «смысловая
  нагрузка это текст, значит норма» ЗАКРЫТА законом выше вместе с типографской og-карточкой: у
  доказательных кадров пара `6-15` разбирается как повтор одного экрана и переснимается другой
  функцией или другой зоной кропа. Оправдание текстом остаётся только легаси-страницам
- `< 6` между hero и og ОДНОЙ страницы - норма: это одна фотография в двух раскладках
  (hero с кикером, og с заголовком)

**Вторая метрика - доля различающихся пикселей** (`(|Δ|.max(axis=2) > 16).mean()`). Средняя
разница обманывает на тёмных обложках: два разных ночных кадра дают низкий `mean|Δ|` просто
потому, что оба тёмные. Доля различающихся пикселей разводит их честно - у нормальных пар
она 37-75%, у клон-пары падает до 8-12%. Гонять обе цифры вместе:

- `mean|Δ| < 15` **и** различающихся `< 30%` = клон, переделать
- `mean|Δ| 15-25` при различающихся `> 35%` = разные сцены в одной палитре, норма

После замены на свои фото-сцены пара разошлась до `61.11` при 66.5%

**Как делать разные кадры (норма с этой редакции).** Разность берётся не из выдуманной сцены, а из
предмета съёмки: у каждой статьи СВОЯ функция сервиса и свой экран результата. Кадр снимается
`shot.py` в одном из легальных классов - `result` (результат функции), `step` (путь клика),
`own-run` (окно-чат Claude Code или веб-панель результата), `inherited` (кадр перенесён со старой
страницы при её ревизии). Две
статьи про один сервис расходятся РАЗНЫМИ функциями и разными экранами, а не разной обработкой
одного кадра. Сцены не выдумываются вообще. На кадр НИЧЕГО не печатаем: заголовок несёт H1 строкой
ниже, `og` - тот же кадр или его кроп, тоже без вшитого текста (`checklists/visual.md`, пункт

снимается свой

🔒 **Легаси-справка (для ревизии старых страниц, не для новых статей).** Прежняя норма звучала

**🔴 Третья метрика - СТРУКТУРА (обязательна с этой редакции).** Пиксельная разница слепа к
самому частому виду клона: та же сцена, другая палитра. Два изометрических рендера (светлый

корпуса 0.007-0.254. Порог `>= 0.40` = одна сцена, публикация запрещена.

**🔴 Гейт видит ОЧЕРЕДЬ, а не только прод (обязательно с этой редакции).** Сравнение только с
опубликованным кластером - дыра при параллельной публикации: два агента одновременно делают
две статьи, каждый честно прогоняет diff против прода и оба выпускают одну картинку. Индекс
общий на машину: `.business/scripts/seo/images/uniq.py`, хранилище
`cover-index/index.json` + миниатюры. Любая обложка встаёт туда со статусом `queued` в момент

```bash
python3 uniq.py --seed                                  # пересобрать индекс: обложки по хинтам
                                                        # имени + кадры-кандидаты в обложку
                                                        # из shots-manifest.json (result/own-run)
python3 uniq.py --check FILE --slug SLUG                # проверить (exit 4 = клон)
python3 uniq.py --register FILE --slug SLUG --role og   # проверить и встать в очередь
python3 uniq.py --publish SLUG                          # queued -> published после деплоя
python3 uniq.py --matrix A B C                          # попарная таблица трёх метрик
```

**Кто регистрирует кадр (обновлено).** Штатной точкой входа был `chatgpt_cover.py`
(регистрировал готовую обложку сам и падал с `exit 4` на клоне) - для SEO-статей этот канал
закрыт (`visual-engine.md`, «Закрытые каналы»), роль регистратора с него снята. Теперь hero и og
встают в общий индекс ОТДЕЛЬНЫМ шагом конвейера, сразу после съёмки, до вставки в страницу:

```bash
python3 uniq.py --register <каталог статьи>/assets/<slug>-result-1.webp --slug <slug> --role hero
python3 uniq.py --register <каталог статьи>/assets/<slug>-og.jpg      --slug <slug> --role og
python3 uniq.py --publish <slug>                                       # queued -> published после деплоя
```

`--register` = проверить и встать в очередь одним действием: клон даёт `exit 4` и в индекс НЕ
пишется. Кадры держим в `assets/` страницы - пути со служебными сегментами (`/shots/`, `/raw/`,
`/qa/`, `/preview/` и прочие из `SKIP_PARTS` в `uniq.py`) чистка `--prune` выкидывает из индекса
как снимки вёрстки. Картинки ОДНОЙ статьи (hero и og) друг с другом не сравниваются - слаг
общий, это одна съёмка в двух раскладках.

🔴 **Почему манифест обязателен и для очереди тоже (правка кода по решению автора).** `--seed`
пересобирает индекс С НУЛЯ, и обложку он опознаёт по хинту в имени файла (список `COVER_HINTS` в
`uniq.py` - `<slug>-og.jpg` под него подходит). Имя доказательного кадра по конвенции съёмки
(`<slug>-result-N` / `<slug>-step-N`) ни одного хинта не содержит, поэтому раньше
зарегистрированный hero после ближайшего `--seed` молча пропадал из индекса, и дыра параллельной
публикации открывалась заново ровно для кадров нового мира. Теперь у `--seed` ВТОРОЙ источник -
`shots-manifest.json` рядом со страницей (`manifest_frames()` в `uniq.py`): в индекс попадает
снятый кадр, слаг берётся из имени каталога манифеста, роль записи - `frame`. Отсюда
рабочее правило: кадра нет в манифесте - после `--seed` его нет и в индексе, значит `--register`
без записи манифеста живёт только до следующей пересборки. Регистрируй кадр И записывай его в
манифест (`shot.py --manifest ... --class ...`), это одна операция конвейера, а не две разные.

🔴 **В индекс идут только КАНДИДАТЫ В ОБЛОЖКУ - классы `result` и `own-run`** (`COVER_FRAME_CLASSES`
в `uniq.py`, правка 22.08.2026). Уникальность канон требует от hero и og, а шаговый кадр уникальным
быть не обязан: два гайда законно снимают один и тот же экран регистрации сервиса. Пока `step` и
`inherited` попадали в общий индекс, чужой шаговый кадр становился законным источником вердикта
«клон» и `exit 4` для ЧУЖОЙ обложки. Записи без поля `class` (манифест дописан руками, мимо `shot.py`) в индекс
тоже не идут. Практический вывод для съёмки: если кадр реально претендует на hero - снимай его
классом `result` или `own-run`, шаговым кадром обложку не закроешь.

## 🔴 HARD: реальный вывод и реальный экран, не выдуманный

**Закон честности не отменён, изменилась область его применения.** Новые статьи терминальных сцен
не производят вообще (`novice-standard.md` §5), поэтому правило ниже работает там, где скрин, вывод

**Любой вывод команды в кадре - ТОЛЬКО с реального прогона.** Порядок: выполнить команду →

Выдумывать вывод, «восстанавливать по памяти», брать из чужих скринов - ЗАПРЕЩЕНО: версии, пути и
формулировки в реальном выводе другие, читатель сверяет свой экран с картинкой, расхождение = потеря
доверия ко всей статье. Нет возможности выполнить команду (нужен чужой аккаунт, платный сервис) →
кадра не делаем, показываем копируемую команду и словами «что увидишь». То же для скринов UI:
только реальный интерфейс, никаких нарисованных «по мотивам» экранов чужих платформ.
🔴 Из этого правила прямо следует замена визуала шага на `.vizblock.vizsteps`: снимков реального UI
на весь корпус не снять, а рисовать «по мотивам» запрещено - значит шаг несёт HTML-блок, а не картинку

## Технические правила каждой картинки

- **alt 50-125 знаков**, описывает что на картинке; запрещены пустые «изображение», «картинка»,
  «иллюстрация», «скриншот» без содержания
- **Имя файла - слаг-через-дефис** с ключом темы: `slug-chto-pokazano.webp` (латиница, дефисы,
  без пробелов и подчёркиваний). 🔴 Для доказательных кадров имя строго по конвенции:
  кадры тела - `<slug>-result-N` / `<slug>-step-N`, шапка и превью - под именами реестра
  `<slug>-hero` и `<slug>-og` (имя говорит про РОЛЬ кадра на странице, класс происхождения живёт
  в поле `class` манифеста). Терминальные слова запрещены и в имени файла,
  и в `alt`, но машина бьёт их ДВУМЯ РАЗНЫМИ словарями, и путать их дорого: имя файла проверяет
  `SHOT_SRC_TOKENS` (десять латинских токенов, срабатывает целым СЕГМЕНТОМ имени), а `alt` и
  `class` - совсем другой шаблон `SHOT_ALT_HINT` (русские «терминал»/«консоль»/«командная
  строка»/«оболочка» плюс часть латинских; `cli`, `cmd`, `tty` в нём нет вовсе). Дом обоих -
  `tools/novice-check.py`, разбор с примерами промахов - README каталога `config.md` →
  `image.path`, подраздел `--terminal`. Списки по памяти не переписываем и в канон не копируем:
  копия протухнет молча (терминальные сцены выведены по решению автора, `novice-standard.md` §5)
- **figcaption** у каждой иллюстрации: что на картинке и зачем смотреть (1 строка)
- **width/height обязательны** у каждого img (анти-CLS: без них вёрстка прыгает при загрузке)
- **hero - единственный eager:** `loading="eager" fetchpriority="high"`; ВСЕ остальные картинки -
  `loading="lazy" decoding="async"`
- Формат: webp (основной) + jpg fallback; og:image - jpg/png (соцсети webp не везде понимают)
- Вес: картинки жать (потолок - из `config.image.max_kb`), совокупный бюджет страницы держит
  `checklists/visual.md`
- **Мелкий бокс = мелкий файл.** Картинка в боксе NxN пикселей отдаётся файлом максимум 2N
  по стороне. Аватар автора в боксе 72x72 = webp ~150x150 (~5 КБ), а не исходник 600x600 на 89 КБ:
  иначе один аватар весит четверть страницы. Исходник остаётся исходником, в вёрстку не идёт
- **alt фото человека** = кто на фото И в каком качестве выступает в этом материале
  (`<Имя Фамилия>, автор гайда: <роль/специализация>, портрет в квадратном кадре`);
  голое имя в 12 знаков = брак

## Hero на мобиле: вшитый заголовок не выживает

> 🔴 **Дополнение по решению автора.** Hero теперь = доказательный кадр (класс `result`, для тем без
> стороннего UI - `own-run`), не сгенерированная сцена; `og:image` - тот же кадр или его плотный
> кроп на зону результата, тоже без вшитого текста. Hero едет ОДНИМ файлом, отдельный обязательный
> мобильный файл ОТМЕНЁН: вес держим под `config.image.max_kb`, а `convert.py` печатает вес в КБ и
> даёт рычаг `--quality` - сам размер он не режет и ступеней не строит. Сборщик
> `build_hero` (`build_page.py`) умеет развернуть `<picture>` с `webp_srcset` и общим `sizes`, но
> это ОПЦИЯ, а не обязанность конвейера: ступень `-720` автоматически не производит никто
> (автосборка ступеней в `convert.py` и `article_build.py` - отложенный хвост, работающей её не
> считать). Нужен srcset - кладёшь ступень рядом руками и вписываешь её в карту hero. Канал
> `og_hero.py` для новых статей закрыт ЦЕЛИКОМ - и заголовочная плашка `--variant`, и
> `--illustration` (`visual-engine.md`, «Закрытые каналы»).
> Механика ниже про вшитый заголовок - справка по легаси-обложкам: на новый кадр типографика не
> кладётся вообще

Hero-обложка 1200x630 с ВШИТЫМ в картинку заголовком на экране 390px ужимается до ~350 CSS-px:
кегль заголовка падает до ~7px, текст превращается в кашу и при этом дублирует живой H1 прямо
под собой. Путей исторически было два, законным с этой редакции остался ОДИН (второй):

1. 🔒 **Скрыть hero до 640px** (`@media (max-width: 639.98px) { .article-hero { display: none } }`) -
   ЗАКРЫТО с этой редакции, легаси-механика для уже стоящих страниц. Причина: hero отдаётся мобиле
   адаптивно самим сборщиком, прятать нечего, а `display:none` браузер всё равно качает - читатель
   платит трафиком за картинку, которой не видит
2. ✅ **Один кадр под потолком веса - действующий путь, безусловно.** В карте страницы у hero есть
   `webp` и `jpg`-фолбэк, вес держим САМИ под `config.image.max_kb`: `convert.py` печатает вес
   каждого файла в КБ и даёт рычаг `--quality`, но порога он НЕ проверяет, файл не режет и на
   превышении не падает - смотрим число глазами и переснимаем/жмём. Машинного гейта веса кадра
   в конвейере нет, это хвост ОТЛОЖЕНО. В боевом шаблоне
   единственный hero-плейсхолдер - `%%HERO_FIGURE%%` (`page-template.html`), отдельного мобильного
   плейсхолдера НЕТ. Ключ `webp_srcset` сборщик читает, если ступень положена рядом и вписана в
   карту hero - опция под ручную ступень, не шаг конвейера. Кроп плотной зоны кадра -
   ОПЦИОНАЛЬНЫЙ инструмент `shot.py --mobile-crop X,Y,W,H` (+ `--mobile-width`, по умолчанию 720):
   он нужен под og 1200×630 и под узкие колонки, обязательным шагом конвейера не является.
   Оговорка «ставим hero, только если он несёт смысл, которого нет в тексте» снята: у
   доказательного кадра такой смысл есть ВСЕГДА (ось A2, `visual-engine.md`)

🔴 Следствие: **на кадр типографика не кладётся вообще** - вшитый заголовок дублирует живой H1,
на мобиле нечитаем, а надпись-картинку закон по решению автора запрещает прямо (`og` = тот же кадр или
его кроп, без текста). САМ кадр обязан нести то, чего в тексте рядом нет: вид экрана,
взаимное расположение элементов, готовый выход функции (ось A2, `visual-engine.md`). Проверка
обязательна скрином 390x844, а не «на глаз в десктопе»

## Как это ложится в конвейер

1. **Этап 2 (раскладка):** в blueprint у каждого блока помечен его визуал по таблице выше -
   план картинок рождается вместе со структурой
2. **Этап 3 (контент):** снять кадры сценарием `shot.py` - hero-кейс-превью (`result`, для тем
   без стороннего UI `own-run`) ОБЯЗАТЕЛЕН на каждую статью, шаги тела снимаются там, где мы
   реально ведём читателя по клику. Записать `shots-manifest.json` рядом со страницей, в
   `$WORK/<slug>/` (🔴 не в `assets/`: этот каталог уезжает на публикацию целиком, служебному
   файлу там не место), зарегистрировать hero и og в `uniq.py` (раздел про
   очередь выше), собрать `.vizblock` там, где кадра нет, вставить сниппеты в тело. Реальный
   прогон команды нужен только под кадр, где вывод физически виден
3. **Приёмка:** прогнать `checklists/visual.md` плюс машинные гейты стадии `page` по статье
   (`python3 article_gates.py <slug> --stage page`; среди них `frame-provenance` - сверка каждого
   кадра с манифестом, актуальный перечень гейтов стадии - `python3 article_gates.py --list`).
   Без зелёного визуального гейта статья не уходит в публикацию

## 🔴 Служебные комментарии не уезжают в прод

Шаблон и черновики намеренно нашпигованы пометками для сборщика: «🔴 ШАПКА - КАНОН.
Пять строк ниже копируются в страницу КАК ЕСТЬ», «only-wide (Обо мне запрещено)»,
«Один блок на 88% документа читатель просто не доживал увидеть», даты разъездов
кластера, объяснения решений. Это кухня, и в шаблоне ей место. В СОБРАННОЙ странице
её быть не должно: читатель жмёт Ctrl+U и читает наши внутренние заметки, чужие слаги
и хронику косяков.

Закон: **рабочие пометки живут в шаблоне, в собранный HTML не попадают.** Исключение
ровно одно - маркеры внешних счётчиков, которые вендор просит не трогать
(Яндекс.Метрика открывает и закрывает свой блок комментарием).

Инструмент вырезает пометки последним шагом сборки, до заливки:

```bash
python3 .business/growth/seo/article-template/strip_notes.py <собранный.html>
python3 .business/growth/seo/article-template/strip_notes.py --check <собранный.html>   # приёмка, exit 1 если грязно
```

Приёмка: `--check` возвращает 0, в файле остались только вендорские маркеры.

Почему гейт: срез по решению автора по живому проду дал 30 служебных комментариев на
одной странице, 18 / 17 / 15 на трёх соседних против 2 на эталонной. Корень - пометки копировались вместе с блоками из
`page-template.html`, отдельного шага зачистки в конвейере не было


## Класс `viz` на карточках-визуалах (тёмная тема)

Собственная карточка бренда (кремовая подложка семейства `#FAF6EF`, наш заголовок,
подпись `<домен>` из конфига проекта) получает `class="viz"`. В тёмной теме к таким картинкам
применяется `filter: brightness(.88) contrast(1.02)` - иначе кремовый прямоугольник
светит в глаза на фоне `--paper:#161311`.

Скриншоты ЧУЖИХ интерфейсов класс НЕ получают: Amnezia, claude.com, Claude Docs,
страница загрузки Git for Windows и любой другой снимок реального экрана. Там важна
достоверность цвета - человек сверяет картинку со своим экраном, приглушение врёт.

Как отличить машинно (замер подложки по рамке картинки): наша карточка тёплая,
`R - B >= 8` и `G - B >= 4` при p95 яркости >= 235; чужой интерфейс нейтрально-белый
(`[255,255,255]`, `[253,253,249]`) или холодный (`[242,243,247]`) - разница R и B около нуля.
Тёмные картинки (герои, мемы, превью-плитки, p95 < 235) класс не получают, им приглушение
не нужно.

Правило CSS живёт в `tokens.css`, раздел «Тёмная тема: приглушение кремовых карточек-визуалов».
Приёмка: в тёмной теме медиана p95 по картинкам страницы падает с ~245 до ~215-219,
скриншоты чужих интерфейсов остаются как есть
