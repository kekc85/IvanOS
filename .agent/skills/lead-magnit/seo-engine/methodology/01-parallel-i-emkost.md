# Параллельное производство и ёмкость конвейера (цель - 15 касаний в день)

> Этот файл - механика скорости. 16-этапная методология (`00-methodology-16-stages.md`) отвечает
> на вопрос ЧТО делать на каждом этапе, этот файл - КАК распараллелить те этапы, которые сегодня
> идут одним монолитным проходом, и как распределить дневную ёмкость. Законы качества он не
> ослабляет: при конфликте с `ZAKONY-SEO.md` и `SKILL.md` побеждают они.

**Откуда цифры.** Аудит скорости на двух боевых прогонах (`.business/growth/seo/_rebuild/research-wave1-2026-08-04.md`,
раздел speed): монолитный черновик текста занимает 3м45с на простой статье и 41-59 минут на
сложной, монолитная ревизия с хуманайзером - 13 минут на простой и 51 минуту на сложной. Оба
прохода пишут все 8-14 разделов за один вызов, хотя методология уже предписывает фан-аут
суб-агентов на ресёрче (Этап 4) и на QA (Этап 7). Межстатейный фан-аут при этом уже работал
по решению автора: два прогона стартовали с разницей 83 секунды и финишировали с разницей 43 миллисекунды.

**Что было доказано на том же материале про риск.** по решению автора два параллельных прогона выпустили одну
и ту же обложку на разных статьях: у обоих упал генератор, оба молча ушли в один фолбэк, и каждый
честно сверился с продом - где чужой картинки ещё не было. Отсюда закон §4: общий ресурс
захватывается в реестре в момент старта, а не сверяется с продом в момент выпуска.

## §1. Черновик по разделам: N параллельных суб-агентов + шов

Заменяет один длинный заход Этапа 6. Порядок жёсткий, шаги не сливаются.

**Шаг 1.1 - раскладка H2 в section-brief.** Оркестратор берёт `sections[]` Этапа 2 (в терминах
методологии - структуру Этапа 5) и на КАЖДЫЙ контентный H2 пишет бриф-файл
`$WORK/<slug>/briefs/<NN>-<slug-раздела>.md`. Бриф несёт ровно то, чем секционный агент
распоряжается сам, и границы, за которые он не выходит:

| Поле брифа | Что в нём |
|---|---|
| `h2` | точная формулировка заголовка раздела (агент её не меняет) |
| `words` | плановый объём раздела из таблицы Этапа 2 |
| `answers` | на какой вопрос читателя раздел отвечает первой фразой |
| `facts` | якоря из кэша куста и ресёрча: команды, пути, версии, цифры с источником |
| `visual` | какой визуал стоит в этом разделе и какие якоря обязан нести кадр |
| `links` | какие внутренние ссылки ставит именно этот раздел (из реестра §4) |
| `already_defined` | термины, которые объяснены в РАНЕЕ идущих разделах - переобъяснять запрещено |
| `forbidden` | что раздел не делает: не ставит CTA (их ровно три, архитектура Этапа 6a), не пересказывает соседний раздел, не открывает новую тему |
| `troyka` 🔴 | ТОЛЬКО у технического раздела (`knowledge/novice-standard.md`): на каждый шаг раздела три строки - куда нажать · что увидишь · что даёт. Бриф без `troyka` техническому разделу не выдаётся |
| `slovar` 🔴 | ТОЛЬКО у технического раздела: термины этого раздела с готовым переводом-метафорой одной фразой - агент берёт перевод отсюда, а не сочиняет свой |

Бриф без `facts` не выдаётся: агент без фактуры начнёт выдумывать, а это прямой запрет канона.
Технический раздел без `troyka`/`slovar` не выдаётся тем же порядком (`02-blueprint.md` §7).

**Шаг 1.2 - фан-аут.** По одному суб-агенту на бриф. Ширина окна - `tools.fanout.section_workers`
(дефолт 6): при 8-14 разделах это 2-3 волны, оркестратор остаётся оркестратором и не держит в
контексте весь текст. Каждый агент пишет ОДИН файл `$WORK/<slug>/sections/<NN>-<slug-раздела>.md`
и возвращает его как артефакт. Нет файла - раздел не написан, пересборка не стартует (тот же гейт,
что на Этапе 4: без артефактов от всех агентов следующий этап не начинается).

**Шаг 1.3 - сборка.** Оркестратор склеивает файлы строго в порядке `sections[]` в
`$WORK/<slug>/draft.md`, добавляет frontmatter (Этап 6) и блоки, которые по конструкции не
принадлежат разделу: быстрый ответ, FAQ, чек-лист-памятка, «Источники», три точки CTA.

**Шаг 1.4 - ШОВ-ПРОХОД (обязателен, один вызов по ВСЕМУ телу).** Секционный агент физически не
видит текста соседей, поэтому склейка без шва даёт предсказуемый набор дефектов. Шов чинит ровно
их:

1. повторное определение одного термина в двух разделах - остаётся первое, дальше отсылка
2. одна и та же цифра или факт в разных разделах - цифра живёт в одном месте
3. обрыв связки между разделами - переход дописывается в первой фразе следующего раздела, не нарушая её критериев (§13 IVAN-LAWS)
4. дрейф лица, времени и тона между агентами - голос один, канон `config.md → voice_profile`
5. одна и та же внутренняя ссылка больше двух раз - лишние снимаются
6. нарушение архитектуры CTA - подписка ≤1, встроенный оффер ≤2, подвал один
7. сбитая сквозная нумерация «Шаг 0, 1, 2…» после склейки

🔴 **Шов не сливается с хуманайзером и не режется на секции.** Хуманайзер работает со стилем внутри
куска, шов - со связностью между кусками; посекционный проход эти семь классов не видит по
конструкции. Отдельной машинной оси «повтор внутри статьи» в инструментах нет - шов закрывается
глазами и остаётся обязательным ручным проходом. Артефакт - `$WORK/<slug>/etap-06-seam.md`
(что склеено, что снято как повтор, где дописаны переходы).

**Что это даёт.** Время монолита (сумма всех разделов) схлопывается до времени самого медленного
раздела плюс шов. Гейт длины остаётся прежним: `wc -w` по собранному телу, вилка интента из Этапа 2.

## §2. Хуманайзер по секциям параллельно + финальный проход целиком

Заменяет монолитный Этап 8 (13-51 минута одним вызовом).

**Шаг 2.1 - посекционный фан-аут.** Вход - уже собранный и прошитый черновик, разрезанный по тем же
границам разделов. По одному суб-агенту на секцию, ширина `tools.fanout.humaniser_workers`
(дефолт 6), каждый гонит `Skill('humaniser')` по своему куску и пишет
`$WORK/<slug>/humanised/<NN>-<slug-раздела>.md`. Здесь снимается всё, что видно локально: клише,
длинные тире, точки в конце абзаца, нейро-связки, канцелярит.

**Шаг 2.2 - финальный проход целиком (обязателен).** После сборки хуманайзер идёт ЕЩЁ РАЗ по всему
телу одним вызовом. Причина - часть паттернов существует только на масштабе текста и внутри секции
невидима:

- одна и та же конструкция, повторённая в разных секциях (каждая секция по отдельности чиста)
- монотонный ритм: секции написаны разными агентами, а сходятся к одинаковой длине предложений
- одинаковые зачины разделов (шаблон серии вместо предмета статьи, §14 IVAN-LAWS)
- ярлык-метка резюме, встреченный больше одного раза на странице

**Шаг 2.3 - машинный гейт только по собранному телу.** `ai-cadence-check.py` считает плотность на
1000 слов: на секции в 250 слов эта метрика шумит и врёт в обе стороны. Поэтому baseline и recheck
Этапа 8 гоняются по `draft.md` целиком, а не по кускам. Артефакты Этапа 8 не меняются.

🔴 **Причина второго полного черновика закрывается до письма, а не после.** В прогоне по решению автора статья
прошла полный re-draft `content-first -> content-second` и это стоило 51 минуту. Правило: если гейт
уронил секцию, чинится СЕКЦИЯ и её бриф, а не переписывается вся статья. Полный второй черновик
допустим только когда провалена структура (Этап 5), то есть неверна сама раскладка.

## §3. Кэш куста: ресёрч, снимки выдачи, корпус originality - один раз на куст

**Куст** - кластер статей вокруг одного инструмента или интента (обычно 3-8 страниц). Сегодня
каждая статья куста заново делает один и тот же ресёрч официальной документации, заново снимает
одну и ту же выдачу и заново собирает корпус для проверки оригинальности.

**Папка:** `$WORK/_cache/<cluster>/`

| Файл | Что внутри | Кто пишет |
|---|---|---|
| `meta.json` | `{cluster, created, keys[], slugs[], sources:[{url, sha, fetched}]}` | первая статья куста |
| `research.md` | общая фактура куста: официальная дока и README инструмента, боли аудитории, цитаты с атрибуцией | Этап 4, агенты A и B |
| `serp-<ключ>.md` | снимок выдачи по ключу: что в топ-10, какой интент, где дыра | Этап 1/5 |
| `originality-corpus/` | черновики уже опубликованных соседей кластера - вход второго аргумента `originality-check.py` | Этап 12 после выпуска |

**Правило захвата.** Первая статья куста ГЕНЕРИРУЕТ кэш и кладёт его в общую папку. Следующие
статьи куста ЧИТАЮТ его и добирают только то, чего в нём нет, - повторный общий ресёрч запрещён.

**Инвалидация (проверяется ДО чтения, по `meta.json`):**

- `serp-*.md` - TTL `tools.cache.serp_ttl_days` (дефолт 7): выдача переставляется быстро
- `research.md` - TTL `tools.cache.research_ttl_days` (дефолт 14) плюс событие: sha источника из `meta.json` не совпал с живым - секция кэша перегенерируется
- `originality-corpus/` - событийно, не по времени: каждая выпущенная статья кластера добавляется в него сразу после верификации 200
- 🔴 **НЕ КЭШИРУЕТСЯ НИКОГДА:** цены, тарифы, лимиты, номера версий, наличие фич. Закон 11
  `ZAKONY-SEO.md` требует живой проверки на каждом касании. В кэше они могут лежать только как
  «было на дату», и в текст статьи из кэша не попадают - только из живого источника

Просроченная секция кэша перегенерируется целиком. «Почти свежее» не берётся: дрейф фактов нашёлся
на 5 страницах из 6 в волне 1 именно так.

## §4. Реестры разделяемых ресурсов при межстатейном фан-ауте

> Закон-владелец: `ZAKONY-SEO.md` §19. Этот раздел - его механика (каталог, формат строки,
> протокол пяти шагов). При конфликте формулировок прав law-файл.

**Класс дефекта.** Несколько статей выпускаются одновременно, каждая честно сверяет общий ресурс с
продом и обе получают «свободно», потому что чужой захват ещё не доехал до прода. Так вышла одна
обложка на двух статьях по решению автора. Лечится не более частой сверкой, а захватом в момент старта.

**Каталог:** `$WORK/_registry/`, по файлу на класс ресурса.

| Файл | Ресурс | Почему общий |
|---|---|---|
| `codewords.jsonl` | код-слово = `target_keyword` (одна сущность) | два прогона возьмут одно слово или один ключ - каннибализация выдачи и враньё механики бота |
| `links.jsonl` | внутренние ссылки в кластер, которые прогон СОБИРАЕТСЯ поставить | параллельные статьи проставляют ссылки по устаревшему снимку индекса гайдов |
| `assets.jsonl` | имена файлов ассетов (`<slug>-hero.webp`, `<slug>-og.jpg`) | совпадение имени = один прогон затирает картинку другого |
| обложки и сцены | реестр уже существует и НЕ дублируется: `uniq.py` + `cover-index/index.json`, канон - `knowledge/visual-layer.md` | образец, по которому сделаны остальные три |

**Формат записи - одна строка JSON (JSONL), только дописывание:**

```json
{"ts":"2026-08-05T09:14:02Z","run":"<run_id>","resource":"codeword","value":"<СЛОВО>","keyword":"<поисковый ключ>","slug":"<slug>","status":"queued"}
```

Поля: `ts` - UTC в ISO; `run` - идентификатор прогона (pid + время старта), по нему видно, чей
захват; `resource` - класс из таблицы; `value` - само значение; `slug` - статья; `status` -
состояние. Для `links` дополнительно `to` (куда ссылка), для `assets` - `path`.

**Три состояния:** `queued` - захвачено в момент старта · `published` - статья прошла верификацию
200 · `released` - прогон умер или откатился, значение снова свободно.

**Протокол (пять шагов, нарушать нельзя):**

1. **Проверка занятости - по РЕЕСТРУ, не по проду.** Читается весь файл, актуальное состояние пары
   (`resource`,`value`) = ПОСЛЕДНЯЯ по `ts` запись. Есть `queued` или `published` от другого
   `slug` - значение занято, берётся следующее. Прод в этой проверке не участвует: захвата соседа
   там ещё нет, именно этот зазор и породил дубль-обложку
2. **Захват - в момент старта прогона, ДО первой строки текста.** Не перед публикацией, не после
   черновика. С этой секунды значение видно всем параллельным прогонам
3. **Атомарность - только дописывание.** Строка пишется одним открытием файла в режиме `a` и
   короче 4 КБ, поэтому конкурирующие прогоны не режут друг друга. Перезапись общего JSON-объекта
   запрещена: два прогона, переписывающих один объект, теряют записи друг друга («последний
   победил») - у append-only строк этого класса дефекта нет
4. **Закрытие.** После верификации 200 прогон дописывает вторую строку со `status: published`.
   При откате или падении - `released`. Записи не редактируются и не удаляются, история остаётся
5. **Гейт.** Прогон без записи `queued` не имеет права начинать письмо. Статья без записи
   `published` не считается выпущенной, даже если страница на проде отвечает 200

## §5. Три пост-аудита (13/14/15) - в один проход по одному скачиванию страницы

**Было.** Этап 13 качает страницу, Этап 14 качает её же в `etap-14-prod.html`, Этап 15 качает её же
в `etap-15-prod.html`. Три скачивания одной страницы и три последовательных блока, каждый из которых
держит конвейер.

**Стало.** Один снимок прода, дальше три суб-агента параллельно по одному и тому же файлу.

```bash
SLUG="<slug>"; URL="https://<ВАШ_ДОМЕН><content_path>/$SLUG"
curl -s -D "$WORK/$SLUG/prod-headers.txt" -o "$WORK/$SLUG/prod-snapshot.html" \
     -w "HTTP=%{http_code} time=%{time_total}s size=%{size_download}\n" "$URL" \
  | tee "$WORK/$SLUG/etap-13-availability.txt"
```

Ожидаем в `etap-13-availability.txt`: HTTP 200, размер тела больше 200000 байт, время меньше 2s.

**Три параллельных суб-агента на одном `prod-snapshot.html`:**

- **A (Этап 13)** - валидация микроразметки, перелинковка, индексационные артефакты, GEO
- **B (Этап 14)** - compliance: стоп-слова, обещания результата, ложная срочность, персональные данные
- **C (Этап 15)** - `python3 tools/ai-cadence-check.py $WORK/$SLUG/prod-snapshot.html --json > $WORK/$SLUG/etap-15-audit.json`

**Отдельными сетевыми пробами остаются ровно три** - их физически нельзя взять из снимка, потому что
это другой запрос:

1. Core Web Vitals - внешний измеритель, mobile и desktop
2. реестры - `sitemap.xml`, реестр для языковых моделей, markdown-версия страницы
3. GEO-бот - тот же URL с User-Agent бота языковой модели: сервер может отдать боту другое

Эти три пробы гоняет агент A параллельно с B и C, а не отдельным блоком после них.

**Сведение.** Оркестратор ждёт три отчёта, вердикт - логическое И. Любой fail - правка через
фактический канал публикации, потом ПЕРЕКАЧАТЬ снимок и повторить всё три: правка меняет страницу,
старый снимок после неё недействителен.

**Артефакты.** Появляется `prod-snapshot.html` и `prod-headers.txt`; `etap-14-prod.html` и
`etap-15-prod.html` больше не создаются - это было одно и то же тело, скачанное трижды. Отчёты
этапов (`etap-13-*`, `etap-14-compliance-audit.md`, `etap-15-audit.json`) остаются как были.

## §6. Каденция и распределение дневной ёмкости

🔴 **Ёмкость дня - 15 КАСАНИЙ, а не 15 новых статей.**

| Тип касания | В день | Что это |
|---|---|---|
| новая статья | 3-5 | полный конвейер 16 этапов |
| ревизия существующей | 10-12 | факт-чек по закону 17, добор собственного материала, перелинковка, обновление даты по реестру content-sha |

**Почему не 15 новых подряд.** Три независимых причины:

1. Внешний стандарт: издания, которые держат объём органики, публикуют доли новой статьи в день и
   держат масштаб ревизией архива (у одного из них обновлено 91% статей). Наша прежняя цель «15
   новых» не совпадает ни с одним живым бенчмарком
2. Профиль scaled abuse: 15 новых страниц в день с одинаковым скелетом - ровно тот шаблон, который
   антиспам-классификаторы поисковиков ловят по формальным признакам
3. Экономика показов: ревизия работает по уже накопленным показам, новая статья стартует с нуля.
   При равной стоимости часа ревизия отдаёт трафик быстрее

**🔴 Гейт публикации на КАЖДОЕ касание (и новое, и ревизию):**

```bash
python3 tools/structure-check.py <работа>/index.html --own-blocks-hard
```

Ось `own-blocks` требует минимум **3 блока собственного, невыводимого из модели материала**. Порог -
`tools.structure.min_own_blocks` (дефолт 3). Засчитывается только то, что видно машинно:

- `data-own="screenshot|measure|quote|number|artifact"` на блоке (в markdown-черновике - строка
  `<!-- own:screenshot -->` над блоком) - свой скрин, свой замер, цитата владельца, число из своего
  опыта, свой артефакт
- `<blockquote cite="https://...">` - цитата с машинно читаемым источником
- абзац, где число и внешняя ссылка стоят в ОДНОМ предложении - число с inline-источником

Не засчитывается: обычная иллюстрация конвейера, таблица без источника, ссылка без числа рядом -
это модель выводит сама, доказательством собственного вклада не служит.

Рядом в том же скрипте живёт ось `first-sentence` (закон §13 `ZAKONY-SEO.md`). Она остаётся
**soft** до отдельной калибровки: на слепке корпуса ей не соответствует 73% страниц, включение
`--first-sentence-hard` сейчас уронит каждый прогон. `own-blocks` включается hard-флагом сразу -
корпусного долга по ней нет.

**Журнал каденции** `$WORK/_journal/cadence.jsonl` - одна строка на касание:

```json
{"date":"2026-08-05","slug":"<slug>","kind":"new","own_blocks":4,"own_kinds":["screenshot","measure"],"reviewed_by":"<кто смотрел глазами>","next_revision":"2026-10-04"}
```

Журнал - не отчётность, а источник очереди ревизий и доказательство собственного вклада на дату.

**Слот ревизии - 60-90 дней.** `next_revision` = дата касания плюс 60 дней для тем про быстро
меняющиеся инструменты и 90 для стабильных. Статьи с ценой или тарифом ревизуются при каждом
изменении прайса вне очереди (закон 11). Очередь дня = записи с `next_revision <= сегодня`,
сортировка по спросу из кабинета вебмастера, если данные есть, иначе по возрасту записи.

🔴 **Ревизия - это не `touch` даты.** Голая правка `lastmod` без содержательной правки текста -
антипаттерн. Ревизия обязана нести факт-чек всех чисел, команд, версий и путей по живым источникам
(закон 17) и минимум один НОВЫЙ блок собственного материала. Дату двигает реестр content-sha, а не
рука: разметочная правка дату не сдвигает, и это by design.

**Что считается касанием:** новая статья, ревизия статьи. **Не считается:** пинг индексации,
перелинковка соседей, замена одной картинки, правка шаблона.

## §7. Границы: что НЕ параллелится и не кэшируется

1. **Цена, тариф, лимит, номер версии** - только живой вызов на каждом касании, кэш и память не в счёт
2. **Захват общего ресурса** - только через реестр §4 (закон 19 `ZAKONY-SEO.md`); «сверюсь с продом перед выпуском» не работает by design
3. **Заливка в общий прод** - по одному прогону за раз, протокол мержа и CAS (закон 16 `ZAKONY-SEO.md`): база - живая страница, скачанная прямо сейчас, sha сверяется непосредственно перед заливкой
4. **Шов (§1.4) и финальный хуманайзер (§2.2)** - монолитны по конструкции: они видят то, чего секция не видит. Резать их на куски = вернуть дефект, ради которого они существуют
5. **Уведомление поисковиков** - обе ноги обязательны и последовательны после верификации 200 (закон 20 `ZAKONY-SEO.md`, механика - `00-methodology-16-stages.md`, Этап 12a): статья не считается опубликованной, пока не ушла в оба контура
