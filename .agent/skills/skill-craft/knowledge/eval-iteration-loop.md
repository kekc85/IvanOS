# Eval-iteration loop + improve-философия (поглощено из Anthropic skill-creator)

Источник: официальный Anthropic `skill-creator` (plugins/skill-creator). Поглощено в skill-craft 2026-05-31 как Режим C (eval-iteration) и Режим D (description-optimization). Закрывает дыру: 7-уровневый audit проверяет *устройство* скилла, но не доказывает эмпирически, что скилл **реально добавляет ценность** поверх baseline и **надёжно триггерится**.

---

## 1. Зачем baseline (главное отличие от L5 E2E)

L5 audit прогоняет скилл на одном троянском кейсе и смотрит, не сломался ли. Этого мало. Скилл может «работать» и при этом **не добавлять ничего** поверх голой модели — тогда он только жрёт контекст и замедляет.

**Правило:** на каждый тест-кейс запускать ДВА сабагента в ОДНОМ ходу:
- `with_skill` — модель с доступом к скиллу
- baseline:
  - **новый скилл** → `without_skill` (тот же промпт, без скилла вообще)
  - **правка существующего** → `old_skill` (снапшот ДО правок: `cp -r <skill> <ws>/skill-snapshot/`, baseline целит в снапшот)

Запускать обе ветки сразу (не сначала все with_skill, потом baseline) — чтобы закончились примерно одновременно.

Скилл оправдан только если `with_skill` ощутимо лучше baseline по качеству / pass_rate, при приемлемой добавке токенов и времени. Если дельта ≈ 0 — скилл лишний или его надо урезать.

## 2. Эмпирическая петля (Режим C)

```
draft/edit скилл
  → 2-3 РЕАЛИСТИЧНЫХ тест-промпта (как реальный юзер напишет, не «отформатируй данные»)
  → запустить with_skill + baseline сабагенты параллельно
  → пока бегут: набросать assertions (объективно проверяемые, с понятными именами)
  → grade каждого прогона по assertions (скриптом где можно, не на глаз)
  → aggregate в benchmark (pass_rate, токены, время — mean ± stddev + дельта)
  → human review через eval-viewer (qual + quant)
  → improve по фидбэку
  → повторять, пока: юзер доволен / фидбэк пуст / прогресса нет
  → расширить тест-сет, прогнать на масштабе
```

Структура воркспейса (sibling скилла, не внутри): `<skill>-workspace/iteration-N/eval-<descriptive-name>/{with_skill,without_skill|old_skill}/outputs/`. Каждому evalʼу — описательное имя, не «eval-0». Тайминг (`total_tokens`, `duration_ms`) ловить из notification сабагента СРАЗУ в `timing.json` — больше негде взять.

**Готовые скрипты** (в `scripts/`, запускать из корня skill-craft, `python -m scripts.<name>`):
- `aggregate_benchmark.py <ws>/iteration-N --skill-name <name>` → `benchmark.json` + `benchmark.md`
- `eval-viewer/generate_review.py <ws>/iteration-N --skill-name <name> --benchmark <…>.json` (для итерации 2+ добавить `--previous-workspace`). В headless/cowork: `--static <out.html>`.
- `quick_validate.py` — быстрая структурная проверка.

**Agent-промпты** (в `agents/`):
- `grader.md` — как оценивать assertions против outputs (поля grading.json строго `text`/`passed`/`evidence`).
- `analyzer.md` — анализ benchmark: какие assertions всегда проходят (недискриминирующие), какие evalʼы flaky (высокий разброс), trade-off время/токены.
- `comparator.md` — слепое A/B двух версий (опц., для «новая версия реально лучше?»).

Схемы JSON — `references/schemas.md`. HTML-форма ревью триггеров — `references/eval_review.html`.

## 3. Improve-философия (4 принципа — поглощено дословно по смыслу)

Это самое ценное и частично **переопределяет** MUST-heavy стиль старого skill-craft.

1. **Генерализуй, не оверфить.** Скилл создаётся для миллиона разных промптов; на 2-3 примерах ты только итерируешь быстро. Не зашивай фиддли-правки под конкретный пример и не лепи душащие MUST. Упёрся в проблему — попробуй другую метафору / другой паттерн работы, это дёшево.

2. **Держи промпт lean.** Убирай то, что не тянет свой вес. Читай ТРАНСКРИПТЫ прогонов, не только финальные outputs — если скилл заставляет модель тратить ходы на бесполезное, выкинь эту часть и проверь.

3. **Объясняй ЗАЧЕМ, а не дави MUST/ALLCAPS.** Сегодняшние модели умные, у них хорошая theory of mind. Если ловишь себя на `ALWAYS`/`NEVER` капсом или жёстких структурах — это жёлтый флаг: переформулируй и объясни причину, чтобы модель понимала, почему это важно. Так гуманнее, мощнее и эффективнее. (Этот принцип сознательно мягче, чем исторический «MUST-heavy» стиль skill-craft — при конфликте побеждает «explain why».)

4. **Замечай повторную работу между прогонами.** Если в транскриптах все сабагенты независимо писали похожий хелпер (`create_docx.py`, `build_chart.py`) — это сигнал вынести скрипт в `scripts/` один раз и сослаться. Экономит каждый будущий вызов.

## 4. Description optimization (Режим D) — против undertriggering

Description во frontmatter — **главный** механизм, решает, вызовет ли Claude скилл. Текущая болячка моделей — **undertriggering** (не зовут скилл, когда он полезен). Лечение:

- Делать description слегка «pushy»: не «Как строить дашборд», а «…используй этот скилл всякий раз, когда юзер упоминает дашборды / визуализацию данных / метрики, даже если слово ‘дашборд’ не прозвучало».
- **Механика триггеринга:** Claude зовёт скилл только для НЕтривиальных задач. Простой «прочитай этот PDF» может не триггернуть, даже если description идеально совпал — модель сделает сама. Значит тест-запросы должны быть достаточно содержательными, чтобы скилл реально был нужен.

**Петля оптимизации:**
1. 20 trigger-эвалов: 8-10 should-trigger (разные формулировки одного интента, casual/formal, без явного имени скилла) + 8-10 should-NOT-trigger (**near-miss**: делят ключевые слова, но нужен другой инструмент — это самые ценные; не делать очевидно-нерелевантные вроде «напиши fibonacci»). Запросы конкретные, с деталями (пути файлов, имена компаний, контекст), иногда с опечатками/lowercase.
2. Ревью с юзером через `references/eval_review.html` (плейсхолдеры `__EVAL_DATA_PLACEHOLDER__` / `__SKILL_NAME_PLACEHOLDER__` / `__SKILL_DESCRIPTION_PLACEHOLDER__`).
3. `python -m scripts.run_loop --eval-set <…>.json --skill-path <skill> --model <model-id> --max-iterations 5 --verbose` (в фоне). Делит 60/40 train/test, гоняет каждый запрос 3× для надёжного trigger-rate, итеративно улучшает description, выбирает `best_description` по **held-out test** (защита от оверфита).
4. Применить `best_description` во frontmatter, показать юзеру before/after + скоры.

## 5. Когда что применять

- **Объективно проверяемый output** (трансформации файлов, извлечение данных, генерация кода, фикс-воркфлоу) → нужны assertions + benchmark + baseline (Режим C полностью).
- **Субъективный output** (стиль письма, дизайн) → не насиловать assertions, оценивать качественно через human review; benchmark пропустить, оставить baseline-сравнение глазами.
- **Любой скилл после build/правки** → предложить Режим D (description optimization).
- **Claude.ai / нет сабагентов** → петля та же (draft→test→review→improve), но прогон один-за-другим самим, без параллельных baseline, без quant-benchmark; упор на human review.
