# Workflow 01 - Router (Mode detection + Lane Selection)

**Назначение:** определить mode работы (Plan / Spark / Transcript), genre поста и lane обработки (fast / co-creation), затем передать управление соответствующему workflow-файлу.
**Входы:** raw user input + `config.md`
**Выходы:**
- `brief.mode = "plan" | "spark-b1" | "spark-b2" | "transcript"`
- `outline.genre = "<one of 10>"`
- `outline.pipeline = "deep"` (всегда; lane-оси нет, v4.2)
- переход в следующий workflow
**Следующая стадия:** один из `01a-plan.md` | `01b-spark.md` | `01c-transcript.md` → затем `01-finalize.md` → единый глубокий конвейер (02b→02c→02d→02e→02f→**03-dry**→04-review→05-publish)

**Версия:** v2.2 (2026-05-28) - добавлены Шаг 0.6 (Lane Selection) и Шаг 0.7 (Pipeline Routing) для Architecture C Hybrid (fast vs co-creation lanes).

## Шаг 0.3 - 🔴 ТЗ ВЛАДЕЛЬЦА = СПИСОК ПРИЁМКИ (HARD, NEW по решению автора, разнос «полностью проигнорировал ТЗ»)

**Зачем.** Прецедент в даты запуска.2026: владелец дал ТЗ («новость-инфоповод → раскрыть → как получить → что успеть завайбкодить за неделю → лёгкий fear of missing out»), конвейер прогнал ВСЕ внутренние гейты (форма, голос, доноры, линтер) и выдал пост, где заказанные пункты потерялись: новость ушла из заголовка, FOMO выпал, сцена уехала в нерелевантный июль. Вердикт владельца: «0 из 10, полностью проигнорировал ТЗ». Внутренние гейты оптимизируют КАК написано, и ни один не проверял ЧТО заказано.

**Правило.** Если постановка пришла от владельца текстом (а не «/post» без аргументов по карте), ПЕРВЫМ действием после чтения config:

2. Записать список в `brief.tz_ivana` (state). Пришли ДОПОЛНЕНИЯ владельца по ходу сессии → дописывать в тот же список с пометкой времени, не затирая прежние пункты.
3. Этот список - ГЛАВНЫЙ критерий приёмки поста, ВЫШЕ внутренних гейтов формы: конфликт «пункт ТЗ против внутреннего правила» решается в пользу ТЗ с печатью строки `конфликт: <пункт ТЗ> vs <правило> -> взял ТЗ` (иерархия §8.1 уровень 2 «прямое указание владельца в сессии»). ### 0.49-E - Класс `event` (событийный пост, канон правок п.17, введён по решению автора)

🔴 **Зачем третий класс.** Эталон владельца 6.08 - анонс эфира, где доля «одного прикладного скилла» заведомо ниже 80%, и это НЕ брак. До этой редакции таких постов в классификаторе не было: они писались как `sales`, ловили порог доли скилла, и либо валились гейтом, либо обходили его через `launch_window` - то есть класс работал рубильником. Теперь классы разведены по МЕРИЛУ, а не по строгости:

| класс | чем мерится качество | чем НЕ мерится |
|---|---|---|
| `razbor` / прикладной `sales` | доля скилла (≥80% / ≥50%), причинная цепь ≥5/≥4 звеньев | - |
| **`event`** | **плотность идей: минимум одна цифра, имя или личный факт на каждые 3 предложения** (канон п.19) + конкретика ИМЕННО этого события (п.74) | долей скилла - требовать её от событийного поста ЗАПРЕЩЕНО |
| `narrative` | близость, живая сцена | долей скилла |

**Признаки класса `event` (достаточно любых двух):** в посте названы дата или время события · пост входит в каскад доходимости (слоты 9:00 / за 4 часа / за час / T-15 / момент старта / после старта) · единственное действие читателя - регистрация или явка на конкретное событие · тело поста отвечает на вопрос «что будет на ЭТОМ эфире», а не «как работает инструмент».

**Длины (канон п.45, свод 6.08):** касание каскада ≥700 знаков полноформатом смысла · событийный пост и финальный пуш (T-15, момент старта) ≥500 знаков. Верхнего потолка нет ни у того, ни у другого - длину ограничивает тест удаления абзаца, не счётчик.

**Числовой профиль для линтера (переписано по решению автора, дефект Д8).** 🔴 ПОДМЕНА КЛАССА ОТМЕНЕНА. До этой редакции здесь стояло «линтер знает четыре класса, пятого у него нет», и в `--form-class` уходило слово `sales` со строкой соответствия. Это и был дефект Д8 (скептик-раунд 3, находка 8): класс существовал только на бумаге, событийный пост мерился порогами продажи, а суть класса (плотность и конкретика события) держалась одним текстом ревью. Теперь `scripts/lint-post.py` знает ПЯТЬ классов и `--form-class event` принимает наравне с остальными:

```
--form-goal <sales|forwards> --form-class event
```

Что линтер теперь проверяет САМ при `--form-class event`:
- **4.DENS** машинно: `density = S/D` против порога `3.0`, HARD (строка `[PASS|FAIL] 4.DENS плотность идей: S=.. D=.. density=.. порог=3.0 (класс event)`). Носители считаются прокси - цифры, имена собственные, латиница-названия, цитаты в «ёлочках», срок словами, физический артефакт; служебная launch-строка (👉-CTA, адрес двери, счётчик мест, дедлайн) из знаменателя вынесена, канон п.18;
- **дата или время события в теле** - признак класса выше, HARD;
- профиль формы `E-событие`: длина ограничена только абсолютным полом 500 знаков (канон п.45, верхнего потолка нет), нумерованный список разрешён, цифра в хуке желательна.

Полную оценку 4.DENS по всем пяти видам носителя (включая «имя с представлением» и «личный факт от первого лица») по-прежнему даёт верификатор 4.M.2 - машина считает прокси и ошибается в сторону PASS. Что остаётся текстом `04-review.md`: 4.ET, W15-цепь, 4.R, Checklist A-F, 4.M.2.

## Шаг 1 - Mode detection (auto-detect по сигналам)

Проверять сигналы **в строгом порядке** (первый сработавший - побеждает):

### Mode D - Rewrite (улучшить ГОТОВЫЙ пост) — NEW v4.1, проверять ПЕРВЫМ

**Признаки (нужны ОБА — текст поста + интент улучшить):**
- User приложил/вставил **уже готовый пост** (связный текст, похожий на финальный, не сырые мысли)
- И интент-слова: «улучши», «перепиши», «докрути», «сделай лучше», «причеши», «усиль», «поправь этот пост», «что не так с постом», «rewrite», «improve this post», «punch up»

**Важно — отличие от Mode C (Transcript):** Transcript = сырые надиктованные мысли → НОВЫЙ пост. Rewrite = ГОТОВЫЙ пост → улучшенная версия с сохранением голоса. Если текст длинный, но это надиктовка/мысли — Mode C. Если это оформленный пост, который просят докрутить — Mode D.

→ `brief.mode = "rewrite"`, перейти в `01d-rewrite.md`. (Поглощено из HubSpot Mode B «Rewrite», v4.1. Платформа определяется как обычно — Шаг 0.4; работает для TG и LinkedIn.)

### Mode C - Transcript (длинный неструктурированный вход)

**Признаки:**
- Длина user-input > 500 символов
- ИЛИ содержит фразы: «надиктовал», «надиктовка», «мои мысли», «вот текст», «расшифровка», «вот что я думаю», «послушай, я сейчас расскажу»
- ИЛИ пользователь приложил файл с длинным текстом / аудио-транскриптом

→ `brief.mode = "transcript"`, перейти в `01c-transcript.md`.

### Mode A - Plan (из Карты смыслов на дату)

**Признаки:**
- User написал `/post` БЕЗ аргументов
- ИЛИ содержит фразы: «по плану», «по карте», «смысл дня», «сегодняшний смысл», «что в плане на сегодня»
- ИЛИ упомянута дата («на 28 мая», «завтра», «послезавтра»)

**Дополнительная проверка:**
- Прочитать `paths.content_map` (с подстановкой `<active-launch>` из config).
- Если файл существует И содержит запись на нужную дату → `brief.mode = "plan"`, перейти в `01a-plan.md`.
- Если файла нет ИЛИ нет записи на дату → fallback на Mode B2 (Spark - generate ideas), сообщить пользователю: «Карты смыслов на эту дату не нашёл, перехожу в режим генерации идей под JTBD».

### Mode B1 - Spark с идеей (расширение конкретной темы)

**Признаки:**
- User дал конкретную тему: «напиши про X», «/post про вайбкодинг», «пост о Cursor», «сделай хук про N8N»
- Короткая фраза (10-200 символов) с явным предметом

→ `brief.mode = "spark-b1"`, перейти в `01b-spark.md` (sub-flow B1).

### Mode B2 - Spark без идеи (генерация идей под JTBD)

**Признаки:**
- User написал: «дай идеи», «что писать сегодня», «предложи темы», «варианты постов»
- ИЛИ Mode A зафиктвал fall-back

→ `brief.mode = "spark-b2"`, перейти в `01b-spark.md` (sub-flow B2).

## Принципы router

1. **Тихий detect.** Не задавать вопросы пользователю на этапе detection - определять по сигналам. Уточнения возможны только внутри выбранного mode-файла.
2. **Fallback цепочка.** Mode A без карты → Mode B2 (не блокируем работу).
3. **Override > auto.** Явный флаг пользователя всегда побеждает.
4. **Один mode за запуск.** Не смешивать modes в одном run скилла.
