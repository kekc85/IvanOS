## Sub-stage 4.0 - Mandatory Lint + Gate Evidence Report (HARD, BLOCKING)

> Прецедент по решению автора: заявлено «3 слоя пройдено» без реального прогона. Фикс: до output обязательны (1) прогон линтера, (2) Gate Evidence Report с цитатами/счётчиками. Декларация без улики запрещена.

### 4.0.1 - Повторный прогон линтера

`draft.dry` уже прошёл `lint-post.py` в `03-dry.md` Шаг 3.5 (exit 0 обязателен на входе сюда - если `draft.dry.meta.lint_exit != 0`, это брак маршрута, вернуть в `03-dry.md`). Здесь линтер прогоняется ЕЩЁ РАЗ как независимая проверка (сюда мог прийти текст без факта прохода 03-dry):

```bash
python3 ~/.claude/skills/post/scripts/lint-post.py <tmp-file> \
  --form-goal <brief.form_goal> --form-class <brief.form_class: narrative|razbor|sales|event|gate> \
  --channel <brief.channel> \
  --budget <brief.budget> --factbase <путь факт-базы> \
  --anchor "<state.anchor>" --hero "<state.hero>"
```

🔴 `--anchor`/`--hero` берутся из ключей state `anchor` и `hero`, записанных фазой `02d-components-options.md` (Шаг «Якорь и герой в state»). Без них дубль-гейт журнала якорей (класс R2-8, «герой не повторяется два дня ни в каком канале») здесь молчит и ловится только в 05-publish - то есть на шаг позже, когда пост уже собран. Ключей в state нет → вернуться в 02d и записать их, а не выдумывать значения тут. Тот же прогон делает своими руками хук `post-phase-gate.sh` (архитектура доверия v3): он читает те же ключи из state, поэтому расхождение между вызовом здесь и вызовом хука означает, что state не соответствует посту.

`--channel <brief.channel>` (канал выдачи, в Mode A он же носитель `brief.carrier`; не задан - `osn`) обязателен - по нему линтер проверяет UTM / PS-ACTION / поддержку-в-бот-цепочке; без флага всё считается по дефолту `osn` (основной TG) и пост другого канала проверяется чужими правилами. `--budget` берётся из `brief.budget` (единое имя ключа, записан в `01-router.md` Шаг 0.49 и равен `form_profile.length_target`).

Единый словарь цели - слово из `reactions|forwards|sales|gate` (`brief.form_goal`), буква только в `brief.form_goal_letter` для печати улики, сравнивать по ней запрещено. `brief.form_goal` пуст → ветка B (`--max/--min` из `01-finalize.md` таблицы типов, HARD-пороги старого типа) - это не рабочий режим, см. 4.0.2b.

Линтер детерминированно проверяет: точки в конце абзаца (4.1.6.5), em-dash (4.1.1), длину (4.1.6, WARN при объявленной цели), `!` (4.1.4), списки (4.1.5), скелет-гейт (см. ниже), профильные жирный/блоки/ссылки/нумерацию/медиану/цифру-в-хуке (§9 канона). Полный список проверяемого - в самом `lint-post.py` (Z1), здесь только вызов и разбор кода возврата.

🔴 **Скелет-гейт (v4.5, прецедент по решению автора: два поста подряд одним каркасом).** Каждый вызов извлекает скелет блоков (HB/IT/P/LIST/NUMLIST/QUOTE/CTA) и сверяет с `.skeleton-log.jsonl` канала за последние 5 постов. Совпадение или общий зачин из 3+ блоков → FAIL, перестроить порядок ВТОРОГО блока и далее (заголовок закреплён отдельным правилом ниже). Обход только `--allow-skeleton-repeat "<причина, что автор явно просил>"`.

🔴 **Правила владельца (машинные, каждый вызов):**
- Хук-эмодзи HARD: первая строка = эмодзи в тему + жирный заголовок целиком; если у тебя настроен свой канал доставки, премиум-версия подставляется автоматически при отправке (05-publish п.1d, деградация там же - скрипта нет, оставляй обычный эмодзи). Обход `--allow-no-premium-hook "<причина>"`.
- Два жирных абзаца подряд - HARD FAIL всегда.
- Эмоциональная палитра (капс-слово, растянутые гласные) - INFO, не квота: применять по смыслу, не шаблонить.
- 🔴 **Rich-разметка запрещена (правка владельца).** Таблицы `|...|`, чек-боксы ☐/✅ списком, заголовки `#`/`##`/`###` внутри тела, `__подчёркнутое__`, `||спойлер||` → HARD FAIL `check_no_rich_entities`. Формат выдачи = донорский, других сущностей у поста нет.

- exit 1 (FAIL) → **STOP**, вернуться в `03-dry.md`, починить, перегнать. Output запрещён.
- exit 0 (PASS) → вставить вывод линтера verbatim как доказательство.

### 4.DRY - Осушение честное (HARD, компактный)

🔴 **Зачем.** `03-dry.md` может отработать вхолостую: фаза отмечена пройденной, `dry_report` в state есть, а в нём «снято 0» - при том что линтер прямо здесь показывает воду выше потолка или длину выше бюджета. Ровно так пост с водой доезжал до выдачи: осушение формально было, фактически не случилось, и никакой гейт этого не ловил.

**Вход:** вывод `lint-post.py` из 4.0.1 (строки «вода суммарно» и «бюджет длины») + `dry_report` из state.

**Правило (одна строка):**

> Линтер отдал `вода суммарно > 3.0/1000` (HARD-потолок) **ИЛИ** `вода суммарно > 2.5` (потолок-цель) **ИЛИ** `длина > brief.budget`, а `dry_report` показывает «снято 0» (ни знаков, ни водянистых оборотов) → **FAIL**, возврат в `03-dry.md` Шаг 2. Осушение обязано либо снять, либо честно назвать, что снимать было нечего, - и тогда цифры линтера обязаны быть в норме. «Вода есть и снято ноль» одновременно - невозможное состояние, это невыполненная фаза.

**Не-FAIL случаи:** вода/длина в норме при «снято 0» (сжимать было нечего - легально); вода выше цели, но `dry_report` показывает реально снятое (осушение работало, остаток объясняется одной строкой в отчёте и уходит в WARN).

### 4.0.2 - Gate Evidence Report

Перед output заполнить отчёт РЕАЛЬНЫМИ уликами (цитаты/счётчики из текста), не словом «PASS»:

```
GATE EVIDENCE REPORT
- 4.1.6.5 точки в конце абзаца: <вывод линтера N/M>
- 4.6.3 форматирование: emoji-маркеры <список> + brail-spacer <есть/нет + 4.7.4.5>
- 4.SUB метафоры: <каждый выразительный оборот + вердикт легально/подмена>
- hook: <первая строка + счёт слов>
- форма: цель=<reactions/forwards/sales/gate> (<буква>) класс=<...> слаг=<file_slug> тема=<...> -> длина <N в профиле min-max>, жирный <N (покрытие)>, перечислений <N>, ссылок <N>, цифра в хуке <да/нет>
- конфликты формы: <«конфликт: <пункт канона> vs <правило уровня N> -> взял уровень N» + дословная цитата> | нет конфликтов
- mandatory_reads.donor_devices: <true (прочитан самой единицей, фаза <02d Шаг 0.6 | 01d Шаг 2.5 | E1>) | packet:<packet_id> (прочитан один раз на пакет, только при route: packet) | FAIL (не прочитан)>
- mandatory_reads.formatting_skeleton: <true (прочитан самой единицей, фаза <02f Шаг 4 | 01d Шаг 3.4>) | packet:<packet_id> (прочитан один раз на пакет, только при route: packet) | N/A (short-event, справочник не читается) | FAIL (не прочитан)>
```

Пункт без улики = не пройден. Любой HARD-гейт без улики/с FAIL → output запрещён.

🔴 **Пункт `mandatory_reads.donor_devices` обязателен (NEW по решению автора, дефект Д3 скептик-раунда 1).** Ключ ставят три точки маршрута ДО ревью: `02d-components-options.md` Шаг 0.6 (полный маршрут), `01d-rewrite.md` Шаг 2.5 (rewrite), фаза E1 короткого событийного маршрута - это ТРИ из ЧЕТЫРЁХ точек HARD Read справочника, полный список - `knowledge/workflow-overview.md`. Четвёртая точка - Read самим верификатором прямо здесь, в 4.M.2 (файл вкладывается в промпт целиком, на ВСЕХ маршрутах); её след - не `mandatory_reads.donor_devices`, а отдельная строка реестра `donordev_read` (см. `review_verdict` ниже). До этой правки ключ никем не проверялся - справочник приёмов можно было не открыть, и единственным следом остался бы `donor-devices: нет` у верификатора, который сам был легален. «Не отметил, но читал» уликой не является: ключ и есть улика.

🔴 **Легальные значения ключа - ровно два, третьего нет (уточнено, дефект Д16 скептик-раунда 3).**
> - `true` - справочник прочитала САМА единица. Штатно при `brief.route` = `full` / `rewrite` / `short-event`.
> - `packet:<packet_id>` - справочник прочитан ОДИН РАЗ НА ПАКЕТ и переиспользован. Легально ТОЛЬКО при `brief.route: packet`, и `<packet_id>` обязан посимвольно совпасть с `packet_id` в корне `.post-state-по решению автора-<file_slug>.json` этой единицы (канон значений - `_phases-state.md`, раздел «Как ссылается единица»). Чужой или пустой id = FAIL: ссылка на пакет, которого у единицы нет, ничего не доказывает.
>
> Любое другое значение (`false`, пусто, «читал», отсутствие строки) → **HARD FAIL**, возврат в свою фазу на чтение `references/donor-copy-devices.md`.
>
> До этой правки здесь стояло «значение не `true` → HARD FAIL», и пакетный маршрут ломался о собственный канон: `_phases-state.md` велит писать `packet:<id>` вместо `true`, а `true` при `route: packet` считает сигналом продублированного чтения - то есть штатно исполненный пакет получал HARD FAIL, а исправление этого FAIL требовало напечатать ровно тот признак брака, от которого пакет и уходит.

🔴 **Пункт `mandatory_reads.formatting_skeleton` обязателен (NEW по решению автора, дефект Д4 скептик-раунда 2).** Ключ пишут `02f-polish.md` Шаг 4 (full) и `01d-rewrite.md` Шаг 3.4 (rewrite) при чтении `references/formatting-skeleton.md` - справочник раздаётся вместе со скиллом, поэтому его отсутствие не штатная деградация, а поломка пакета. До этой правки ключ писался, но не проверялся никем: справочник можно было не открыть, и ни один гейт этого не заметил бы - тот же класс дефекта, что был у `donor_devices` до этой редакции.
> - `true` - справочник прочитала САМА единица. Штатно при `brief.route` = `full` / `rewrite`.
> - `packet:<packet_id>` - прочитан один раз на пакет и переиспользован, легально ТОЛЬКО при `brief.route: packet`; `<packet_id>` обязан посимвольно совпасть с `packet_id` state этой единицы (`packet_state.reads.formatting_skeleton`, `01-router.md` Шаг 0.7-П).

### 4.1.7 → 4.SUB - Метафоры и несуществующие словосочетания (HARD, независимый верификатор)

## Sub-stage 4.DENS - Плотность идей (НОВЫЙ по решению автора, HARD, ВСЕ классы)

> Канон правок п.19 (устная правка владельца 6.08: «в каждом посте **90%** вырезать») + эталон 6.08 п.2: «Цифры и личные факты в каждом третьем предложении ($20 · MAX · 2 подписки · ночь · неделя · миллион · сотни слов/лидов). **Как мерить (детерминированно, руками по тексту).**

1. Посчитать предложения `S`. Граница предложения - точка, `?`, `!` **и перенос строки** (память `feedback_rhythm_in_words_is_generator_marker`: абзац-такт в одну строку без точки - это отдельное предложение, иначе счёт врёт в свою пользу)
2. Посчитать носители плотности `D` - засчитывается **только конкретика**: число (сумма, срок, количество, время) · имя человека с представлением · название конкретного продукта/платформы/тарифа · физический артефакт (файл, страница, скрин) · личный факт автора от первого лица («оставляю компьютер включённым на ночь»)
3. НЕ засчитывается: оценка («мощный», «быстро»), обобщение («много лидов», «за короткое время»), абстрактное существительное-образ, повтор уже посчитанного носителя в том же абзаце, число внутри служебной launch-строки (счётчик мест, дедлайн - они не несут идею, канон п.18)

Все союзные и перечислительные | (1) в одном предложении есть и союз `и`, и союз `а` · (2) противопоставление `не ... а ...` / `это не X, это Y` / `дело не в A, дело в B` · (3) перечисление из **3+ однородных частей** (считать по разделителям одного ряда: запятая, `и`, тире-двоеточие со списком следом) |

## Sub-stage 4.V - Прикладная ценность (НОВЫЙ, HARD для прикладных классов, независимый верификатор)

Раньше исключение работало только при `launch_window=true`, и обязательные по канону элементы («в КАЖДОМ посте ЗАКР: сколько мест осталось + когда закроются заявки») механически ломали порог 80% у прикладного поста.
