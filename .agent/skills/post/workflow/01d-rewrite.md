# Workflow 01d - Rewrite (улучшить готовый пост) — NEW v4.1

**Назначение:** взять УЖЕ ГОТОВЫЙ пост (свой черновик / старый пост / чужой как референс по структуре) и выдать улучшенную версию **с сохранением голоса автора**, не превращая его в другого человека.
**Вход:** `brief.mode == "rewrite"` (router Mode D) + текст поста от пользователя.
**Выход:** улучшенный пост → дальше в общий конвейер `04-review` → `05-publish`.

> Поглощено из HubSpot `linkedin-post-generator` Mode B «Rewrite». Универсально: TG и LinkedIn (платформа из router Шаг 0.4). Голос/канон — по внешним путям `config.voice_canon` (читать условно через `[ -f ]`), не по generic-LinkedIn и не по пустому шаблону `references/_voice-TEMPLATE.md`.

## Шаг 1 - Diagnose first (диагностика ДО правок)

Прочитать пост пользователя. Назвать вслух (в internals, не выдумывать):
- **Что работает** (НЕ выбрасывать это): сильный заход / живая деталь / голос / факт.
- **Что слабо** (типовое): мягкий заголовок / закопанный главный смысл (lede в 3-м абзаце) / канцелярит / нет receipts / слабый или отсутствующий CTA / стена текста.
- 🔴 **Два пункта диагностики ОБЯЗАТЕЛЬНЫ и считаются, а не оцениваются** (по решению автора, дефекты «метафора» и «жидкий текст»):
  1. **Образы.** Выписать каждое место, где стоит образ ВМЕСТО названной вещи (корни `check_metaphor_roots`: дверь · ступень · лестница · путь · карта · дыра · мостик · фундамент · арка · «в ноль»). Каждое такое место идёт в `weak` **дословной цитатой**, не формулировкой «многовато образности»
  2. **Плотность по абзацам.** По каждому абзацу строка `P<i>: S=<предложений> К=<носителей конкретики> норма=ceil(S/3) мин.1`. Носители и «не носители» - `03-dry.md` Шаг 3.1. Каждый абзац с `К=0` идёт в `weak` с номером

**Записать:** `rewrite_diagnosis = {keep: [...], weak: [...], metaphors: [<цитаты>], density: [<строки P1..Pn>]}`.

## Шаг 3 - Улучшить по 5 рычагам (из диагностики)

1. **Заголовок/заход** — если слабый, усилить по формулам заголовков из `config.voice_canon.voice_gold_standard` (секция `## 10 топ-постов`, поля `Первая строка (ВЕРБАТИМ)`/`Hook type`). Главный смысл — в первую-вторую строку, не закапывать.
2. **Receipts/Evidence** — если нет реального пруфа (число/результат/срок), добавить ИЗ материала пользователя. Нет реального → **спросить пользователя** (context-gap gate), НЕ выдумывать.
3. **Структура/читаемость** — разбить стену текста; нелинейная динамика с твистами (КАНОН раздел 4), не «пришёл-увидел-победил».
4. **Ценность** — заострить микро-пользу на 24ч (КАНОН раздел 5), если размыта. 🔴 Заострять фактом (что именно человек сделает, с чем, за сколько), а не образом: «увидишь всю картину» / «первая ступень» / «дверь к результату» - это размытость, переодетая в красивое, а не заострение.
5. **Финал/CTA** — заменить слабый/«Thoughts?»/«пишите в комменты» на 1 вопрос с псих-триггером ИЛИ тизер (КАНОН раздел 6).

**Записать:** `final_post = <улучшенный текст>`.

**3.3.2 - Поабзацный прогон.** По каждому абзацу вердикт из `03-dry.md` Шаг 3.1: `ДЕРЖИТ | ПЕРЕПИСАТЬ | СНЕСТИ | СЛИТЬ`. **Улика в `rewrite_diagnosis` (обязательна):**

```
буквальность: образов <n> → заменено <n> (<«было» → «стало»> по каждому)
поабзацно: абзацев <n> → держат <a>, переписаны <b>, снесены <c> | S/К=<X.X> (норма ≤3.0)
связность: проверено <N> предложений (союзных <a> + длинных <b> + обобщённых <c>) → держат <d>, переписаны <e>, разрезаны <f> | худшее: «<цитата>» (<ось названа | ось НЕ названа: причина>)
```

🔴 Строка `связность:` обязательна так же, как две над ней: гейт `4.СВЯЗ` в `04-review` ищет её первым делом и без неё ставит FAIL по маршруту, а не по тексту (см. 3.3.2-ter ниже).

## Шаг 3.5 - Анти-шаблон: скелет против последних выданных постов (v4.5, прецедент по решению автора)

Rewrite обязан пройти ротацию скелета так же, как генерация. Прецедент: два переписанных поста подряд вышли в одном каркасе «жирный хук → курсивная вторая строка → жирные подзаголовки → тире-список», владелец поймал шаблонность. Линтер это не ловит (он считает числа, не порядок), профиль цели это не оправдывает (канон §4.2: одну и ту же метрику выполняют десятком построений).

Сравнение делает МАШИНА, не глаза: `lint-post.py` в каждом вызове извлекает скелет (порядок блоков HB/IT/P/LIST/NUMLIST/QUOTE/CTA) и сверяет с журналом последних 5 выдач канала `.skeleton-log.jsonl`. Идентичный скелет или общий зачин 3+ блоков = FAIL линтера (см. 04-review «СКЕЛЕТ-ГЕЙТ»). Задача этого шага - не дотянуть до FAIL, а спроектировать другой скелет ДО написания:

1. Прочитать хвост журнала: `tail -5 ~/.claude/skills/post/.skeleton-log.jsonl` - какие скелеты уже выданы в канал.
2. Выбрать другой порядок блоков ПОСЛЕ заголовка (первая строка закреплена правилом владельца: эмодзи + пробел + жирный заголовок, вариативность начинается со второго блока). Варианты слома: вторым блоком сцена / прямая речь / цитата вместо курсив-строки; список распустить в абзацы или наоборот; сместить список вглубь поста; подзаголовки убрать, дать сплошной нарратив с одним акцентом; курсивную вторую строку заменить частностью обычным текстом (канон §4.2: решает содержимое, не курсив).
3. После выдачи - записать скелет в журнал (`--log-skeleton <slug>`, см. 05-publish Шаг 1c).

Исключение: структура задана источником и пользователь ПРЯМО просил «сохрани структуру» - тогда линтер зовётся с `--allow-skeleton-repeat "скелет унаследован от источника по просьбе автора"` (единственная законная причина), FAIL понижается до WARN с печатью причины.

## Шаг 3.6 - Сверка с донор-эталонами (до передачи в 04-review)

Rewrite не проходит фазу `03-dry`, где эта сверка стоит на полном маршруте (Шаг 3.5), поэтому прогон живёт здесь - иначе улучшенный пост доезжает до выдачи, ни разу не сравнённый с живыми эталонами доноров (дефект Д1 скептик-раунда 1, по решению автора):

```bash
python3 ~/.claude/skills/post/scripts/bench-post.py <файл с final_post> --form-goal <brief.form_goal> \
  --form-class <brief.form_class> \
  --against-etalons
```

- 🔴 **`--form-class` передаётся ВСЕГДА, а не «если reactions» (исправлено по решению автора, Д32 раунда 6).** Класс тут обязан быть ТОТ ЖЕ, что подставит хук `post-phase-gate.sh` на выдаче: хук передаёт `--form-class` при любом значении из словаря `narrative | razbor | sales | gate | event` (блоки «в» и «г», `case "${P_CLASS}"`), без оговорки про цель. Прежняя оговорка «если reactions» давала расхождение мерок на пересечении `mode=rewrite` × `form_class=event`: оператор гнал бенч по классу цели (`sales`), хук - по классу `event`, и человек с гейтом смотрели на разные пороги. Класс в `brief.form_class` пуст - флаг не передаётся (так же поступает хук: пустое значение легально и в команду не попадает).
- `--against-etalons` печатает метрики поста рядом с эталонами своего класса и строку `микс эталонов: <класс> - Донор-А N · Донор-Б N · Донор-В N` (микс показывает, чьими текстами реально меряется класс, и называет донора, которого корпус в этот класс не дал, с точной причиной отсева).
- 🔴 **Случай «класс несовместим с целью»: строка `[ФОРМА-КОЭРЦИЯ]` (дописано, Д79 раунда 26, тот же закон, что в `03-dry.md:162`).** Появилась в выводе бенча - прогон недействителен как мерка: `form_goal`×`form_class` был передан нелегальной парой, профиль взят чужой, а сверка с эталонами шла классом, который автор не заявлял. Чинится `brief.form_class` (или цель в `01-router`), а не повторным прогоном с тем же флагом.
- 🔴 **Класса может не быть в наборе (дописано, Д22 раунда 4).** Записи есть только у `narrative`, `razbor`, `sales`. Пост цели `forwards`, цели/класса `gate` и класса `event` даёт строку `эталонов этого класса в наборе нет, сверка идёт по всему набору (счёт против ЧУЖИХ классов - ориентир, не мерило)`. На такой строке нельзя писать «форма сверена с донорами класса» - в `04-review` уезжает факт «эталонов класса нет, сверка шла по всему набору как ориентир».
- FAIL на HARD-пороге чинится тут же, до передачи в `04-review`; WARN печатается и обосновывается одной строкой.
- Набора эталонов нет / он пуст → бенч печатает `[INFO] эталоны недоступны, сверка с донорами пропущена` и идёт дальше: вердикт и exit-код от этого не меняются (портативность для ученика).
