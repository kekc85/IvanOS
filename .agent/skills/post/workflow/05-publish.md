## Шаг 0b - 🔴 СВЕРКА С ТЗ ВЛАДЕЛЬЦА + КАНАЛ ДОСТАВКИ (HARD, NEW по решению автора)

**Прецедент.** в даты запуска.2026 пост прошёл реестр целиком и был забракован владельцем «0 из 10»: заказанные пункты (новость-инфоповод, «как получить», «что успеть за неделю», FOMO) потерялись между фазами, а артефакт вдобавок продублирован простынёй в чат при заказанной доставке в бот («зачем мне сюда? я же сказал, в боте отправить»).

**Правило 1 - ТЗ.** В state есть `brief.tz_ivana` (Шаг 0.3 роутера) → перед выдачей напечатать таблицу «пункт ТЗ → каким куском поста закрыт (цитата)». Пункт без куска = выдача запрещена, возврат в тот слой, где пункт потерялся. Сверка «по памяти» не считается - только против записанного списка.

**Правило 2 - канал доставки.** Владелец назвал канал доставки (бот, файл, конкретный чат) → артефакт целиком уходит ТУДА, а в чат - короткий отчёт строкой (что отправлено, куда, id сообщения). Полный текст поста в чат при заказанной доставке в канал НЕ дублируется. Канал не назван → дефолт прежний: copyable markdown-блок в чат (закон-якорь №12).

**Правило 2b - в канал уходит ГОТОВЫЙ вид, не сырец (NEW по решению автора, разнос «скинул без форматирования, даже ссылки не вставлены»).** Доставка в Telegram-бот/чат идёт с настоящим форматированием: `parse_mode: HTML` (`<b>` жирный, `<i>` курсив, `<a href>` ссылка вшита в слово), спецсимволы `& < >` экранированы. Звёздочки `**…**` сырым текстом и ссылка отдельной строкой-инструкцией = брак доставки: владелец должен получить сообщение, которое можно форвардить в канал как есть. Инструкция «выдели руками» остаётся ТОЛЬКО там, где канон элемента прямо требует ручной вставки (PS-ACTION при ручном постинге), а не заменяет форматирование всего поста.

**Правило 3 - референс.** Если элемент поста (приписка, CTA, оформление) шёл по референсу владельца (ссылка/скрин) - в отчёте выдачи строка `референс: <элемент> взят 1:1 из <источник>`. Элемент «по мотивам» вместо дословного = брак выдачи (Шаг 0.3 роутера).

## Шаг 2 - Generate 2-3 A/B варианта

A/B варианты = разные версии того же поста под разные A/B тесты. Не правки - альтернативные направления.

### Variation A - Hook alternative

Взять `outline.headline_alternatives[0]` (variant A - hook-alt из stage 02).

Переписать первые 2-3 строки `final_post` под этот альтернативный hook (другой type из 15 templates), сохранив остальное тело.

Output: полный текст альтернативного поста.

**Записать:** `variation_a = <full text>`.

### Variation B - Archetype alternative

Взять `outline.headline_alternatives[1]` (variant B - archetype-alt из stage 02).

Переписать tone / framing основной части под альтернативный archetype:
- Если оригинал был Magician → перепиши с Sage tone (более framework-driven, less transformation-driven)
- Если оригинал был Sage → перепиши с Outlaw tone (more contrarian edge)
- Если оригинал был Outlaw → перепиши с Magician tone (more transformation focus)

Сохранить same core idea (`outline.angle`), изменить только подачу.

**Записать:** `variation_b = <full text>`.

### Variation C - CTA alternative (опционально)

Если оригинальный CTA был soft → попробовать чуть более direct.
Если был direct → попробовать soft / open-ended.

> 💰 **При `brief.launch_window = true` (NEW v5.0):** вариации CTA подчиняются Sales Gate 4.S.1 — то же ЕДИНСТВЕННОЕ действие из боевой карточки, кнопка + практ-ремарка, без вопросов/open-ended. Варьировать можно мост к действию и формулировку «почему сегодня» (на реальных фактах), НЕ тип действия. Вариация, обходящая 4.S, = брак.

Только если CTA - meaningful часть поста (sales / build-in-public / tool-drop). Для personal-reflection / short-situational без CTA - пропустить.

**Записать:** `variation_c = <full text or null>`.

## Шаг 3 - STEPPS evaluation (Beттs framework)

`Read(references/maxwell-ross-9-checklist.md)` или соответствующий раздел про STEPPS.

Оценить `final_post` по 6 параметрам STEPPS (Jonah Berger - Contagious):

| Параметр | Что меряет | Score 1-5 |
|---|---|---|
| **S - Social Currency** | Поделившийся выглядит умнее / в курсе? | ? |
| **T - Triggers** | Есть ли якорь в посту, который напомнит о нём в повседневности? | ? |
| **E - Emotion** | Вызывает ли сильную эмоцию (awe / anger / amusement / inspiration)? Не «sadness» - она убивает share. | ? |
| **P - Public** | Видимо ли? (формат подходит для public share, не приватный) | ? |
| **P - Practical Value** | Useful info которую сохранят / применят? | ? |
| **S - Stories** | Есть ли narrative wrapper вокруг point? | ? |

**Каждый параметр:**
- 1 = отсутствует
- 2 = слабо выражен
- 3 = средне
- 4 = сильно
- 5 = отлично

**Общий STEPPS score:** sum / 30.

Если average < 3 → flag: «STEPPS слабый, виральность низкая». Не блокер (review уже прошёл), но для user info.

**Записать:**
```
stepps_score:
  S_social: <1-5>
  T_triggers: <1-5>
  E_emotion: <1-5>
  P_public: <1-5>
  P_practical: <1-5>
  S_stories: <1-5>
  total: <N>/30
  average: <N.N>
```

> 🔴 **Факты Telegram-форматирования при ручной вставке:** (1) markdown-символы (`**жирный**`, `__курсив__`, `||спойлер||`, `` `моно` ``, `~~зачёрк~~`) авто-превращаются в формат ТОЛЬКО когда их НАБИРАЮТ в поле Telegram и отправляют; при ВСТАВКЕ готового текста они НЕ конвертируются надёжно и торчат буквами. > 🔴🔴 **ОВЕРРАЙД по решению автора (прямая директива автора, ДЕФОЛТ): пост выдавать в блоке кода (```) С markdown-ЗВЁЗДОЧКАМИ `**жирный**` / `*курсив*` ВНУТРИ** — чтобы при копировании звёздочки КОПИРОВАЛИСЬ (рендеренный жирный в чате теряет звёздочки при копировании → человек получает текст без выделения, бесило автора несколько раз). автор применяет звёздочки сам. Точек в конце абзацев НЕ ставить. Прежний «чистый текст + Карта» (п.1/1a ниже) — НЕ дефолт, только по явному запросу автора.
