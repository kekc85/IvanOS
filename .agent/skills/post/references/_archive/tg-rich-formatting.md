# TG Rich Formatting - слой богатого форматирования (v5.4, 2026-07-16)

> **Что это.** по решению автора Telegram выпустил «Расширенный текстовый редактор» - в сообщениях теперь рендерятся таблицы, чек-боксы, формулы, списки, заголовки, разделители, коллапс-блоки. Владелец скилла ведёт TG-канал и хочет, чтобы `/post` умел выдавать посты с этим форматированием ради вовлечения. Это НЕ замена телеграм-разметки из `_phases-state.md` (жирный/курсив/спойлер/цитата остаются основным инструментом) - это ДОПОЛНИТЕЛЬНЫЙ слой усилителей поверх обычного текста, применяемый точечно.
>
> **Статус:** фича однодневная (релиз по решению автора), часть фактов ниже помечена confidence VERIFIED/UNKNOWN. На UNKNOWN не опираться при сборке поста - см. раздел 7.

## 1. Факты о фиче

**VERIFIED (high):**
- Пользовательский редактор: релиз по решению автора, iOS + Android подтверждены, Desktop скорее да, macOS/Web - UNKNOWN. Открывается разворотом поля ввода (иконка `[]` в правом углу поля), внутри полноэкранный редактор с тулбаром: «+», списки (маркированный/нумерованный/чек-лист), таблица, скрепка, эмодзи
- Сущности редактора: таблицы, math-формулы (LaTeX-вид), чек-боксы, маркированные и нумерованные списки, выравнивание по центру, заголовки, разделители, коллапс-блоки, цитаты, сноски
- ОТПРАВКА rich-сообщения пользователем требует Telegram Premium (у владельца есть). Просмотр входящих rich-сообщений Premium НЕ требует
- **Деградация на старых клиентах:** над сообщением плашка «This message is not supported in your version of Telegram. Please update to the latest version», обычный текст и базовые entities (жирный и т.п.) рендерятся, неизвестные блоки теряются или падают в plain text. Покомпонентная раскладка деградации (что именно происходит с ТАБЛИЦЕЙ отдельно от ЧЕК-ЛИСТА) - UNKNOWN
- **Bot API:** 10.1 (по решению автора) добавил метод `sendRichMessage` + классы `RichBlock*`/`RichText*` (отдельная система, НЕ `MessageEntity` и НЕ `parse_mode`); 10.2 (по решению автора) расширил. `python-telegram-bot` ещё НЕ поддерживает (в roadmap на v23), слать можно только raw HTTP-запросами к Bot API. Лимиты (medium-high confidence): rich message до 32768 символов, таблицы до 20 столбцов, до 500 вложенных блоков, вложенность до 16
- **VERIFIED живым постом в канале (в даты запуска.2026, скриншоты поста ученика + разбор владельца):** в опубликованном rich-посте реально рендерятся - маркированные списки (жирный/курсив внутри пунктов, вложенность) · нумерованные списки · чек-листы с квадратиками · таблицы (в ячейках работают эмодзи ✅/❌ и жирный) · **цитата-блок с ПОДПИСЬЮ автора** (отдельная серая строка под цитатой) · **код-блок с подсветкой синтаксиса** · заголовки H1/H2/H3 · разделители (горизонтальная линия) · **инлайн-изображения в СЕРЕДИНЕ поста, с подписью-caption** · **выделение цветом (highlight, жёлтый маркер)** · подчёркивание · выравнивание по центру (цитата в примере отцентрована). Лимит поста поднят с 4096 до 32 000+ знаков - «восемь старых постов в одном», лонгрид живёт прямо в канале с реакциями/комментами/статистикой, читателя не надо уводить в Telegraph

**UNKNOWN (честно помечено, на это НЕ опираться):**
- Автоконвертация markdown при вводе (`| |` в таблицу, `1.` в список) - неизвестно, работает ли как в Notion
- Сохраняется ли rich-форматирование при вставке скопированной извне таблицы - неизвестно. **ПОЭТОМУ дефолт доставки = ручная сборка блоков в редакторе по карте (раздел 4), НЕ ставка на копипаст**
- Поведение в группах vs каналах - неизвестно
- Точный вид деградации КАЖДОГО типа блока по отдельности (таблица/чек-лист/список могут деградировать по-разному)

## 2. Каталог блоков v5.4 - ПОЛНЫЙ набор, когда применять, когда нет

> v5.4 (по решению автора, прямой запрос владельца «убедись, что мы ВСЕ виды форматирования включили и реально выбираем в workflow»): каталог расширен с 3 типов до полного набора редактора, подтверждённого живым постом в канале. Не используются только формулы/коллапс/сноски (§2.12). Выбор типа - на фазе ФОРМАТ по функции (алгоритм - `formatting-skeleton.md` §5); для обычного поста действует правило одного главного акцента, для режима СТАТЬЯ - свои правила (§2.13).

### 2.1 Таблица

**Когда применять:** сравнение 2-4 опций / до-после / метрики прогресса. До 3 колонок (лимит редактора - 20, но мобильная читаемость режет до 3 - телефон, не десктоп).

**Когда НЕ применять:** данные, которые естественнее сказать одним предложением; сравнение с одним пунктом (не таблица, а просто фраза); когда данные уже есть в тексте абзацем (см. правило «не дублировать» ниже).

### 2.2 Чек-лист

**Когда применять:** самопроверка читателя («отметь, что из этого у тебя есть») или шаги-последовательность, которые читатель реально выполняет по порядку.

**Когда НЕ применять:** список фактов без действия (это обычный маркированный список текстом, не чек-лист); >5-6 пунктов (теряется механика вовлечения, превращается в простыню).

### 2.3 Нумерованный список

**Когда применять:** шаги (сделай раз, два, три - в этом порядке, не переставить).

**Когда НЕ применять:** не-последовательные факты (тогда либо просто текст, либо чек-лист).

### 2.4 Маркированный список (буллеты)

**Когда применять:** реальный перечень 3+ равноправных пунктов по нарастанию силы (Бенсивенга, fascinations); внутри пунктов работают жирный/курсив и вложенность.

**Когда НЕ применять:** как замену связному абзацу (2 пункта = просто предложение); перечень-шаги (это нумерованный список); перечень-самопроверка (это чек-лист).

### 2.5 Цитата-блок с подписью автора

Новый редактор рендерит цитату отдельным блоком с левой линией + серой строкой-подписью под ней (в живом посте: цитата + подпись «Джейсон Стетхем»).

**Когда применять:** смысловая врезка-отступление; слова клиента/ученика/мастера, где ИСТОЧНИК - часть аргумента (подпись = социальное доказательство); панчлайн-афоризм самого владельца как визуальный пик.

**Когда НЕ применять:** цитата без реального автора (подпись выдумывать ЗАПРЕЩЕНО - гейт «не выдумывай контекст»); собственный текст, замаскированный под чужую мудрость; больше одной цитаты на обычный пост.

### 2.6 Код-блок с подсветкой синтаксиса

**Когда применять:** аудитория владельца - вайбкодеры: реальный промпт, команда терминала, фрагмент кода, который читатель скопирует и применит. Код-блок = «инструмент в руки» прямо в посте, не скриншот.

**Когда НЕ применять:** код ради антуража «я технарь»; длиннее ~10 строк в обычном посте (простыня убивает скролл - длинное в статью-режим или в гайд по ссылке); псевдокод, который нельзя реально запустить.

### 2.7 Заголовки (H1/H2/H3)

**Когда применять:** ТОЛЬКО режим СТАТЬЯ (§2.13) - секционная навигация лонгрида. В живом посте ученика заголовки держат структуру обзора из 5 разделов.

**Когда НЕ применять:** обычный пост 200-500 слов (там роль заголовка играет жирная первая строка-хук, H-блоки на коротком тексте = канцелярит-структура).

### 2.8 Разделитель (горизонтальная линия)

**Когда применять:** режим СТАТЬЯ - граница крупных смысловых частей (в живом посте отделяет «текст ИИ» от «мой вариант»); резкий слом контекста, который абзацем не передать.

**Когда НЕ применять:** обычный пост (стык держит скольжение Шугермана, а не линия); чаще 1 раза на 1000 знаков.

### 2.9 Инлайн-изображение в середине поста (+ подпись)

Картинка теперь живёт В ЛЮБОМ месте текста, с caption-подписью, а не только обложкой сверху.

**Когда применять:** доказательство в момент аргумента (скрин метрики/результата ровно там, где о нём речь); личное фото на эмоциональном пике истории; режим СТАТЬЯ - иллюстрация на секцию.

**Когда НЕ применять:** декоративный сток «чтобы был визуал»; обычный короткий пост, где одна обложка справляется (см. visual suggestion, Шаг 4.V); картинка, дублирующая текст рядом.

### 2.10 Выделение цветом (highlight)

Жёлтый маркер по фразе - самый сильный визуальный удар нового набора, сильнее жирного.

**Когда применять:** ОДНА фраза-вывод, ради которой написан пост (то, что читатель должен унести, даже если прочёл только её).

**Когда НЕ применять:** больше 1 фразы на пост (два маркера = ни одного); целые абзацы; вместе с жирным на той же фразе (двойной акцент = шум).

### 2.11 Подчёркивание

**Когда применять:** точечно, слово-термин или короткая фраза-условие (в живом посте: «Premium»). Фон, не главный акцент.

**Когда НЕ применять:** ссылки рядом НЕ подчёркивать текстом (читатель примет за ссылку и будет тыкать); как замену жирному по всему посту.

### 2.12 Не используется в v5.4

Math-формулы (аудитория не математики), коллапс-блоки (прячут контент - враг скролла), сноски (журнальный жанр, не TG). Кандидаты на будущее, в контракт не входят.

### 2.13 Режим СТАТЬЯ (лонгрид до 32к знаков) - отдельный жанр

Лимит 32 768 знаков открыл новый формат: полноценная статья прямо в канале (реакции/комменты/статистика на месте, Telegraph и сайт больше не нужны как костыль; сам владелец: «пойду переупаковывать свои лонгриды под новый формат»).

- **Когда:** обзоры, разборы-туториалы, переупаковка лонгридов/гайдов; НЕ дефолт - обычный пост 200-500 слов остаётся ядром канала
- **Правила форматирования статьи (вместо правила одного акцента):** заголовки H2 на секции · 1 картинка-доказательство на 1-2 секции · таблица/чек-лист/код-блок легальны по одному на секцию, если несут функцию из каталога · разделители на границах крупных частей · highlight по-прежнему ≤1 на ВСЮ статью · ядро (тезис, CTA, ссылка) по-прежнему обычным текстом, деградация-safe
- **Структура текста:** это жанр `longform` (800-3000 слов), не пост - смысловой конвейер брать оттуда, слой TG-форматирования отсюда

## 3. Правила применения (D1, ядро)

1. **Только для `platform == telegram`.** LinkedIn/другие платформы этот слой не трогает.
2. **Дозировка: максимум ОДИН rich-блок на обычный пост** (правило одного главного акцента, канон - `references/formatting-skeleton.md` §2; ужесточено по решению автора с «1-2»). НЕ каждый пост - не чаще 1 из 3-5, после rich-поста минимум 2 поста без блоков. Пост без rich-блоков остаётся нормой. **Исключение - режим СТАТЬЯ (§2.13): там свои правила дозировки, посекционные.**
3. 🔴 **Деградация-safe (главное правило).** Ядро поста - тезис, история, CTA, ссылка - ВСЕГДА обычным текстом. Rich-блок = усилитель, не носитель смысла. CTA и ссылки НИКОГДА не кладутся внутрь rich-блока. Пост обязан полностью работать, если блок выпал (часть аудитории на старом клиенте увидит только плашку «не поддерживается»).
4. **Соответствие смыслу** - см. каталог блоков выше (раздел 2). Блок ставится потому что тип контента ему соответствует, не потому что «давно не было таблицы».
5. **Не дублировать.** Данные, вошедшие в таблицу, не повторяются жирным текстом рядом - либо там, либо тут.
6. **Чек-лист = интерактивная механика.** Связывается с CTA-лестницей (`tg-engagement-layer.md`): «сколько пунктов отметил - кинь цифру в комменты» / реакция-голосование поверх чек-листа.
7. **Новизна-эффект временный.** Фича вышла по решению автора - первые посты с таблицей/чек-листом сами по себе инфоповод и паттерн-прерыватель в ленте. Эффект угасает по мере того как формат становится привычным - не строить долгосрочную стратегию только на новизне.
8. **HARD-правила поста действуют на ТЕКСТ, не на содержимое блока.** Точки в конце абзацев / em-dash / двоеточия ≤1 - это правила прозы поста. Содержимое ячеек таблицы и пунктов чек-листа освобождено от проверки точек/лесенки (короткие фразы в ячейках - это нормально, не staccato). Но **em-dash запрещён и внутри блока** - это правило без исключений.

## 3.1 Рабочий контур доставки rich в КАНАЛ (по решению автора, ПРОВЕРЕНО живьём)

🔴 Живой rich (таблица/highlight/цитата) собирает ТОЛЬКО бот через Bot API `sendRichMessage`.
Юзер-аккаунт (Telethon/MTProto) rich-блоки НЕ умеет (нет entity Table/marked - проверено),
копипаст и форвард из лички в канал блоки роняет. Единственный авто-путь в канал:

1. **Бот-админ канала кладёт rich-пост в ОТЛОЖЕННЫЕ канала** (`schedule_date` = unix-ts +N сек).
   Пост НЕ публикуется, лежит в «Отложенных», владелец открывает, при желании цепляет фото руками
   (фото ВНУТРИ rich Bot API пока не отдаёт - структура photo-блока не разгадана), жмёт «Отправить».
   Владелец НЕ собирает форматирование руками - оно уже собрано (правило).
2. Скрипт: `scripts/send-rich-post.py --markdown-file <пост.md> --chat-id <@канал|-100id> --schedule-in <сек> --now-ts <$(date +%s)> --send`.
   chat_id канала: приватный инвайт-хэш API не принимает - резолвить в `-100<id>` через юзер-сессию
   (CheckChatInviteRequest) или взять @username. Бот должен быть админом канала с `can_post_messages`.
3. Тестировать в ОТДЕЛЬНОМ тест-канале, не в основном (цена ошибки в проде = сотни людей сразу).

🔴 **ВОЗДУХ между абзацами (обязательно, встроено в скрипт `add_paragraph_air`).** rich-парсер
схлопывает пустые строки между paragraph-блоками → абзацы вплотную без отступа. Между блоками
нужен абзац из НЕРАЗРЫВНОГО пробела ` ` (обычный пробел парсер съедает). Скрипт делает сам.

🔴 **Курсив = ОДИНАРНОЕ `_текст_`** (GFM). Двойное `__текст__` парсер НЕ рендерит курсивом,
проглатывает как текст. Жирный - `**текст**`, highlight - `==текст==`, цитата - `>`.

## 4. Контракт выдачи (D2 v3, по решению автора - ЖЁСТКИЙ вердикт владельца)

> **Два прецедента по решению автора, оба - прямые вердикты владельца:**
> 1. Маркеры-заглушки `[ТАБЛИЦА 1]` в тексте поста - «я это скопирую, это же никуда не вставится». Маркеры ЗАПРЕЩЕНЫ.
> 2. Секция «Блок к посту (опционально)» с инструкцией ручной сборки - «какое нахер опционально? Ты мне должен только пост скидывать: один целый для копирования и вставки. У нас нету категории опционально-неопционально». Вторые секции, опции и инструкции сборки ЗАПРЕЩЕНЫ.

**Контракт: выдача ЛЮБОГО поста = ОДИН цельный пост в блоке кода. Копируй-вставляй-отправляй. Всё.**

**D2 v5 - ФИНАЛ (по решению автора, ЗАКРЫТО ЖИВЫМ ТЕСТОМ АВТОРА).** владелец вставил markdown-таблицу в полноэкранный редактор (десктоп) - разметка ОСТАЛАСЬ плоским текстом «| Параметр |...», НЕ сконвертировалась (скриншоты по решению автора). Одновременно скриншоты тулбара показали устройство редактора: блоки создаются ТОЛЬКО кнопками - меню стилей (Heading/Text/Bold/Italic/Underline/Strikethrough/Monospace/Spoiler/Formula), меню списков (Bullet/Numbered/**Checklist**/Indent), кнопка **Insert Table**, «+» = Photo-Video/Location/Audio. Итого ФАКТ (VERIFIED тестом владельца): **никакой текст при вставке не превращается в таблицу/чек-лист/формулу. Пейст-доставка живых блоков невозможна в принципе.**

Следствия:
1. **Ручной контур: пост выдаётся БЕЗ каких-либо блоков и БЕЗ их разметки** (разметка = мусор-палки в редакторе, прецедент по решению автора «я сюда вставил, а говнос получилось»). Один цельный пост, сравнения и перечни выражаются текстом. Никаких маркеров, вторых секций, «опционально», инструкций сборки (вердикты владельца выше).
2. **Живые блоки доставляются ЕДИНСТВЕННЫМ способом - бот присылает УЖЕ СОБРАННОЕ rich-сообщение.** ✅ ПУТЬ РАБОТАЕТ, подтверждено живой отправкой по решению автора (message_id 6605 в чат владельца): скрипт `scripts/send-rich-post.py --markdown-file <пост.md> --send` отдаёт серверу `rich_message.markdown` (GFM: `**bold**`, `| |` таблица, `- []` чек-лист) - Telegram САМ собирает блоки (таблица пришла с рамкой/шапкой, чек-лист с галочками). Ручная сборка `blocks` НЕ нужна (API отклонял наши имена RichText-узлов - legacy в скрипте). Боевая отправка только по явному «да» владельца (страж no-bot-send-without-permission). ## 5. Механика вовлечения чек-листа

Чек-лист - не просто список, а интерактивный приём: читатель мысленно (или физически, если рендерится с галочками) отмечает пункты и получает личный результат («у меня 2 из 3»). Связка с CTA-лестницей `tg-engagement-layer.md`:
- «Сколько пунктов набралось - кинь цифру в комменты» (аналог вопроса-вовлечения, ранг 3 в CTA-лестнице)
- Реакция-голосование поверх итога чек-листа («🔥 если 3/3, 🐳 если 0/3»)
- Не превращать чек-лист в опросник ради опросника - он обязан нести реальную самопроверку по теме поста, не оторванную механику

## 6. Bot API - будущий путь автоматизации (справочно, НЕ текущий workflow)

Bot API 10.1 добавил `sendRichMessage` + классы `RichBlock*`/`RichText*` - отдельная система от `MessageEntity`/`parse_mode`, которыми пользуются обычные боты. `python-telegram-bot` (библиотека, которой мог бы пользоваться автопостинг) rich-блоки пока НЕ поддерживает - в roadmap на v23. Слать `sendRichMessage` можно ТОЛЬКО raw HTTP-запросами к Bot API напрямую, без обёртки библиотеки.

**Статус для этого скилла:** справочно на будущее. Сейчас `/post` выдаёт под РУЧНОЙ постинг (владелец постит руками в приложении, см. `_phases-state.md` п.8) - контракт раздела 4 рассчитан именно на это. Если/когда появится автопостинг через Bot API 10.x, `sendRichMessage` - кандидат на прямую доставку rich-блоков без ручной сборки. До этого момента - не строить пайплайн вокруг него.

**Отправщик подготовлен (по решению автора), НЕ активирован.** `scripts/send-rich-post.py` - raw HTTP через sendRichMessage (Bot API 10.2), stdlib only. Дефолт `--dry-run` (печатает JSON, в сеть не ходит); `--demo` даёт встроенный пример поста (заголовок/абзац/таблица 3×4/чек-лист/абзац); реальная отправка только `--send` и только по явному "да" владельца (страж `no-bot-send-without-permission.sh` блокирует send*-вызовы к api.telegram.org без обхода `IVAN_ALLOW_BOT_SEND=1`). Токен/chat_id - из env `IVAN_TG_BOT_TOKEN`/`IVAN_TG_CHAT_ID` с фолбэком на `~/.business/scripts/auto-uniqualize/.env` (тот же токен, что у auto-uniqualize доставщиков, <твой-бот>). Схема полей: метод/параметры sendRichMessage и факт поля `blocks` у `InputRichMessage` - VERIFIED напрямую с core.telegram.org; точные имена полей ячейки таблицы (`is_header`/`colspan`/`rowspan`/`align`/`valign`) и чек-бокса (`has_checkbox`/`is_checked`) - UNVERIFIED напрямую (страница обрезалась до раздела types/methods при каждом WebFetch), взяты из вторичного зеркала спеки и помечены в коде. До прогона первого реального ответа Bot API - считать структуру рабочей гипотезой, не подтверждённым контрактом.
