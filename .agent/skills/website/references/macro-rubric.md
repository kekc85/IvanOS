# Макро-рубрика — сайт как СИСТЕМА (Фаза 10, горизонтальная ось)

> 🔴 Зачем этот файл. Фаза 09 доводит КАЖДЫЙ экран до ≥9 в вакууме (11 линз — вертикальная
> ось). Но сайт — не сумма экранов, а ПОСЛЕДОВАТЕЛЬНОСТЬ, по которой движется один человек.
> Локальный оптимум N экранов ≠ глобальный оптимум воронки. Согласованность живёт ТОЛЬКО
> в стыках и в порядке — туда 09 структурно не смотрит. Эта рубрика проверяет ИМЕННО это.
> Источник: разбор автора — «экраны собираются без единой маркетинговой
> согласованности, это зона роста». Применяется в `workflow/10-site-review.md` (СТАДИЯ C).

## 🔴🔴 ГЛАВНЫЙ ЗАКОН РАЗГРАНИЧЕНИЯ (не дублировать 09)

Эта рубрика проверяет **ТОЛЬКО то, что невидимо на одном экране.** Если дефект виден на
отдельном экране (орфан, контраст, мокап-плейсхолдер, кривой перенос, наезд) — это РАБОТА
ФАЗЫ 09, не сюда. Сюда — только МЕЖэкранное: дуга, порядок, аромат, сшивка, путь к CTA.
Признак, что ты залез в чужой скоуп: дефект формулируется про один экран без слова «между/
после/перед/по всему сайту». Тогда верни его в 09.

## 🔴 ЗАКОН ДОКАЗАТЕЛЬНОЙ БАЗЫ: мастера = ЛИНЗЫ, не образцы бенчмарка

Schwartz / Hormozi / Cialdini / StoryBrand / Ries–Trout / Sugarman — это **рубрика (ЧТО
проверять)**, операциональные тесты. Они НИКОГДА не кладутся в бенчмарк как образцы — это
прямой запрет (`feedback_benchmark_same_type_exemplar_not_method`, страхуется
`FRAMEWORK_DENYLIST` в `website-review-gate.sh`). **Бенчмарк сайта** = живые сайты ТОГО ЖЕ
типа целиком (вся воронка), из `refs/_manifest.json`. Метод — линза, образец — живой сайт.

## 8 ОСЕЙ (каждая = мастер + операциональный тест + машинный пол + порог)

Порог по КАЖДОЙ оси — **≥9/10** (шкала — `benchmark-standard.md`). Балл сайта = `min` по
осям, пересчитывает МАШИНА (хук), не самоназначенное число.

### A. One Big Idea — одна сквозная мысль · **Ries–Trout (positioning)**
- **Операциональный тест:** прочитать ВСЕ экраны как впервые → сформулировать ядро в ОДНОМ
  слове/фразе. Каждый экран усиливает это слово? Тест жертвы: что сайт явно НЕ обещает
  (позиционирование = выбор чего НЕ делать)? Тест удаления: удали любой экран — ядро держится?
  Да → экран размывает фокус.
- **FAIL-сигнатура:** «вижу 3 разных питча» / «экран 1 про экспертный AI, экран 3 про
  комьюнити-вайб, экран 5 про дешевизну» / «для сегмента A или B — непонятно».
- **Машинный пол (ревью M4):** ось A держится не на одном вкусе — её судят ≥2 СУДЬИ, каждый формулирует «ядро сайта в одном слове»; оба ядра пишутся в `cores` маркера. Гейт сверяет: ядра РАЗОШЛИСЬ → размытое позиционирование → BLOCK. Сходятся → ось A прошла.

### B. Лестница осознанности — порядок = состояние читателя · **Schwartz**
- **Операциональный тест:** каждому экрану присвоить ОДНУ стадию (1 unaware → 2 problem-aware
  → 3 solution-aware → 4 product-aware → 5 most-aware/buying). Вход (1-й экран) совпадает со
  стадией основной ЦА? По скроллу стадия РАСТЁТ без прыжков назад и без перескока?
- **FAIL-сигнатура:** «экран говорит как будто решение уже принято, а пруфов ещё не было» /
  вход на стадии 3 при ЦА на стадии 1.
- **Машинный пол (`journey-map-audit.py`):** поле `awareness` (1-5) НЕ убывает по порядку
  экранов; финальный экран = max. Нарушение → блок ещё до судей.

### C. Информационный аромат — каждый экран тянет в следующий · **Sugarman (slippery slide)**
- **Операциональный тест:** на КАЖДОМ стыке — «почему он скроллит ДАЛЬШЕ прямо сейчас?»,
  пальцем в конкретную фразу/элемент. Открытая петля (вопрос/интрига) закрывается НИЖЕ?
  Stop-point: где человек естественно закроет вкладку (конец списка, после картинки)? Перед
  этой точкой стоит «семя любопытства»? (≤1 петля на стык — больше = отчаяние.)
- **FAIL-сигнатура:** «3 экрана прошли без причины читать дальше» / «тут можно честно сказать
  „мне хватит“ и уйти».
- **Машинный пол (`journey-map-audit.py`):** каждый `question_raised` (непустой) резолвится в
  `answered_by` БОЛЕЕ ПОЗДНЕГО экрана. Висячая петля (ответ выше/нет ответа) → блок.

### D. Архитектура убеждения — пруф ПЕРЕД просьбой, не скучкован · **Cialdini (pre-suasion)**
- **Операциональный тест:** перед КАЖДЫМ значимым ask (опт-ин, клик CTA, оплата) — в 1-2
  экранах ДО него есть хотя бы один принцип влияния (взаимность/обязательство/соц.пруф/
  авторитет/симпатия/дефицит/единство)? Пруфы НЕ свалены весь в один блок «Возражения» в
  конце, когда интерес уже умер? Нужное ментальное состояние создано в экране НЕПОСРЕДСТВЕННО
  перед ask (pre-suasion: безопасная дистанция = 1 экран назад)?
- **FAIL-сигнатура:** «соц.пруф на экране 1, а большой ask на экране 6 — пруф выветрился» /
  «все возражения скучкованы, ask стоит голый».
- **Машинный пол:** частично — ask-экран (cta≠none) без принципа в соседнем экране → судья
  флагует (детерминированно не ловится, остаётся за судьёй D).

### E. Конверсионная физика — путь один, трение↓ мотивация↑ · **Hormozi VE + MECLABS CSH + Fogg**
- **Операциональный тест:**
  - **Value Equation (Hormozi)** для оффера/CTA: явны 4 компонента — мечта-результат · вера в
    успех (пруф/шаги/гарантия) · скорость первого результата · усилие/жертва (что отдаёт, что
    облегчено)? Один отсутствует → покупатель узнаёт позже и чувствует обман.
  - **CSH (MECLABS):** C = 4m + 3v − 2(1−a) − 2f. По всему сайту: мотивация (m) собрана к точке
    CTA, ценность (v) ясна, тревога (a) снята, трение (f) минимально на пути к действию.
  - **Fogg (B=MAT):** в точке CTA одновременно есть мотивация, способность (легко сделать) и
    триггер (видимая кнопка)?
- **FAIL-сигнатура:** «не понимаю что получаю и как быстро» / «путь к оплате петляет» /
  «тупик — некуда нажать».
- 🔴 **Дедуп с 09 (ревью H2):** per-screen «один фокус/CTA на экране» и `flow_to_cta` — это
  09 (вертикаль). Здесь E смотрит ТОЛЬКО МЕЖэкранную физику: мотивация НАКАПЛИВАЕТСЯ по
  скроллу, пруф приходит ДО ask за 1-2 экрана, трение не растёт к точке оплаты.
- **Машинный пол (`check-deploy.py`):** все CTA резолвятся, есть рабочее целевое действие,
  опц. одна цель (`--target`); мёртвый/отсутствующий CTA → блок.

### F. Редактура — каждый экран зарабатывает место · **Hormozi (cut/stack)**
- **Операциональный тест:** на КАЖДЫЙ экран — «двигает продажу (мечта/вера/скорость/лёгкость)
  или это тормоз?». Тормоза: повтор выгоды, размытое заверение, бренд-история не двигающая
  оффер, касательная фича. Правило: убрал — ask не ослаб → убрать. Стек оффера: каждый
  элемент дёшев тебе + ценен покупателю; иначе срезать. Стек лин, не раздут.
- **FAIL-сигнатура:** «экран приятно читать, но он не помогает сказать „да“» / дубль-секция.
- **Машинный пол:** — (вкус/смысл, только судья). Дубль контента ловится сравнением journey-
  ролей (две строки с одинаковой `role` + близким `thinks` → кандидат на REMOVE).

### G. Канва + нарратив — клиент-герой, сквозной язык · **StoryBrand (Miller) + Gestalt**
- **Операциональный тест:**
  - **StoryBrand:** клиент = герой (не «мы/наша компания»: доля «мы»-предложений <15%,
    «ты/твоя трансформация» >70%); проблема в 3 слоя (внешняя/внутренняя/философская);
    трансформация видна (до→после: «я становлюсь X», не «я получаю фичу Y»).
  - **Сквозные линии канвы (НЕ токен-консистентность — её держит 09 линза 8 + regression):**
    повторяющийся МОТИВ/история через экраны (образ hero отзывается в pricing), единый
    нарративный визуальный язык — не «hero и тарифы как два разных сайта». 🔴 Поэлементную
    идентичность токенов НЕ дублируем (это вертикаль 09); здесь — нарративная связность.
- **FAIL-сигнатура:** «сайт про то какие мы крутые, а не кем станет он» / «hero и тарифы —
  два разных сайта по дизайну».
- **Машинный пол:** регрессия Слоя 2 (`regression-check.mjs`) ловит токен-дрейф, но это уже
  работа 09 линзы 8 — здесь судья G смотрит ТОЛЬКО нарративную связность (StoryBrand-дуга +
  сквозной мотив), которой в 09 нет. Дубль с 09 запрещён (закон разграничения выше).

### H. Закрытие возражений — страхи/возражения сняты ДО цены · **JTBD/objections (запрос автора)**
- **Операциональный тест:** взять ключевые возражения/страхи ЦА (источник — `.business/audience/objections.md` + аватар: страхи/желания). По сайту: КАЖДОЕ значимое возражение закрыто на каком-то экране ДО первого primary-CTA (не после цены, когда уже ушли). Желания и страхи из аватара отражены в копи воронки, а не проигнорированы.
- **FAIL-сигнатура:** «возражение „дорого / не получится у меня / нет времени“ не снято нигде до оплаты» / страх есть в аватаре, но на сайте не отвечен.
- **Машинный пол:** частично — список возражений из `objections.md` сверяется с журналом/HTML (есть ли экран-ответчик ДО primary-CTA); семантику закрытия судит судья 2 (скептик).
- Порог ≥9. 🔴 Это sitewide-проверка (по запросу автора «страхи/желания/возражения») — НЕ per-screen контур смысла 09; здесь — покрыта ли ВСЯ карта возражений ПО ХОДУ воронки.

## 🔴 СКОУП ПРОВЕРКИ = ЗАКРЫТАЯ МАТРИЦА (не открытый список)

Полнота гарантируется матрицей, выведенной из РЕАЛЬНЫХ данных, а не списком классов
(`feedback_verify_completeness_by_content`). Две оси охвата, обе обязательны:

```
ПОЛНОТА = 7 ОСЕЙ (что искать) × ВСЕ СТЫКИ ЭКРАНОВ (где искать)
          где «стыки» = пары соседних экранов из screens[] state (машинно, не из головы)
```

- Журнал (Customer Journey Map) ОБЯЗАН покрыть КАЖДЫЙ экран из `screens[]` — машинный пол
  блокирует, если множество строк journey ≠ множеству экранов. Пропустить экран нельзя.
- Новый класс дефекта НЕ требует правки рубрики: судья ищет «всё, что не как у эталона того
  же типа», по матрице осей×стыков. СВЕРХ списка: любое «между экранами смотрится не так,
  как сделала бы топ-студия» = валидный FAIL, даже если не попало в 7 осей.

## 🔴 ГЛУБИНА И ШИРИНА

- **Глубина:** на каждую ось — операциональный тест ИМЕННОГО мастера (не «оцени на вкус») +
  **грундинг** (вердикт привязан к конкретному экрану/стыку; без привязки НЕ засчитан —
  защита от «вообще плохо») + 2-3 прохода уточнения (метод 09, arxiv 2412.16829/2510.08783).
- **Ширина:** матрица осей×стыков + **4 судьи с разными линзами** (ниже), свод по ХУДШЕМУ
  баллу оси + журнал покрывает все экраны.
- 🔴 **Мобильная ось (ревью):** воронка чаще мобильная — каждый судья проходит сайт на **390 И 1280**; аромат/порядок/CTA-путь на мобиле (длиннее экраны, sticky-bar, CTA уезжает) ломаются независимо от десктопа. Дефект на одной ширине = FAIL оси.

## 4 АДВЕРСАРИАЛЬНЫХ СУДЬИ (перспектива-диверсити; свежие, НЕ сборщик)

Каждый — pairwise против живого сайта того же типа, с грундингом, 2-3 прохода. Свод осей —
по ХУДШЕМУ баллу (одна линза слепа → добирает другая). Установка-промпт каждому: «Презумпция:
рассинхрон есть, найди его. Вот воронка-эталон того же типа, вот наш сайт целиком».

| Судья | Линза | Оси | Главный вопрос |
|---|---|---|---|
| 1. Перформанс-маркетолог | воронка / awareness / CSH | B, C, E | где человек выпадает по пути к CTA? |
| 2. Скептик-посетитель | первый заход, сомнение | A, C, F | где я заскучал/засомневался/ушёл бы? |
| 3. Стратег-инвестор | продаёт ли как система | A, D, G | одна ли это идея, ведёт ли к покупке? |
| 4. Арт-директор | канва как система | G | один ли визуальный язык на всём сайте? |

## ИНТЕРПРЕТАЦИЯ → ТАКСОНОМИЯ ПРАВОК

Каждая находка → ровно одна правка, привязанная к ОСИ + ЭКРАНУ:
- **REMOVE** — дубль/трение (ось F): экран/блок не двигает продажу → убрать.
- **ADD** — недостающее звено (ось C/D/E): висячая петля без ответа, ask без пруфа, нет
  скорости результата → добавить экран/блок.
- **REORDER** — порядок осознанности (ось B/D): экран не на своей стадии / пруф после ask →
  переставить.
- **CONNECT** — сшить (ось A/C/G): смысловой/визуальный разрыв между экранами → связать
  (сквозная линия, эхо мотива, мостик-фраза).

## ЛУП СХОДИМОСТИ И ФИНАЛЬНАЯ ПАРАЛЛЕЛИРОВКА

```
build → машинный пол (journey-audit + cta-path) → fix → повтор до НУЛЯ красных
      → 4 судьи параллельно (оси×стыки, pairwise, грундинг) → свод по ХУДШЕМУ
      → применить REMOVE/ADD/REORDER/CONNECT → пересборка → пере-суд
      повтор, ПОКА ОДНОВРЕМЕННО:
        (1) 7 осей ≥9 (min пересчитан машиной)
        (2) машинный пол чист (journey + cta)
        (3) РЕГРЕССИЯ: каждый экран 09 всё ещё ≥9 (правки не сломали экран)
      СТОП по СХОДИМОСТИ, не по числу итераций.
```

## 🔴 АНТИ-ОШИБКА (мои прошлые провалы, не повторять)

1. **Гейт перепроверяет САМ, не верит флагу** (`feedback_enforcement_machine_reverifies_not_flags`):
   `cross_screen:true` / `machine_floor:true` хук НЕ принимает — он сам перегоняет
   `journey-map-audit.py` + `check-deploy.py` и пересчитывает `min` по осям.
2. **Балл = min по осям, не свободное число** (как `criteria` в 09).
3. **Мастера = линзы, не образцы бенчмарка** (FRAMEWORK_DENYLIST).
4. **Скоуп = закрытая матрица из реальных screens[], не открытый список.**
5. **Каждый слой принуждения покрыт selftest** (happy/negative/edge), гоняется после правки.

## Схема маркера `.site-review.json` (рядом с index.html)

```json
{
  "ts": 0,
  "axes": {
    "one_big_idea": 9, "awareness_ladder": 9, "information_scent": 9,
    "persuasion_sequencing": 9, "conversion_physics": 9,
    "editorial_cut": 9, "canvas_continuity": 9, "objection_coverage": 9
  },
  "cores": ["вайбкодинг", "вайбкодинг"],
  "journey": [
    {"screen": "hero", "awareness": 2, "role": "захват+оффер",
     "thinks": "что это и мне ли", "question_raised": "что это даст мне?",
     "answered_by": "value", "cta": "primary"},
    {"screen": "value", "awareness": 3, "role": "механизм",
     "thinks": "ок, как это работает", "question_raised": "а сработает у меня?",
     "answered_by": "cases", "cta": "none"},
    {"screen": "pricing", "awareness": 5, "role": "оффер",
     "thinks": "сколько и что внутри", "question_raised": "", "answered_by": "none",
     "cta": "primary"}
  ],
  "fixes_applied": [
    {"type": "CONNECT", "screen": "value→cases", "axis": "information_scent",
     "note": "добавлен мостик-вопрос, петля закрывается кейсом"}
  ]
}
```
- `axes` — 8 осей, балл по каждой; гейт требует ВСЕ 8 и пересчитывает `min≥9` строго по ним.
- `cores` — «ядро сайта в одном слове» от ≥2 судей (ось A); гейт блокирует, если разошлись.
- `journey` — одна строка на экран, в порядке скролла; машинный пол валидирует структуру.
- `awareness` — 1-5 (Schwartz); `cta` ∈ {primary, secondary, none}; `answered_by` — имя
  более позднего экрана или "none".
