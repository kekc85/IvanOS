# Фаза 4b — ПОЭКРАННАЯ КОНВЕРСИОННАЯ СТРАТЕГИЯ (согласовать ДО пикселей, экран за экраном)

> 🔴 Зачем файл. Прецедент по решению автора (лендинг вайбмаркетинга): агент показывал «визуальную кашу» — собирал hero из головы, дёргал элементы туда-сюда по репликам автора, без единой логики. автор: «ты даёшь бездумную кашу. По каждому экрану ты должен последовательно согласовывать стратегию — аргументировать, доказывать, какие элементы зачем там, почему нужны; показывать у кого уже есть = доказывать что это best practice; не отсебятина и не копипаст без переосмысления. Системно доказывать, что каждый элемент СВОЕЙ ФУНКЦИЕЙ служит конверсии. Оптимизируемся в конверсию/результативность». Этот файл делает экранную стратегию обязательным гейтом ПЕРЕД вёрсткой каждого экрана.

## Закон фазы
1. **Ни одного пикселя экрана без согласованной стратегии этого экрана.** Сначала — стратегия (зачем каждый элемент), апрув автора, потом вёрстка. Обратный порядок = «каша», запрещён.
2. **Экран за экраном, последовательно.** Не вываливать стратегию всех 12 экранов разом. Один экран → таблица-доказательство → апрув/правка → (вёрстка позже) → следующий экран. Автор ведёт по конверсионной логике, а не отлавливает хаос.
3. **Каждый элемент доказывается, а не «мне так нравится».** Для КАЖДОГО элемента экрана: (а) конверсионная функция — что он делает для результата (доверие / снятие возражения / фокус на CTA / пруф / срочность / ясность оффера); (б) доказательство best-practice — КТО из эталонов/топов это использует + источник (референс-доска 2b / `benchmark-standard.md` / research-артефакт с цитатой); (в) почему именно так, а не альтернатива (отвергнутый вариант). Нет хотя бы одного — элемент не оправдан, убрать или переосмыслить.
4. **Не отсебятина и не слепой копипаст.** «Сам придумал» без пруфа = запрещено. «Забрал у конкурента» без переосмысления ФУНКЦИИ под наш оффер = запрещено. Берём ПРИНЦИП (зачем работает) → адаптируем под нашу конверсионную задачу.
5. **Оптимизируем в конверсию, не в красоту.** Критерий включения элемента — вклад в результат (доверие→действие→оплата), а не «смотрится». Декор без конверсионной функции — вырезать.
6. 🔴 **ТРИ СТОП-согласования на экран ДО сборки (микроцикл СТАДИИ B, `_phases-state.md`).** Эта фаза 4b = подфаза **`concept`**. Порядок СТОПов по экрану: `concept` (эта таблица-стратегия — ✋ согласовать) → `copy` (копи экрана + humaniser — ✋) → `design` (визуал/дизайн экрана на языке СТАДИИ A — ✋). Каждый апрув записывать helper'ом в `approvals` (`… '<имя>' 'concept' 'null' 'concept'`). Сборка (Фаза 6) и показ экрана НЕДОСТУПНЫ, пока в `approvals` нет всех трёх — **хук `website-review-gate.sh` физически блокирует показ экрана без них** .

## Формат экранной стратегии (таблица — показать автору)
Для экрана N (из структуры Фазы 3a + копи 3b + Hero-Blueprint, если есть):

**Экран N — <название> · Конверсионная задача экрана: <одна фраза: что экран должен сделать с посетителем>**

| Элемент | Конверсионная функция (зачем для результата) | Доказательство best-practice (кто использует + источник) | Почему так, а не иначе (отвергнутая альтернатива) |
|---|---|---|---|
| H1-оффер | … | флагман ref-00 / Stripe / [research §X] | … |
| фото эксперта + взгляд | доверие к личн. бренду + gaze-cue к CTA | [research узел 1-2: gaze cueing] / флагман | анфас-в-камеру vs 3/4-к-CTA — выбор обоснован данными |
| … | … | … | … |

+ под таблицей: **путь взгляда экрана** (F/Z, где доминирующая CTA, один фокус) и **что НЕ кладём и почему** (отрезанные альтернативы).

+ 🔴 **МОБАЙЛ-ПОРЯДОК + ПЕРФ-СТОИМОСТЬ экрана** (фундамент-решение `00-brief.md` шаг 7): как элементы стекаются на 360/390 (порядок, что скрываем/упрощаем на моб), где доминирующая CTA на мобиле. Для КАЖДОГО тяжёлого элемента (видео/canvas/3D/большое фото/тяжёлый шрифт) — **перф-стоимость и решение**: оправдан ли вес на мобиле, lazy/preload, формат, fallback. Тяжёлый декор без конверсионной функции на мобиле — резать первым. Принцип автора: «на мобилке грузиться максимально быстро» — мобайл-вес элемента входит в решение «класть/не класть», наравне с конверсионной функцией.

## Источник доказательств (строгий research, не из головы)
Пруфы в колонке «доказательство» берём из: (1) референс-доска 2b (живые скрины эталонов, включая нишевые образцы, которые автор отметил как эталонные — напр. forexsprint: берём СТРУКТУРУ/ДИЗАЙН, не смысл/нишу); (2) `references/benchmark-standard.md` (карта критериев); (3) **строгое best-practice исследование** (ресёрч артефакт по теме экрана — eye-tracking/CRO/gaze, с источниками). Если доказательной базы под решение нет — сначала исследовать (research), потом утверждать. Утверждение «это best practice» без названного источника/эталона невалидно.

> 🔴 **ЗАКОН «МЕТОД ≠ ОБРАЗЕЦ» в колонке доказательства .** Допустим ТОЛЬКО живой САЙТ того же ТИПА из `refs/_manifest.json` (`exemplars`) — для флагмана Миллер + конкуренты того же типа (Замесин/Мари/Нагорнова), НЕ bootcamp-компании (SheCodes) и НЕ фреймворки. Фреймворк (Hormozi/StoryBrand) = метод-линза: ОТДЕЛЬНОЙ строкой «метод применён: <какой> → как влияет на элемент», НЕ как образец сравнения. Хук блокирует показ экрана, если в манифесте образец чужого типа / фреймворк-как-образец / нет named-core.

## Процесс
1. Берём экран по порядку структуры (Фаза 3a). Поднимаем его копи (3b) + релевантный research. 🔴🔴 **PER-SCREEN РЕФЕРЕНСЫ — 10 ЭТАЛОНОВ ИМЕННО ЭТОГО БЛОКА (автор, страхуется хуком).** Не «3-4 говносайта», а **10 эталонных конкурентов** того, как этот тип блока (hero / тарифы / кейсы / FAQ-финал / value-stack…) решают топы НАШЕЙ ниши/типа — отдельно от общей доски жанра 2b. По рамке `refs/_scope.json` (Шаг 0 фазы 2). Для каждого:
>    - живой скрин рендера в `refs/<screen>/*.png` (browser-screenshot, не текст WebFetch — ДИЗАЙН только глазами);
>    - запись в `refs/<screen>/_manifest.json`: `{block, target:10, exemplars:[{name,url,screenshot,why_works (≥60: что и за счёт чего работает), niche_relevant (≥20: почему эталон для нас)}]}`.
>
>    **Засчитываются ТОЛЬКО понятые релевантные эталоны** (валидатор `scripts/validate-refs.py` это считает; мусор без разбора не идёт в счёт). **Не нашёл 10** — объяви честный `shortfall {found,reason,searched[≥4 места]}`, и это покажи автору. **Врать (падить случайными сайтами) запрещено — «не можешь найти, скажи».** Прогнать ДО показа концепции: `python3 ~/.claude/skills/website/scripts/validate-refs.py refs/<screen>/_manifest.json --block <screen>` → PASS. **Хук блокирует показ экрана без валидного per-screen манифеста.** Это пруф-база колонки «доказательство» для данного экрана.
2. Раскладываем на элементы. К каждому — функция + пруф + почему (таблица выше).
3. Фиксируем конверсионную задачу экрана + путь взгляда + что отрезали.
4. **Показываем таблицу автору → согласование/правка.** (Это смысловой показ, не пиксели.)
5. Только после апрува стратегии экрана — вёрстка ЭТОГО экрана (Фаза 6) → бенчмарк (Фаза 09).
6. Следующий экран — тем же циклом.

## Anti-patterns
- Сборка пикселей до согласованной стратегии экрана («покажу — потом объясню»).
- Элемент без конверсионной функции (декор ради красоты).
- «Это best practice» без названного эталона/источника.
- Копипаст композиции конкурента без переосмысления функции под наш оффер.
- Стратегия всех экранов разом вместо последовательного согласования.
- Дёрганье элементов по репликам без возврата к единой логике Blueprint.
- **<10 эталонов на экран без объявленного shortfall** (3-4 случайных сайта + «охват есть» = враньё, хук блокирует). Не нашёл — объяви честно, не падь мусором.

## Связь с другими фазами
- **Вход:** структура 3a + копи 3b + визуал-направление 4 + (для hero) Hero-Blueprint из research.
- **Выход:** согласованная экранная стратегия (таблица-доказательство) → улика в `.website-state.json` (`screen_strategy.<N>{approved:true}`) → допуск к вёрстке экрана в Фазе 6.
- **Фаза 6 (build):** строит экран ТОЛЬКО при наличии approved-стратегии этого экрана.
- **Фаза 09 (benchmark):** судит готовый экран против эталона; экранная стратегия — это «техзадание на конверсию», по которому потом сверяем.
