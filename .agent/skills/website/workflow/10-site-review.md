# Фаза 10 — МАКРО-РЕВЬЮ САЙТА КАК СИСТЕМЫ (СТАДИЯ C, до деплоя)

> 🔴 Последняя итерация. Запускается, когда ВСЕ экраны `done` (каждый прошёл Фазу 09 ≥9).
> Проверяет НЕ экраны (это сделано), а САЙТ ЦЕЛИКОМ как одну воронку: межэкранную
> согласованность — дугу, порядок осознанности, аромат, сшивку смысла и дизайна, путь к
> CTA. Рубрика и доказательная база — `references/macro-rubric.md`. Порог — 8 осей ≥9.
> Перекрывает соблазн «все экраны ≥9, значит сайт готов»: локальный оптимум ≠ глобальный.

## Когда запускается
- Вход в СТАДИЮ C: `stage="assembly"`, все `screens[].status == "done"`, собран `index.html`.
- НЕ раньше: пока хоть один экран не `done`, гейт показа сайта блокирует (Фаза 09 по экранам).
- Гейт `website-review-gate.sh` на показе/деплое сайта требует пройденную Фазу 10
  (`.site-review.json` с 8 осями min≥9 + журнал-аудит + CTA-путь) ДОПОЛНИТЕЛЬНО к Фазе 09.

## Закон гейта (как 09, но на уровне сайта)
ЗАПРЕЩЕНО показывать/деплоить собранный сайт без прохода Фазы 10. ЗАПРЕЩЕНО спрашивать
автора «согласован ли сайт между экранами?» — на это отвечает гейт. Не сходится по оси →
чинить по таксономии REMOVE/ADD/REORDER/CONNECT до сходимости, потом показывать готовое.

## Шаг 10.1 — ПОСТРОИТЬ Customer Journey Map (артефакт-якорь)

Прежде чем судить — построить карту пути клиента по сайту. Берётся из РЕАЛЬНЫХ `screens[]`
блокнота (не из головы), одна строка на экран В ПОРЯДКЕ СКРОЛЛА:

| Поле | Что |
|---|---|
| `screen` | имя экрана (точно как в `screens[]`) |
| `awareness` | стадия Schwartz 1-5 (unaware→buying) |
| `role` | роль в воронке (захват/механизм/пруф/оффер/…) |
| `thinks` | что человек думает/чувствует/сомневается здесь |
| `question_raised` | вопрос, который этот экран поднимает (или "") |
| `answered_by` | имя БОЛЕЕ ПОЗДНЕГО экрана, что закрывает вопрос (или "none") |
| `cta` | primary / secondary / none |

Записать в `.site-review.json` (схема — `references/macro-rubric.md`). Это вход для
машинного пола и для судей: карта МЕХАНИЧЕСКИ обнажает разрывы (вопрос поднят — ответа нет;
страх не закрыт перед ценой; два экрана говорят одно; стадия прыгнула назад).

> 🔴 Журнал — НЕ для галочки. Если строишь его честно, половина дефектов осей B/C/F видна
> прямо в таблице ещё до судей.

## Шаг 10.2 — МАШИННЫЙ ПОЛ (детерминированно, ДО судей)

Меряемое не должно проскакивать на вкус. Запустить ПЕРВЫМ:

```bash
# 1) Журнал-аудит: покрыты все экраны · awareness не убывает · нет висячих петель · arc-скелет
python3 ~/.claude/skills/website/scripts/journey-map-audit.py <DIR>
# 2) CTA-путь: все CTA резолвятся, есть рабочее целевое действие (опц. --target /pay)
python3 ~/.claude/skills/website/scripts/check-deploy.py <DIR>/index.html
# 3) Канва: регрессия по склееному сайту против эталона (дрейф токенов/языка между экранами)
node ~/.claude/skills/website/scripts/regression-check.mjs <DIR>/index.html   # если есть baseline
# 4) ПЕРФ-ПОЛ СОБРАННОГО САЙТА (mobile-first скорость загрузки, автор): на склеенном
#    index перф-дефекты копятся (несколько тяжёлых героев/шрифтов/eager-картинок со всех экранов).
node ~/.claude/skills/website/scripts/layout-audit.mjs <DIR>/index.html 390,1280   # exit 1 = перф/макет-дефект
```
Любой красный → чинить ДО запуска судей (как Слой 1 в 09). Гейт всё равно перегонит сам.
🔴 **Перф собранного сайта принуждается на показе/деплое:** хук `website-review-gate.sh` в ветке показа САЙТА сам перегоняет `layout-audit.mjs` на `index.html` (390+1280) и блокирует на HARD-перф-дефектах (render-blocking/FOIT/offscreen-eager) — Финал тоже гейтится по скорости загрузки на мобиле, не только межэкранная согласованность. Advisory-метрики (`weight_kb`/`lcp_ms`) показать автору в Шаге 10.7.

## Шаг 10.3 — 4 АДВЕРСАРИАЛЬНЫХ СУДЬИ (свежие субагенты, НЕ сборщик)

Запустить ПАРАЛЛЕЛЬНО 4 судей (`references/macro-rubric.md` → таблица судей). На вход
каждому: скрины ВСЕГО сайта в порядке скролла + журнал (10.1) + вывод машинного пола (10.2)
+ живой сайт-эталон ТОГО ЖЕ типа (из `refs/_manifest.json`, НЕ фреймворк). Метод (обязателен,
иначе ревью невалидно):
- **pairwise против эталона** того же типа по каждой оси, не абсолютная оценка на вкус;
- **грундинг**: каждый дефект = конкретный экран/стык + правка из таксономии. Без привязки
  не засчитан;
- **2-3 прохода** уточнения;
- свод 4 судей **по ХУДШЕМУ баллу** каждой оси.
- 🔴 **на 390 И 1280** (мобильная воронка проверяется отдельно — порядок/аромат/CTA на мобиле ломаются независимо от десктопа).

Промпт-установка: «Презумпция: межэкранный рассинхрон есть, найди его. Вот воронка-эталон
того же типа целиком, вот наш сайт целиком. По каждой оси своей линзы — балл + дефект с
привязкой к экрану/стыку + правка REMOVE/ADD/REORDER/CONNECT».

## 🔴 Шаг 10.3b — ТЕХНИЧЕСКИЙ АУДИТ САЙТА, счёт /20 (`references/ux-critique-rubric.md` §5)

Отдельный проход ПОСЛЕ судей: он не про воронку и не про вкус, а про то, что 09 меряет
поэкранно и потому не видит накопленного по сайту. Пять измерений, каждое 0-4
(0 системный провал · 1 крупные повторяющиеся · 2 несколько подтверждённых · 3 мелкие
изолированные · 4 связно и намеренно):

1. **Доступность** — контраст, `prefers-reduced-motion` (нужна осмысленная альтернатива, а не
   глобальный `0.01ms`-килл), ARIA-роли и состояния, клавиатурная навигация и порядок табов
   без ловушек, семантика и лендмарки, alt-тексты, формы без лейблов
2. **Производительность** — layout thrashing, дорогие анимации, картинки без lazy,
   `will-change` оставленный в покое, вес бандла, лишние ре-рендеры
3. **Темизация** — захардкоженные цвета мимо токенов, сломанная тёмная тема, значения,
   не обновляющиеся при смене темы
4. **Адаптивность** — фиксированные ширины, тап-таргеты <44×44, горизонтальный скролл на
   узком, поломка при увеличении текста
5. **Целостность реализации** — повторяющиеся срезания углов, дрейф от `Design.md`,
   декоративный или вводящий в заблуждение контент, структура, взаимозаменяемая с чужим
   продуктом. **Детерминированные находки держать ОТДЕЛЬНО от визуального суждения и
   называть ложные срабатывания вслух**

**Полосы итога:** 18-20 Отлично · 14-17 Хорошо · 10-13 Приемлемо · 6-9 Плохо · 0-5 Критично.
🔴 **Вердикт целостности реализации идёт ПЕРВЫМ в отчёте** (выражает ли сайт связную,
специфичную для продукта систему), со ссылками на проверенные улики. Аудит не чинит —
документирует; находки уходят в таксономию 10.4 с severity P0-P3.

## Шаг 10.4 — ИНТЕРПРЕТАЦИЯ → применить таксономию правок

Свести находки в список правок, каждая привязана к ОСИ + ЭКРАНУ:
- **REMOVE** (ось F) — убрать дубль/тормоз;
- **ADD** (C/D/E) — добавить недостающее звено (ответ на петлю, пруф перед ask, скорость);
- **REORDER** (B/D) — переставить экран на свою стадию / пруф перед ask;
- **CONNECT** (A/C/G) — сшить смысловой/визуальный разрыв (сквозная линия, эхо, мостик).

Применить САМ (молча — это качество, не вкус), записать в `fixes_applied`. ⚠️ REORDER/REMOVE
меняют `screens[]` и могут затронуть отдельный экран — после правки прогнать РЕГРЕССИЮ Фазы
09 затронутых экранов (правка сайта не должна сломать экран).

## 🔴 Шаг 10.4b — REORDER/REMOVE: атомарная правка состояния + кап цикла 10↔09 (ревью C2)
REORDER/REMOVE меняют структуру — это НЕ только правка HTML. Делать АТОМАРНО (одним заходом):
- **REMOVE экрана:** убрать из `index.html` + из `screens[]` блокнота + из `journey` маркера + снять его статус (он больше не существует). Иначе журнал-аудит вечно ругается на «фантом/непокрытие».
- **REORDER:** переставить секции в `index.html` И порядок в `screens[]` И в `journey` синхронно (аудит требует journey-порядок == screens-порядок).
- **Статус затронутого экрана:** если REORDER сломал стык / REMOVE сосед — статус экрана СБРОСИТЬ из `done` в `review` (трекер обязан показывать правду, а не врать «done»), прогнать РЕГРЕССИЮ 09 этого экрана до ≥9, вернуть `done`.
- 🔴 **КАП ЦИКЛА 10↔09:** если правка Фазы 10 роняет экран в 09, а доводка 09 снова меняет журнал (пинг-понг), вести СЧЁТЧИК итераций 10↔09. **3 полных круга → СТОП**, не крутить дальше: это структурная развилка (другой порядок экранов / убрать экран совсем), вынести автору ОДНОЙ строкой как реальную развилку, не зацикливаться. (Внутренний кап Шага 10.5 — про оси Фазы 10; этот — про пинг-понг РАЗНЫХ фаз.)

## Шаг 10.5 — ЛУП СХОДИМОСТИ + ФИНАЛЬНАЯ ПАРАЛЛЕЛИРОВКА

```
пересборка → машинный пол (10.2) → 4 судьи параллельно (10.3) → свод по ХУДШЕМУ
повтор, ПОКА ОДНОВРЕМЕННО:
  (1) 8 осей ≥9 (min)      (2) машинный пол чист      (3) каждый экран 09 ≥9 (регрессия)
СТОП по СХОДИМОСТИ, не по числу итераций.
```
Кап здравого смысла: 2 круга подряд режут по одной оси по одной причине → это не «подкрутить»,
а смена решения (другой порядок экранов / убрать экран / иной мостик), не бесконечные правки.

## Шаг 10.6 — Записать маркер-улику (иначе показ/деплой ЗАБЛОКИРОВАН хуком)

После сходимости — записать рядом с `index.html` (helper ниже). 🔴 **Балл по осям пишется
ТОЛЬКО из реального прогона судей.** Гейт `website-review-gate.sh` САМ пересчитывает
`min` по 8 осям и САМ перегоняет `journey-map-audit.py` + `check-deploy.py` на артефакте —
флагу не верит (`feedback_enforcement_machine_reverifies_not_flags`).

```bash
# Записать .site-review.json после сходимости (8 осей + журнал + cores). <DIR> = папка проекта.
# AXES_JSON: 8 осей с баллами. JOURNEY_JSON: строки журнала (с dom_id, привязка к рендеру).
# CORES_JSON: ["ядро в одном слове" от судьи1, от судьи2] — ось A, гейт сверяет совпадение.
python3 - "<DIR>" '<AXES_JSON>' '<JOURNEY_JSON>' '<CORES_JSON>' <<'PY'
import json, sys, os, time
d, axes, journey = os.path.expanduser(sys.argv[1]), json.loads(sys.argv[2]), json.loads(sys.argv[3])
cores = json.loads(sys.argv[4])
need = {"one_big_idea","awareness_ladder","information_scent","persuasion_sequencing",
        "conversion_physics","editorial_cut","canvas_continuity","objection_coverage"}
miss = need - set(axes)
assert not miss, f"нет осей: {miss}"
assert isinstance(cores, list) and len(cores) >= 2, "cores: нужно ядро от >=2 судей"
p = os.path.join(d, ".site-review.json")
json.dump({"ts": int(time.time()), "axes": axes, "journey": journey, "cores": cores},
          open(p, "w"), ensure_ascii=False, indent=2)
# синк в блокнот для трекера
sp = os.path.join(d, ".website-state.json")
if os.path.exists(sp):
    st = json.load(open(sp))
    st.setdefault("site_review", {})
    mn = int(min(axes[k] for k in need))
    st["site_review"]["cross_screen"] = {"axes": axes, "score_min": mn}
    st["site_review"]["score_min"] = mn
    json.dump(st, open(sp, "w"), ensure_ascii=False, indent=2)
print("OK site-review min =", min(axes[k] for k in need))
PY
```
🔴 Любая ПРАВКА `index.html` после этого → маркер устаревает (гейт ловит по mtime). Перепрогон.

## Шаг 10.7 — Что показать автору (готовый сайт + улика)
В показе: журнал пути клиента (открыть как страницу/таблицу) · балл по 7 осям + против какого
сайта-эталона мерил · список применённых правок (REMOVE/ADD/REORDER/CONNECT с привязкой) ·
открытые РАЗВИЛКИ (только реальные авторские) одной строкой. Не «согласован ли сайт?» — а
«сайт сведён, 7 осей ≥9, вот журнал и что сшил».

## Что блокирует хук (Фаза 10, показ/деплой САЙТА)
`website-review-gate.sh` на показе/деплое сайта дополнительно к цепочке Фазы 09 требует:
- `.site-review.json` есть и СВЕЖЕЕ index.html (не правлен после ревью);
- `axes` содержит ВСЕ 7 осей; гейт пересчитывает `min` → <9 = BLOCK (печатает худшие оси);
- гейт САМ перегоняет `journey-map-audit.py` (returncode 3 → BLOCK) — журнал не сходится;
- гейт САМ перегоняет `check-deploy.py` (returncode 3 → BLOCK) — CTA-путь сломан.
Safe-fail: сбой node/парсинга машинного пола не блокирует ложно.

## Anti-patterns фазы
- «Все экраны ≥9 → сайт готов» без межэкранной проверки (главный анти-паттерн).
- Журнал «для галочки» (не покрывает все экраны / висячие петли) — машинный пол ловит.
- Мастер (StoryBrand/Hormozi) как образец бенчмарка вместо линзы — запрещено хуком.
- Дефект, сформулированный про ОДИН экран без «между/после/перед» — это скоуп Фазы 09, верни.
- Балл сайта вписан числом без прогона 4 судей — гейт пересчитывает min, не примет.
- Правка REORDER/REMOVE без регрессии затронутого экрана 09.

## Выход
7 осей ≥9 (min), машинный пол чист (журнал + CTA-путь), регрессия экранов 09 цела, реестр
правок применён → ТОЛЬКО тогда показ/деплой сайта автору.
