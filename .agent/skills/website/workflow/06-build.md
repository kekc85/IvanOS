# Фаза 6 — Сборка кода

**Вход:** структура (Фаза 3) + Design.md с токенами (Фаза 5) + согласованная экранная стратегия (Фаза 4b).
**Цель:** собрать фронт под структуру и токены — ЭКРАН ЗА ЭКРАНОМ, доводя каждый до идеала перед следующим.

## 🔴🔴 ЗАКОН ПОЭКРАННОЙ СБОРКИ (не весь сайт разом — экран за экраном)
Прецедент по решению автора: агент вываливал «весь сайт сразу» как визуальную кашу и дёргал по репликам. автор: «сайт должен не сразу давать экран, а экран → следующий → следующий. После каждого экрана сам ревью, доводишь до идеала. И ДО показа мне, ещё до review, прогоняешь экран бенчмарком против моих практик И против рынка-ниши, чтобы ДОКАЗАТЬ, что экран не хуже того, что уже работает».

**Микро-цикл КАЖДОГО экрана (строго по порядку, повторять для экрана 1, потом 2, …):**
1. **Стратегия экрана (Фаза 4b)** — таблица «элемент → конверсионная функция → пруф best-practice (+ сила доказательства) → почему так». Согласовать с автором. Без апрува стратегии — не верстать.
2. **Сборка ЭТОГО экрана** — через дизайн-скиллы (ниже), density-движок, реальные ассеты. Только этот экран, не весь сайт.
3. **🔴 БЕНЧМАРК экрана (Фаза 09, Шаг 9.2b) — ДО review и ДО показа.** Независимый судья мерит дельту экрана до (а) эталон-набора best-practice и (б) **нишево-рыночного набора** (реальные работающие образцы КОНКРЕТНОЙ ниши/типа лендинга — где такие лендинги/марафоны реально запускаются и конвертят). Цель — мочь ДОКАЗАТЬ цифрой+цитатой, что экран не хуже работающего рынка. См. `references/benchmark-standard.md`.
4. **Self-review/доводка до идеала (Фаза 09)** — закрыть ВСЕ разрывы из бенчмарка сам, пересъёмка, пока экран не на пороге **≥9 по каждому критерию** (вкус + нишевый; шкала уровней — `benchmark-standard.md`). 7–8 = не финал. «До 9 не пропускать». Не показывать полусырое.
5. **Показ экрана автору** — готовый экран + улика бенчмарка (балл + против каких образцов) + закрытые разрывы. Согласование/правка.
6. **Следующий экран** — тем же циклом. Накапливать в одну страницу, проверяя стыки с предыдущими.

Не собирать экран N+1, пока N не прошёл бенчмарк+review и не показан. «Понемногу везде / весь сайт сразу» = брак (закон конвейера `_phases-state.md`).

### 🔴🔴 ПОЛ РЕМЕСЛА + ДЕТЕКТОР СЛОПА (`references/craft-floor.md`) — прогон на КАЖДОМ экране, Шаг 3 микроцикла

## 🔴 Движок ПЛОТНОСТИ дизайна ПО ЭКРАНАМ (не плоский набросок)
Прецедент по решению автора: фон пустой, эффектов нет, реальных вставок нет, секции плоские белые → «у нас нет дизайна, набросок, не верю что скиллы использованы». Вызвать дизайн-скилл ≠ применить вглубь. Тот же приём, что для копи (Фаза 3b density engine), но для визуала:
- **Шаг A — Бенчмарк ВИЗУАЛЬНОЙ плотности (параллельные агенты по скринам конкурентов из Фазы 2).** На каждый блок измерить у конкурентов: фон/атмосфера (градиент-меш / текстура / глубина — НЕ пустой цвет), эффекты (scroll-reveal / parallax / hover / canvas / marquee), **РЕАЛЬНЫЕ вставки** (скрины приложений, мокап телефона, пруфы-стикеры, фото, мокапы), слои и тени. Выход — целевая визуальная плотность на КАЖДЫЙ экран.
- **Шаг B — Дизайн каждого экрана К бенчмарку:** атмосферный фон (не пустой), ≥1 уместный эффект, РЕАЛЬНЫЕ вставки (не абстрактные плейсхолдеры — настоящие скрины/мокапы/фото-cutout), глубина (слои/тени). Реальные ассеты собрать заранее (cutout фото через `rembg`, скрины ТГ/приложений, мокап телефона).
- **🔴 Density-гейт экрана (на каждый):** пустой плоский фон = FAIL · нет реальных вставок (только абстрактные карточки) = FAIL · нет ни одного эффекта = FAIL · «выглядит как wireframe-набросок» = FAIL. Сверять со скрином конкурента бок-о-бок (как L8 visual gate в skill-craft).

## 🔴🔴 ЗАКОН: CSS-КОЛЛИЗИИ КЛАССОВ (грепни ДО именования + префикс по экрану при склейке)
Прецедент по решению автора (×2): класс `.acc`/`.win`/`.card` переопределил чужие стили — рендер сломался, заметил только глазами. Закон:
- **Перед именованием ЛЮБОГО CSS-класса — `grep` по `index.html`** (и по всем уже собранным экранам): имя уже занято → берёшь другое. Не предполагать «уникально» — проверить машинно.
- **При склейке всех экранов в ОДИН `index.html` — префиксовать классы по экрану:** `.hero-card`, `.pricing-card`, `.faq-card` — НЕ голый `.card` (один `.card` на весь файл = коллизия между экранами). Префикс = имя экрана из `screens[]`.
- **Inline-акцент внутри flex-`<li>`** оборачивать в ОДИН `<span>` (иначе `gap` рвёт строку — прецедент с разорванным переносом).
- **Рендер-ревью глазами после КАЖДОЙ правки** до показа (Закон 5 `_phases-state.md`): свежий скрин, смотреть что ничего не перекрыто/не оторвано.

## 🔴 ANTI-PATTERN: AI-OVERPAINT (не генерить поверх сгенеренного)
Прецедент в даты запуска.2026 (аватары каналов): правка AI-картинки вторым проходом GPT → пиксельность/пластик. Закон для любых AI-ассетов экрана:
- **Правка AI-картинки = ЧИСТЫЙ проход с ОРИГИНАЛЬНОГО фото на макс. качестве**, НЕ генерация поверх уже сгенеренной (двойной проход = деградация).
- **Outpaint/расширение полей — через «zoom out»**, НЕ «expand» (Nano Banana).

## 🔴🔴 ЗАКОН MOBILE-FIRST + ПЕРФ (скорость загрузки = гейт, не пожелание)
Распоряжение автора: «самое важное — на мобилке грузиться максимально быстро, лучше чем на компе». Архитектурное решение задано на фундаменте (`00-brief.md` шаг 7), здесь — реализация. Закладывать в КАЖДЫЙ экран при сборке, не «оптимизировать в конце»:
- **Mobile-first вёрстка:** базовые стили — под узкий экран (360/390), десктоп через `min-width`-медиа. Не наоборот.
- **Критический путь лёгкий (быстрый первый рендер на моб):**
  - JS: некритичный `<script>` → `defer`/`async`/`type="module"`; НИКОГДА синхронный `<script src>` в `<head>` (блокирует рендер — машинный пол `render_blocking` блокирует показ).
  - Шрифты: `font-display: swap` на каждом `@font-face` И `&display=swap` в Google-Fonts `<link>` (иначе FOIT — текст-невидимка на медленной сети; машинный пол `font_display` блокирует). Урезать веса/начертания до используемых; `preconnect` к домену шрифтов.
  - Картинки: ниже сгиба → `loading="lazy"` (машинный пол `img_offscreen_eager` блокирует eager-offscreen); LCP-герой — `preload` + `fetchpriority="high"`, НЕ lazy; всегда `width`/`height` или `aspect-ratio` (CLS=0); адаптивные `srcset`/`sizes`; формат webp/avif.
  - Вес под контролем: тяжёлые библиотеки/видео — оправдать или заменить; `weight_kb`/`requests`/`lcp_ms` мерятся в layout-audit (advisory; жёсткий бюджет — `--weight-budget` / `config.md`).
- **Один тикер анимаций** (GSAP на Lenis), всё под `prefers-reduced-motion` (Фаза 7).
- 🔴 **Перф-пол в микроцикле экрана:** Шаг 3 микроцикла (бенчмарк+09) включает прогон `layout-audit.mjs` на **390** — он ловит перф-дефекты и **блокирует показ экрана**, как геометрию/орфаны. Чинить ДО показа. Те же классы перепроверяет хук на показе (самоотчёт не принимается).

## Правила
- Mobile-first, полностью адаптивно (см. ЗАКОН выше — это архитектура каждого экрана, не строчка).
- Tailwind, без инлайн-стилей.
- Контент из Фазы 3 (реальная копи), не lorem ipsum.
- **Учесть эффект-стек концепта (Фаза 4, Шаг 5b).** Если эффект-сигнатура требует canvas/WebGL-героя, scroll-linked, lottie — заложить движок в стек СБОРКИ здесь (`three`/Spline, `gsap` ScrollTrigger, `lottie`), не только Framer в Фазе 7. Реализация моушна — Фаза 7, но зависимость стека учитывается на сборке.

## Уроки (см. references/lessons-learned.md)
- Платные AI-генерации ассетов (Higgsfield/Stitch) — согласовать подход и стоимость ДО запуска (Янтарный: сожгли ~990/1000 кредитов). Кап ретраев: 2 попытки, потом обходной путь.
- Параллельные генерации: 3-4 concurrent + stagger, не больше (17 параллельных → 502/504).
- Cache-bust статичных ассетов: при подмене файла с тем же именем добавлять `?v=<timestamp>`, иначе браузер держит старый из кеша.
- Не доверять субагенту слепо: проверять mapping ассетов после любой подмены.
