# Фаза 2 — Reference-ресёрч (движок «лучшее от всех» → синтез)

**Вход:** бриф (с **типом сайта** из Фазы 0) + банк сырья + **якорь жанра**.

> 🔴 **ЯКОРЬ ЖАНРА (читать ПЕРВЫМ, чтобы не «открывать» планку заново).** Если тип объекта = инфобиз-лендинг (флагман-сейлз / регистрация на марафон / вебинар) — `references/flagship-style-reference.md` = снятая ДНК жанра «премиум инфобиз RU» (реальный флагман автора, 10 экранов: капс-типографика синим, фото-cutout с летящими иконками, GIF-мокапы, стикеры-наклейки, 3D-деньги, тариф-таблицы, value-stack). Это НЕ опционально и НЕ заменяет ресёрч — это стартовая планка, ниже которой опускаться нельзя. Прецедент по решению автора: агент проскочил эту фазу, выдал приглушённый «Stripe-light» и «удивился» реальному эталону — улика, что research не делался. Под другой тип объекта — свой жанровый якорь (искать в ресёрче, не выдумывать).
>
> 🔴 **ЗАКОН ЭТАЛОНА .** Если у автора ЕСТЬ собственный доказавший себя объект НАШЕГО типа (его реальный флагман/сайт — напр. `flagship-style-reference.md` или присланный сайт), то ИМЕННО ОН — **первичный эталон СТРУКТУРЫ (порядок и состав экранов) И УРОВНЯ**, читается ПЕРВЫМ и обязателен к закрытию фазы. Конкурент (Мари и любой) при этом — **Пул B = только отдельные ПРИЁМЫ**, сверяемые с эталоном автора, не источник порядка. **ЗАПРЕЩЕНО:** называть конкурента «эталоном»; брать у конкурента ПОРЯДОК / состав экранов; титуловать структуру «из разбора <конкурента>». Прецедент: структуру флагмана собрали «из разбора Мари» и поставили value-stack ПЕРЕД ценой — против реального флагмана автора, где value-stack стоит ЗА тарифами (экран 10). **Само-чек перед Фазой 3:** «порядок и состав экранов взят из эталона АВТОРА, а не конкурента?» Нет → фаза не закрыта.
> 🔴 **ЗАКОН «МЕТОД ≠ ОБРАЗЕЦ» .** Бенчмарк-ОБРАЗЕЦ = живой САЙТ того же ТИПА, что строим. МЕТОД/фреймворк (Hormozi Value Equation, StoryBrand, Cialdini, AIDA, JTBD) = **линза**, применяется в копи/стратегии (Фазы 3/4b), но **НИКОГДА не кладётся в reference-доску и не считается образцом бенчмарка**. Прецедент: бенчмарк экрана выдан против Hormozi/StoryBrand (это методы, не сайты) + SheCodes/Hack Reactor (bootcamp-КОМПАНИИ — чужой тип, не «экспертный личный бренд») + пропущен Миллер (прямой эталон жанра) = брак. Тест перед внесением в доску: «это живой сайт, который можно открыть, ТОГО ЖЕ типа?» Нет → это метод (в `methods`, не в `exemplars`) или чужой тип (reject).

> 🔴 **МАНИФЕСТ ОБРАЗЦОВ `refs/_manifest.json` — машинная улика фазы 2b (страхуется хуком `website-review-gate.sh`).** Без него и при нарушениях показ экрана/сайта физически блокируется. Схема (v1.6 — добавлены поля КАЧЕСТВА: каждый образец обязан быть ПОНЯТ и доказанно РЕЛЕВАНТЕН, иначе валидатор его не засчитает):
> ```json
> {
>   "site_type": "<тип из брифа Фазы 0, напр. expert-personal-brand-paid-course>",
>   "named_core_required": ["Миллер"],          // обязательные эталоны жанра (для флагмана — Миллер; авто-дефолт если тип = курс/флагман)
>   "min_exemplars": 3,                            // минимум образцов нужного типа (= дефолтная цель качества, если board_target не задан)
>   "board_target": 10,                            // 🔴 цель КАЧЕСТВЕННОГО охвата доски; поднимает планку выше min_exemplars (хук считает квалифицированные ВСЕГДА)
>   "exemplars": [                                 // ТОЛЬКО живые сайты того же ТИПА
>     {"name":"Миллер","url":"https://example-etalon.ru/training","type":"expert-personal-brand-paid-course","funnel_layer":"flagship","role":"exemplar","screen":"program",
>      "screenshot":"miller-program.png",          // 🔴 файл скрина в refs/ — должен реально лежать на диске
>      "why_works":"≥60 симв: что ИМЕННО в нём работает и за счёт чего (механика, не «красиво»)",
>      "niche_relevant":"≥20 симв: почему это ЭТАЛОН именно для нашей ниши/типа/слоя воронки"}
>   ],
>   "methods": [                                   // фреймворки-линзы — отдельно, НЕ образцы
>     {"name":"Hormozi Value Equation","role":"method","applied_in":"04b/03"}
>   ],
>   "shortfall": {"found":4,"target":10,"reason":"почему эталонов меньше цели","searched":["где искал ≥4 мест"]}  // ЕСЛИ квалифиц.<target — объявить ЧЕСТНО
> }
> ```
> Хук BLOCK, если: нет манифеста · образец `type≠site_type` (чужой тип) · фреймворк в `exemplars` (метод-как-образец) · образец без `url` · нет named-core (для флагмана нет Миллера) · образцов нужного типа < `min_exemplars`. **+ ВСЕГДА: `scripts/validate-refs.py` считает КВАЛИФИЦИРОВАННЫЕ образцы (url + разбор `why_works`≥60 ИЛИ legacy-`note`≥60 + релевантность `niche_relevant`≥20 ИЛИ `note`); недобор цели (`board_target`/`min_exemplars`) без честного `shortfall` = FAIL (это и есть «3-4 говносайта + враньё про охват»).** На доске скрин не у каждого образца (папку скринов проверяет хук отдельно); per-screen — скрин обязателен у каждого. Заполнять по ходу Шага 3, финализировать в Шаге 4.
>
> 🔴 **ЗАКОН КАЧЕСТВА/ЧЕСТНОСТИ ОХВАТА (автор — «ты берёшь 3-4 говносайта, не из ниши, не понимаешь их, и врёшь на каждом шагу»).** Образец засчитывается, ТОЛЬКО если он (1) живой URL, (2) скрин рендера лежит на диске, (3) РАЗОБРАН — `why_works` объясняет механику, (4) доказанно релевантен нашей нише/типу/слою воронки. Мусор-добивка без разбора НЕ считается. Не набрал цель эталонов → **объяви `shortfall` {found, reason, searched[≥4 места где искал]} — и ЭТО показывается автору вместо вранья.** «Не можешь найти — скажи, но не ври» (прямое распоряжение). Проверка: `python3 ~/.claude/skills/website/scripts/validate-refs.py <DIR>/refs/_manifest.json` — прогнать ДО показа, дотянуть до PASS.

**Цель фазы — НЕ «разобрать 3-5 сайтов».** Цель: широко и глубоко понять лучшее, что есть **по трём осям — структура, дизайн, смыслы**, и принести автору **синтез: идеальный вариант, который берёт лучшее от всех**. Ресёрч ПИТАЕТ сборку. Если строю из головы, игнорируя ресёрч, — скилл бессмыслен .

> 🔴 **Эта фаза проваливалась целиком.** Корень — *лень + не сверяю с определением + заявляю непроверенное*. Reference = разбор ЖИВЫХ страниц, которые реально открыл, а не пересказ досье и не 3 URL из одного файла.

## Три оси, которые ресёрч ОБЯЗАН вынуть (всё, целиком)

Выход всего скилла = идеальная страница. Значит из референсов забираем три слоя, не один:
1. **Структура** — порядок и состав секций, что ведёт к целевому действию.
2. **Дизайн / визуал** — как это выглядит у лучших (вход в дизайн-концепт Фазы 4: лейаут, типографика, тон, приёмы).
3. **Смыслы и формулировки** — какие смыслы/офферы/слова работают и **у кого** их берём (атрибуция обязательна).

### 🔴 Ось 2 (дизайн) захватывается В ДИНАМИКЕ, не одним скрином
Прецедент по решению автора: живой герой Миллера (мозг — связи возникают, узлы перебегают) агент изучал по ОДНОМУ статичному скриншоту → не понял, как он на самом деле движется, и не смог воспроизвести («нужно на видео снять, а не один скриншот»). Правило: для каждого референса с **живым/анимированным** элементом (canvas-герой, scroll-reveal, parallax, marquee, hover) захватывать ДВИЖЕНИЕ:
- запись скролла страницы (видео) ИЛИ серия кадров (top → mid → bottom + наведения), не один кадр;
- описать СЛОИ и МЕХАНИКУ эффекта (из чего собран, что и как анимируется), а не «там красивый мозг»;
- это вход в эффект-сигнатуру Фазы 4 (берём ПРИНЦИП движения, реализуем под свою метафору — не клон). Эффекты-арсенал: `references/effects-arsenal.md`.
Статичный скрин динамического героя = неполный референс → дизайн-ось не закрыта.

## Два пула референсов

**Пул A — ТОТ ЖЕ ТИП, что строим (обязательный фундамент).**
Какой тип в брифе Фазы 0 — такие референсы и фундамент: продуктовый лендинг → продуктовые лендинги; контент-хаб → контент-хабы; SaaS-фронт → SaaS-фронты; регистрация на событие → страницы регистрации на событие; и т.д. Это единственный нормальный фундамент по структуре и смыслам. Объект другого типа в фундамент не берём . Тип каждого кандидата сверять ДО разбора, отсеивать по типу.

> 🔴 **ГОЛОВА Пула A = СОБСТВЕННЫЙ объект автора (если есть).** По ЗАКОНУ ЭТАЛОНА выше: когда у автора есть свой доказавший себя объект нашего типа — он первый в Пуле A и единственный источник ПОРЯДКА/состава экранов. Конкуренты в этом случае — НЕ фундамент структуры, а Пул B (приёмы/смыслы/копи), сверяемые с эталоном автора. Конкуренты-фундамент по структуре берём ТОЛЬКО когда у автора своего объекта этого типа нет.

> 🔴 **ДВЕ ОСИ ОТБОРА В ПУЛ A (обе обязательны, прецедент по решению автора ×2 — разнос). Кандидат входит в фундамент, ТОЛЬКО если ДА по обеим:**
>
> **Ось 1 — ЭТО НАШ КОНКУРЕНТ?** Пул A строится из РЕАЛЬНЫХ конкурентов проекта (из досье запуска `0-Конкуренты-Deep-Dive.md` / `2-Конкуренты.md` / landscape), а НЕ из случайных страниц того же типа, выпавших в поиске. Generic-марафон не из ниши (Skillbox AI, Excel-марафон) — это НЕ фундамент, максимум Пул B-форма. **Обязательный чек перед закрытием фазы: «Я открыл фронт-энд ГЛАВНОГО конкурента ниши? Прошёлся по ВСЕМУ seed-списку конкурентов, а не по первым попавшимся?» Пропустил главного (прецедент: проглядел марафон Миллера) → фаза НЕ закрыта.**
>
> **Ось 2 — ЭТО НАШ ТИП ВОРОНОЧНОГО СЛОЯ?** Внутри ниши у конкурента обычно 2 разных объекта: (а) **бесплатный / low-ticket ФРОНТ-ЭНД** (бесплатный марафон, вебинар, дешёвый практикум 1-2К — лид-магнит, кормит воронку) и (б) **платный ФЛАГМАН** (интенсив/курс 40-200К). Если мы строим регистрацию на бесплатный марафон — фундамент = ТОЛЬКО фронт-энды конкурентов (а), флагманы (б) в фундамент НЕ идут . Флагман держим на ВТОРИЧНОЙ полке (ниша-копи/кейсы/структура), но не как тип-фундамент. Для КАЖДОГО конкурента спросить: «я нашёл его ФРОНТ (наш слой), а не его флагман?».
>
> Таблица-разметка обязательна: для каждого кандидата — `конкурент? (да/нет)` × `слой воронки (фронт/флагман)` × `тип страницы`. В фундамент идут только `конкурент=да + слой=фронт + тип=наш`.

**Пул B — кросс-ниша, топ-лендинги (вдохновение по форме).**
Лучшие лендинги из ЛЮБЫХ ниш — для **структуры и дизайна**, не обязательно своя ниша. Берём «как сделана сильная страница» вообще. Для **смыслов** — осторожно: смыслы берём в основном из Пула A (свой тип/ниша), форму можно подсматривать шире.

## Охват (минимум)

- **≥10 референсов суммарно**, с перевесом в Пул A. Меньше — это не ресёрч.
- RU И зарубеж по основному/целевому рынку проекта (из брифа Фазы 0 / `config.md`): EN-референсы под EN-аудиторию, RU — под RU. (Для автора зарубеж — основной рынок с июня 2026.)

## Что управляет ресёрчем (рамка)

Драйвер поиска — **ТИП объекта из брифа Фазы 0** (для текущей задачи это регистрация на марафон; под другую задачу — другой тип), а НЕ список записанных конкурентов. Задача ресёрча: **сам пойти и найти ≥10 живых страниц нужного типа**, где бы они ни были. Записанные конкуренты — лишь **одно из сем имён, не граница и не гарантия нужного типа**: у конкретного эксперта может не быть страницы нашего типа — тогда не подгонять и не выдавать его страницу другого типа за референс, а идти искать тех, у кого страница нужного типа есть (в нише, в соседних, в кросс-нише). Не анкериться на «записан / не записан» — вопрос всегда «это страница нужного ТИПА?».

## Шаг 0 — SCOPE: определить, КТО считается эталоном (ДО любого поиска)

> 🔴 Прецедент по решению автора: «scope research не определяешь, не понимаешь — для флагмана берёшь хрень от марафонов и конкурентов вообще не из наших ниш». Корень: агент шёл искать, не определив рамку, и тащил первое похожее. Лечение: СНАЧАЛА письменно зафиксировать рамку поиска, ПОТОМ искать.

До веб-поиска записать `<DIR>/refs/_scope.json` — это рамка, по которой потом отсеиваем кандидатов:
```json
{
  "site_type": "<тип объекта из брифа Фазы 0>",
  "niche": "<наша ниша: напр. вайбкодинг/вайбмаркетинг RU>",
  "markets": ["RU"],                       // целевые рынки из брифа/config
  "funnel_layer": "<наш слой: фронт-энд / флагман>",
  "etalon_definition": "эталон = живой сайт ТОГО ЖЕ типа+ниши+слоя, доказавший себя (трафик/деньги/имя), а НЕ случайный похожий лендинг",
  "seed_names": ["<главные конкуренты ниши из досье + собственный объект автора>"],
  "screen_blocks": ["hero","pricing","cases","faq-final","value-stack"],  // типы блоков под per-screen референсы
  "per_screen_target": 10
}
```
**Критерий эталонности (все ДА, иначе кандидат — НЕ эталон):** тот же ТИП страницы · та же/смежная НИША · тот же СЛОЙ воронки · доказал себя (не «просто существует»). Generic-марафон не из ниши, конкурент из чужой ниши, bootcamp-компания — мимо рамки, в фундамент не идут. Рамку определил → дальше ищешь ПОД НЕЁ, а не «что выпало».

## Шаг 1 — Семена: поднять ВСЕ записанные источники (ДО веба)

Не сочинять список заново и не скимить один файл . Поднять `glob`-ом ВСЁ, что уже лежит по проекту — это стартовый набор ИМЁН и смыслов, не финальный список референсов:
- Папка текущего запуска/проекта: разборы конкурентов, Battle Card, карта смыслов (имена файлов — из конкретного запуска; для запуска вайбкодинг-RU это `0-Конкуренты-Deep-Dive.md`, `2-Конкуренты.md`).
- `.business/growth/materials/Свёртки/эксперты/` — свёртки конкурентов.

⚠️ **Эти файлы — КОНТЕНТ-досье (прогревы/оффер/позиционирование), а не страницы регистрации.** Дают игроков и их смыслы, но НЕ заменяют разбор лендингов и НЕ ограничивают поиск ими.

## Шаг 2 — Активный поиск страниц нужного ТИПА (research делает сам)

1. По каждому игроку-семени **искать в вебе его реальную страницу нужного типа** (тип из брифа Фазы 0; для текущей задачи — лендинг регистрации на марафон/бесплатник, не главную и не платный сейлз). Нет страницы нужного типа у него → он не идёт в Пул A, не подгонять.
2. **Активно догуглить незаписанных:** кто в нише и соседних нишах делает страницы нужного типа → их сайты (Пул A). Список конкурентов тут расширяется ресёрчем, не равен записанному.
3. Добрать топ-лендинги вне ниши для формы/структуры (Пул B).
4. Каждого кандидата пометить: Пул A или B + тип. Цель — ≥10 живых страниц верного типа.

## Шаг 3 — Разбор живых страниц (только то, что реально открыл)

> 🔴 **ДИЗАЙН-ось снимать ТОЛЬКО со СКРИНШОТА реального рендера (browser/Playwright `browser_take_screenshot fullPage`), НЕ из текста WebFetch.** WebFetch конвертит в markdown и про визуал ВРЁТ: фон/палитру/стиль угадывает по обрывкам CSS. Прецедент по решению автора: WebFetch описал лендинг Миллера `example-etalon.ru` как «светлый молочно-кремовый», реальный рендер — ТЁМНАЯ тема (почти чёрный фон, оранжевый акцент). Структуру/смыслы можно с WebFetch, но **дизайн = только глаза по скрину**. Скрин обязательно открыть себе (Read) для разбора И показать автору (`open`).

1. **Каждую страницу реально открыть** (WebFetch для структуры/смыслов + **browser-screenshot для дизайна**) и разобрать по трём осям: структура секций → дизайн/визуал (со скрина) → смыслы и формулировки + что ведёт к целевому действию.
2. **Описывать СТРОГО то, что видно на ЭТОЙ открытой странице.** Каждый тезис — с source-tag: «открыл `<URL>` → увидел X».
