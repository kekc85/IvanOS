# website — процесс создания сайта (смысл → форма)

> Исполняемый end-to-end процесс. Заменил пассивный план `plans/2026-05-29-website-creation-process.md` (контент переехал сюда). Применяется к ЛЮБОМУ сайту: лендинг / промо / SaaS-фронт / артефакт-страница / многостраничник.

## Главный принцип

**Сначала смысл, потом форма.** Дизайн обслуживает структуру и оффер, а не наоборот. Красивый макет без структуры и целевого действия — пустышка. К визуалу НЕ переходим, пока не готовы структура и контент (HARD GATE после Фазы 3).

> 🔴 **ПРАВИЛО №1 (CLAUDE.md): идти до результата, не возвращаться с пустыми вопросами.** Внутри этого процесса гейты (микро-гейт 3a, HARD GATE 3→4, выбор визуала Фазы 4) — это места реальной развилки. Между ними НЕ дёргать автора вопросами «продолжать?/идём дальше?» — двигать фазы до следующего гейта и приходить с готовым результатом фазы. См..

Процесс — два блока:
- **Блок 1 — смысл (Фазы 0-3):** бриф → интервью → reference → структура. Без визуала вообще.
- **HARD GATE**
- **Блок 2 — форма и код (Фазы 4-8):** визуальное направление → токены → сборка → анимации → запуск.
- **Self-review-ГЕЙТ (Фаза 09)** — перед каждым показом автору.

## 🔴 TURNKEY-КОНТРАКТ (почему этот скилл существует именно так)

Источник: лендинг воркшопа по решению автора потребовал ~50 кругов правок. Разбор показал — дело НЕ в нехватке правил (их добавили), а в том, что правила были **пассивными**: агент нёс автору сырьё и спрашивал «это тот уровень?». Контракт скилла: **по одной команде `/website` автор получает сайт уровня, который раньше достигался 50 кругами — без этих кругов.** Это держится на пяти механизмах (детали — `references/lessons-learned.md` корневой диагноз):

1. **Бар качества зашит явно: Awwwards / Миллер-tier.** Не «прилично», а «выглядит как премиум-продукт, а не как нейросеть собрала». Этот бар — цель рубрики 4.2 и порога гейта 09.
2. **Self-review-гейт (Фаза 09) — блокирующий, перед КАЖДЫМ показом. СТРАХУЕТСЯ ХУКОМ.** Свежий критик-агент по скринам живого рендера, порог ≥8/10 на каждый экран и ноль FAIL → запись маркера `.self-review.json`. Хук `website-review-gate.sh` (PreToolUse Bash) **физически блокирует показ автору (`show-screen.py <рендер>` — кликабельная VS Code-ссылка, ИЛИ legacy `open`) без свежего маркера с порогом ≥8** — обойти гейт нельзя, не «забудешь». **ЗАПРЕЩЕНО спрашивать автора «это высочайший уровень / всё ли идеально?»** — на это отвечает гейт, а не автор. Не идеально → чинить, потом показывать готовое.
3. **Реестр открытых правок** в `tasks/projects/<site>.md` (таблица: правка · статус · проверена-в-рендере). Каждая инструкция автора логируется и закрывается с проверкой в свежем рендере — ничего не теряется между кругами (прецедент: «я же говорил эти правки, почему не внедрил?»). Сверять на шаге 9.4 перед показом.
4. **Поведенческий закон процесса (Правило №1 внутри website):** «доведи до высочайшего уровня» = САМ выведи, что для этого нужно (картинки/ассеты/скиллы/эффекты), и сделай. ЗАПРЕЩЕНЫ возвраты с вопросами «какие картинки накидать? / какие скиллы? / это тот уровень?» — это перекладывание мышления на автора . Автор согласовывает ТОЛЬКО реальные бизнес-развилки (нейминг, состав тарифов, фактура, доход публиковать или нет), а не отлавливает брак и не доделывает за агента.

5. **Конвейер фаз с уликами — против саботажа длинного процесса. СТРАХУЕТСЯ ХУКОМ.** Источник: по решению автора — флагман собрался из головы мимо reference-фазы (агент «удивился» реальному эталону автора = улика, что research не делался). Корень — скилл длинный, агент сворачивал его в один прыжок к финалу, «делая понемногу везде». Лечение: **скилл идёт ПО ПОДФАЗАМ, по очереди; в каждую вкладываешься на 100%; каждая подфаза пишет улику в `.website-state.json`; показ финала автору хук `website-review-gate.sh` пропускает ТОЛЬКО при полной цепочке** (референс-доска 2b на диске + структура 3a согласована + критик 09 ≥8) — прыгнуть в код мимо ресёрча/структуры физически нельзя. **Модель показа (согласовано с автором):** машина проверяет проверяемое молча (2a/2c/5/6/7/09 — улика на диске), человек судит вкус/смысл показом (~6 касаний: бриф → референс-скрины 2b `open` → структура 3a → копи 3b → визуал 4 → финал). **Закон против саботажа:** подфаза либо ПОЛНОСТЬЮ сделана с уликой, либо не начата — «понемногу везде» = брак. Полная карта подфаз, helper записи улик и точные чекпоинты — `workflow/_phases-state.md` (читать ПЕРВЫМ при запуске).

## Когда применять

Триггеры: «сделай сайт», «собери лендинг», «нужен сайт под X», «построй страницу под продукт», «лендинг для запуска», «build a site/landing», `/website`, любой запрос спроектировать/собрать веб-страницу.

**Не применять** для: правки одного компонента в уже собранном сайте (это прямая работа в коде через frontend-design); видео/каруселей/постов (свои skills).

## Workflow (progressive disclosure)

> 🔴 **ЧИТАТЬ ПЕРВЫМ: `workflow/_phases-state.md`** — конвейер подфаз, файл-состояние `.website-state.json`, helper записи улик, модель показа (что молча, что ✋ автору). Скилл идёт ПО ОДНОЙ подфазе, с уликой на диске; показ финала хук пропустит только при полной цепочке (2b+3a+критик≥8).

> 🔴🔴 **КОНТРАКТ ВЫВОДА — КАЖДЫЙ ответ по сайту = ДВА ЛАГЕРЯ (автор):** (1) **РАБОТА** — что обсуждаем/делаем по текущей подфазе; (2) **ТРЕКЕР ФАЗ** в конце ответа — чек-лист «где мы / что ✅⏳⬜ / какой экран / чего ✋ жду», **генерится машиной из диска** (`python3 ~/.claude/skills/website/scripts/phase-tracker.py "<DIR>"`, вставить вывод дословно), НЕ руками. Зачем: автор диска не видит (телефон) → трекер из диска = детектор схлопывания фаз, соврать «мы дальше» нельзя. Порядок хода: работа → записал улику helper'ом → прогнал трекер → ответ = <твой-продукт> 1 + <твой-продукт> 2. Гарантия — Stop-хук `website-tracker-gate.sh` (нет маркера `ТРЕКЕР ФАЗ` в активной сессии → BLOCK). Полный закон — `workflow/_phases-state.md` (раздел «КОНТРАКТ ВЫВОДА»).

### ⚡ Как работает скилл (краткая карта)

```
ЭТАП 1 — ФУНДАМЕНТ (1 раз): Blueprint(00b: ДНК+факты-канон) → бриф → интервью → референс → структура(=список экранов) → общий стиль
ЭТАП 2 — ЦИКЛ ПО ЭКРАНАМ: каждый экран прогоняет ВСЕ подфазы по порядку →
         РЕСЁРЧ(10 эталонов блока, сам, ПЕРВЫМ) → концепция ✋ → копи ✋ → дизайн ✋ →
         → сборка(сам) → 3 слоя(сам) → готовый экран ✋
         экран №1 целиком → №2 целиком → … → №N.  (НЕ часть подфаз, НЕ все экраны разом)
         🔴 РЕСЁРЧ — первая подфаза каждого экрана, не пропускать (трекер держит её видимой фазой)
ЭТАП 3 — СБОРКА: все экраны → сайт → Фаза 10 макро-ревью (сайт как система, 7 осей) → деплой
```
✋ = СТОП-показ автору, без «ок» дальше не идёшь. Полная карта + ответы на частые вопросы — `workflow/_phases-state.md` (читать первым).

### Две стадии + два входа (модель v1.4)

Скилл один, работает на ДВУХ уровнях и сам выбирает стадию по блокноту `.website-state.json` (полная карта стадий, структура блокнота и helper'ы — в `_phases-state.md`):

- **СТАДИЯ A — САЙТ (один раз):** фазы **00b→3** (🔴 Blueprint = бренд-ДНК lock + факты-канон с source-tag · бриф · интервью · reference · структура=карта экранов) + единый визуальный язык 4→5 (визуал-направление · токены → `Design.md`). Фундамент на весь сайт. **Стадия A начинается с 00b — НЕ с брифа** (ДНК+факты лочатся первыми, чтобы визуал/копи не выдумывались заново). Выход: `Design.md` (с запертой ДНК) + факты-канон + массив `screens[]` в блокноте.
- **СТАДИЯ B — ЭКРАН (цикл, по одному; СО СТОПАМИ):** каждый экран = мини-проход с согласованием смысловых подфаз. Микроцикл: **РЕСЁРЧ** (10 эталонов блока, скрины+манифест `refs/<экран>/` — сам, ПЕРВЫМ, ДО концепции) → `concept` (раскладка ✋СТОП) → `copy` (копи ✋СТОП) → `design` (визуал ✋СТОП) → `build` (сборка — сам) → `review` (3 слоя ≥9 — сам, молча) → `done` (✋ показ экрана). 🔴 НЕ собирать и НЕ показывать финал экрана, не согласовав concept/copy/design — хук блокирует показ без них. 🔴 **Ресёрч — ОТДЕЛЬНАЯ ВИДИМАЯ подфаза в трекере** (⬜/⏳/✅), не хвост-индикатор: «эталоны нет» при статусе ≥concept = проскочил ресёрч, трекер палит это строкой «СЕЙЧАС: ⚠️ РЕСЁРЧ НЕ СОБРАН» (автор: «часто пропускаешь экран с ресёрчем и обманываешь»).
- **СТАДИЯ C — СБОРКА (финал):** все экраны `done` → собрать `index.html` → **Фаза 10 — макро-ревью САЙТА как системы** (`workflow/10-site-review.md`): межэкранная согласованность (сайт = воронка, не сумма экранов). Customer Journey Map → машинный пол (journey-map-audit + check-deploy) → 4 судьи по 7 осям (one_big_idea/awareness_ladder/information_scent/persuasion_sequencing/conversion_physics/editorial_cut/canvas_continuity, `references/macro-rubric.md`) → REMOVE/ADD/REORDER/CONNECT до сходимости → 08 деплой. 🔴 Горизонтальная ось, НЕ дублирует per-screen Фазу 09. Гейт деплоя/показа сайта требует `.site-review.json` (7 осей min≥9) и сам перегоняет машинный пол.

**Два входа (автор не выбирает «какой скилл» — всегда `/website`):**
- `/website` — полный оркестратор: блокнот пуст / СТАДИЯ A не закрыта → СТАДИЯ A; есть `pending`-экраны → продолжить СТАДИЮ B; все `done` → СТАДИЯ C.
- `/website screen <имя>` («доработай экран X») — заходит ТОЛЬКО в микроцикл одного экрана. Требует завершённой СТАДИИ A (есть `Design.md` + `screens[]`).

**Показ (исправлено по решению автора — НЕ «hero + дальше сам»):** на КАЖДОМ экране 4 показа автору ✋ — концепция · копи · дизайн · готовый экран. Между ними СТОП: не двигаться к следующей подфазе без апрува текущей. Сборку кода и 3 слоя проверки делаю сам, молча (это качество, не вкус — автора не дёргать). **Носитель показа = `scripts/show-screen.py <render>` — печатает кликабельную VS Code-ссылку в чат (тык → рендер в окне VS Code, без браузера), НЕ `open` (автор; деталь — `workflow/_phases-state.md`).** Хук `website-review-gate.sh` физически блокирует показ экрана (`screen-<name>.png|html`) через ЛЮБОЙ носитель (show-screen.py или legacy open), если `status∉{review,done}`, `score<9` ИЛИ в `approvals` нет concept+copy+design; показ сайта-финала — вся цепочка + ВСЕ экраны `done`. Это машинный стоп против «собрал экран и сразу показал финал».

Каждая фаза — отдельный файл в `workflow/`. Идти строго по порядку. Каждая фаза имеет вход, шаги, выход + **улику в `.website-state.json`**. Следующая фаза не начинается без выхода предыдущей.

```
БЛОК 1 — СМЫСЛ
00b-blueprint.md  → 🔴 СТАДИЯ A СТАРТ: Blueprint — запертый бренд-ДНК (Design.md DNA из РЕАЛЬНОГО билда) + факты-канон в `blueprint.md` с source-tag (доход/ученики/кейсы/статус: подтверждено-экспертом | внешний-пруф | .business-черновик)
00-brief.md       → бриф: тип / цель / целевое действие / ЦА / оффер
01-interview.md   → сбор реального сырья (факты/боли/дифференциация), без выдумок
02-reference.md   → ресёрч-движок: ≥10 живых страниц того же ТИПА + кросс-ниша → СИНТЕЗ «идеал» по 3 осям (структура/дизайн/смыслы)
03-structure.md   → 3a концепция+раскладка экрана → МИКРО-ГЕЙТ → 3b копи (post/longform + humaniser)

═══ МИКРО-ГЕЙТ 3a→3b: раскладка экрана утверждена автором? НЕТ → копи НЕ писать ═══
═══ HARD GATE 3→4 (см. workflow/03-structure.md финал) ═══
структура + копи в регистре типа сайта утверждены? НЕТ → к Фазе 4 не переходить

БЛОК 2 — ФОРМА И КОД
04-visual.md      → визуальное направление: режим поверхности + 7 кандидатов из мира ЦА (visual-world.md) → Stitch ИЛИ frontend-design (реш. правило) + design-taste-frontend (анти-slop концепт) + emil-design-eng (моушен-сигнатура 5b) → контракт направления
05-tokens.md      → ui-ux-pro-max: палитра/шрифты/UX + ремесленный пол токенов (refine-playbooks §5-6) → Design.md
06-build.md       → 21st.dev + frontend-design + design-taste-frontend + ПОЛ РЕМЕСЛА и 59 правил (craft-floor.md) (+ stitch-loop) → React+Tailwind
07-motion.md      → motion/gsap/three + emil-design-eng + 10 непреложных и физика Apple (motion-standards.md) + prefers-reduced-motion
09-self-review.md → 🔴 БЛОКИРУЮЩИЙ self-review-гейт критиком ПЕРЕД КАЖДЫМ показом (per-screen)
10-site-review.md → 🔴 ФАЗА 10: макро-ревью САЙТА как системы (СТАДИЯ C, межэкранно, 7 осей)
08-launch.md      → запуск, проверка на размерах, деплой, проверка конверсии
```

> 🔴 **`09-self-review.md` — это не «последняя фаза», а ГЕЙТ, который прогоняется ПЕРЕД ЛЮБЫМ показом автору** (первый показ, каждая итерация, финал). Свежий критик-агент скринит живой рендер → балл по каждому экрану → порог ≥8/10 и ноль FAIL → чинить до порога → только потом показ. Это главный механизм против 50 кругов правок.

НЕ «не доверять вообще» — для риск-фактов подтверждать.** |

## Решающее правило Фазы 4 — Stitch vs frontend-design

- **Stitch включаем** когда: новый сайт с нуля, визуал не определён, важно увидеть макеты до кода, новичок/клиент выбирает глазами.
- **Сразу frontend-design** когда: визуал понятен / есть Design.md или бренд-гайд / редизайн / мелкая страница.
- **Экономия квоты Stitch** (внешняя бесплатная квота Google, легко спалить): один заход на проект, доводка голосом на canvas, правки кода через Claude Code, не возвратом в Stitch.

**Приём «роль дизайнера/бренда» (быстрое визуальное направление, забрано у Мари/ЛАБС):** при первом промпте на визуал (и в Stitch, и в frontend-design) задавай ИИ роль конкретного дизайнера или бренда вместо абстрактных прилагательных — `«Ты — Джонни Айв, создай <артефакт>»` / `«в стиле дизайн-команды Tesla / Four Seasons / Ferrari»`. Личность/бренд несут целостный визуальный язык (типографика, ритм, воздух), и направление получается за один проход, без перебора 5 вариантов «минималистично/премиально». Подбирать бренд под нишу клиента (люкс-услуга → Four Seasons, технологичный продукт → Tesla). Это техника ВНУТРИ Фазы 4, не замена решающему правилу выше.

## Anti-patterns

- 🔴 **Пропуск ДИЗАЙН-подфаз под «сделай весь сайт сейчас» + фабрикация маркеров ** — собрать сайт руками HTML/CSS, проскочив Stitch / ui-ux-pro-max / frontend-design / design-taste-frontend / motion / emil-design-eng, а `.self-review.json`/`.site-review.json`/`screens[].status=done`/`refs/_manifest.json` ВПИСАТЬ РУКАМИ ради прохода хуков. Итог = слоп (дефолтные шрифты, нет вкус-слоя, не workshop-tier) + ЛОЖНЫЙ отчёт «прошёл все фазы 9/10». ЗАПРЕЩЕНО: (1) пропускать дизайн-фазы даже под «весь сайт сразу/демо/быстро» — они и дают красоту; (2) писать любой phase/review-маркер, не выполнив фазу реальным вызовом подскилла с уликой. Маркер не сделан = фаза не сделана: доделываю, не подделываю.,
- **Прыжок в форму до смысла** — начать с дизайна/Stitch, пропустив бриф/структуру. Главный анти-паттерн, ради него и стоит HARD GATE.
- **Имитация reference-фазы**  — корень «лень + не сверяю с определением + заявляю непроверенное». Три формы брака, все закрыты в `workflow/02-reference.md`:
  - *Референс не того типа* — натащить объект другого типа, чем строим . Тип нашего объекта (из брифа Фазы 0) и каждого кандидата сверять ДО сбора, отсеивать по типу.
  - *Фабрикация переносом* — взять суждение с ДРУГОГО объекта (контент-досье эксперта) и выдать как факт про его лендинг, который не открывал. Описывать ТОЛЬКО реально открытую страницу с source-tag. Контент-анализ ≠ страница регистрации.
  - *Ским одного файла* — взять 3 URL из одного Battle Card, проигнорировав свой же deep-dive на 10–15 конкурентов. Поднимать ВСЕ ресёрч-артефакты запуска/`thoughts/research` перед сбором.
- **Перескок концепция→копи** — писать готовые тексты, минуя микро-гейт 3a (утверждение раскладки экрана автором). Концепция дешева, копи дорога; сверять концепцию раньше.
- **Несовпадение регистра** — продающая продуктовая копи на контент-хабе (или наоборот). Регистр копи обязан совпадать с типом сайта из брифа (Шаг 1). Прецедент по решению автора: герой контент-хаба написали как лендинг продукта («Build your first product») вместо обещания контента + подписки.
- **Выдумывание фактов** — цифры/кейсы/дифференциация только реальные из `.business/` или от эксперта.
- **Рубка предложений** в копи (staccato) — см. humaniser категория 7.
- **Em-dash «—» внутри строк** — только дефис или запятая.
- **Generic AI-slop дизайн** — frontend-design против этого, не дефолтный Bootstrap-вид.
- **Stitch на каждую итерацию** — жжёт квоту; один заход.
- **Смешивание проектов на одном VPS** при деплое.
- **Плоский AI-вайрфрейм** — текст в рамках + буллеты-чекбоксы + flat-мокапы + дефолтные шрифты. Лечится `references/effects-arsenal.md` (реализм + эффекты + анти-AI-slop + mobile).
- **Хватать разговорные формулировки заказчика как финал** (H1, нейминг) — крафтить и согласовывать, не брать дословно сказанное в потоке.
- **Не удалять то, что велено удалить** — удалять сразу, не «доделаю потом».
- **Показ автору без гейта 09** — нести сырьё и спрашивать «это тот уровень?» вместо самостоятельного доведения до порога ≥8/10 свежим критиком. ГЛАВНЫЙ процессный анти-паттерн, ради него Фаза 09 .
- **Потеря правки между кругами** — не вести реестр открытых правок → автор повторяет одно и то же. Логировать и сверять перед показом (9.4).
- **Возврат с вопросами вместо решений** — «какие картинки/скиллы?» при ясной задаче. «Высочайший уровень» = сам выведи и сделай.
- **Блок без обоснования данными ЦА** — поставить экран, который не можешь аргументировать («почему этот экран?»). Нет источника → блок не ставим.
- **Динамический референс по одному статичному скрину** — живой герой изучается в движении (видео/серия кадров), иначе не воспроизводится.
- **Свернуть конвейер в прыжок к финалу** — прочитать весь скилл разом и «сделать сайт», проскочив подфазы и улики (особенно reference-доску). Прецедент по решению автора: флагман из головы → не та эстетика, «удивление» реальному эталону. Лечится конвейером `workflow/_phases-state.md` + хук-цепочкой.
- **Строить дизайн из головы мимо референс-доски жанра** — «понемногу везде» вместо 100% в reference-фазу. Нет `refs/*.png` на диске + якоря жанра → планка не поднята, выходит muted-минимал. Reference-доска обязательна (хук блокирует показ без неё).
- **Правка HTML без скрин-ревью на 2 ширинах**  — «отредактировал = готово» без визуального осмотра рендера на 390+1280 ДО показа. Чинится разделом H чеклиста + гейтом 09.
- **localhost-ссылка для сайта, который уже в проде**  — деплой делаю я сам по FTP, правка сразу на прод. Localhost только до первого деплоя.
- **Отработать десятую часть пачки правок**  — выполнять ВСЮ пачку за раз, в конце сверить реестром каждую правку из запроса.
- **Текстовый/абстрактный слайд в деке**  — каждый слайд = реалистичная визуализация (терминал/чат-бот/воронка/лендинг/оплаты) + законченная мысль с выводом «к чему приведёт». Техчасть («режим свёртки», «слот», «обложка дня», номера фаз) в финальной деке = брак.
- **Выдуманные тарифы / «Fast-action» / гарантии / сроки продаж**  — один продаваемый тариф + якоря, состав строго из оффер-канона; не обещать сроки продаж и возврат/результат (канон «результат зависит от тебя»); контент-завод = трафик-механика.
- **Запрещённые концепты и термины**  — «1 смысл на N площадок / перелив», «авто-сторис», «авто-карусели», нераскрытые OSM/OSMK → понятный язык, канон «контент-завод 2.0».
- **Требования к железу на сайте**  — никаких «Mac M2/M3», «N ГБ RAM» на странице; не поднимать барьер входа.
- **Лендинг без подвала с офертой и политикой**  — юр-минимум сбора заявок; документы через `Skill('yurist')`, не из головы. Без них не деплоить.
- **Слово на отдельной строке**  — правило humaniser; запрещено выносить отдельное слово на строку (страхует орфан-гейт 09).

Действующий закон подачи: вся статья простым языком для новичка решает задачу, с которой человек пришёл, шаг размечается тройкой «куда нажать → что увидишь на экране → что это тебе даёт», термин переводится тут же, воды ноль. Смысловой слой я не переписываю - принимаю как есть и одеваю в форму.

- **Публикация ТОЛЬКО на <твой-домен> через FTP-деплой, НИКОГДА на github.io** или другом стороннем хосте (даже превью). В финале отдать автору ЖИВУЮ ссылку (curl 200).,
