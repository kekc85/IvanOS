# Phase Review — адаптивная верификация фазы через свежих субагентов

Пост-фазовая проверка кода перед переходом к следующей фазе. Свежие субагенты
видят код без предположений «что я имел в виду» — психологически критичнее, чем
сессия, которая его писала.

## Когда применять

- «проверь фазу» / «ревью фазы» / «валидация фазы» / «проверь что написал» / «фаза готова»
- `/phase-review` (опц. `--size S|M|L`)
- Автоматически как review-шаг внутри скилла `[[вайбкодинг]]` (между Stage 4 Implementation и Stage 12 Deploy — усиливает Stage 5/9/10).

НЕ для: PR/diff-ревью (→ `/code-review`), генерик code review без фазы-контекста, задачи с нуля (нет кода для проверки → сначала `[[вайбкодинг]]`).

## 3 правила (не менять без причины)

1. **Свежие субагенты.** Все ревьюеры — свежие субагенты (`general-purpose` с ролевым промптом). Текущая сессия — только оркестратор + исполнитель фиксов (Шаг 3).
2. **Зонирование.** Одна роль = один агент. Ни один агент не делает две роли — иначе теряется глубина.
3. **Адаптивный размер S/M/L.** Баг-фикс не гоняет полный 7-агентный pipeline (перерасход), архитектура — гоняет (иначе пропустим инвариант). Размер на Шаге 0.5, пользователь может override.

## Конвейер (полный, L-размер)

Шаг 0 контекст+Assumption Log → 0.5 size-detection → 1 параллель (1A Spec + 1B Architecture) → 2 параллель (2A Quality + 2B Security + 2C Forward-Look) → 2.5 Adversarial Skeptic → 3 фиксы (сессия) → 3.5 Regression Sweep → 4 отчёт. Промпты всех ролей — `prompts/role-prompts.md`.

## Шаг 0 — Контекст (сессия, всегда)
Собрать: (1) ТЗ фазы одной строкой (CLAUDE.md/plan/указанный файл); (2) изменённые файлы `git diff --name-only` + `--shortstat` объём; (3) команда тестов; (4) project context — приоритет (запустить/продать/масштабировать), объём 1-го месяца (десятки/сотни/тысячи), стадия (pre-MVP/MVP/prod/scale), чувствительные участки в diff (auth/PII/платежи/ЭЦП/файл-аплоад/raw SQL/внешние API/фоновые задачи); (5) файл инвариантов (`architecture/`, ADR, INVARIANTS.md) или «нет»; (6) **Assumption Log** — ключевые допущения реализации («я предполагал X», «считал Y не нужным») → передаётся Skeptic.

## Шаг 0.5 — Size detection (сессия)

| | условие | агентов | ~токены от L |
|---|---|---|---|
| **S** | <4 файлов И <100 строк diff И нет sensitive | 2-3 | ~30% |
| **M** | 4-15 файлов ИЛИ sensitive ИЛИ новый компонент/слой/таблица | 4-6 | ~70% |
| **L** | >15 файлов ИЛИ ≥3 модуля ИЛИ миграция БД ИЛИ новый домен | 7 | 100% (батчинг по 5-8 если >15) |

- **Override:** `--size S|M|L` или «прогони S-ревью / полное L».
- **Sensitive-bump:** если в diff auth/PII/платежи/ЭЦП/файл-аплоад/raw SQL — минимум **M** (S апгрейдится, чтобы security и forward-look не пропустить).

### Матрица: кто на каком размере
| Шаг | Роль | S | M | L |
|---|---|---|---|---|
| 1A | Spec compliance | ✓ | ✓ | ✓ |
| 1B | Architecture invariants | — | ✓¹ | ✓ |
| 2A | Code quality | ✓ | ✓ | ✓ |
| 2B | Security | ✓² | ✓ | ✓ |
| 2C | Forward-look | — | ✓ | ✓ |
| 2.5 | Adversarial skeptic | — | ✓³ | ✓ |
| 3 | Fix | ✓ | ✓ | ✓ |
| 3.5 | Regression sweep | ✓⁴ | ✓⁵ | ✓ |
| 4 | Отчёт | ✓ | ✓ | ✓ |

¹ только если файл инвариантов есть, иначе ARCH_SKIP · ² на S только при sensitive-bump · ³ на M пропуск если <5 находок · ⁴ на S только если ≥3 фикса или security-фикс · ⁵ на M если ≥1 фикс. **0 фиксов → 3.5 пропускается всегда.**

## Шаг 1 — Declarations Gate
Одним сообщением субагенты по матрице (S: только 1A; M/L: 1A+1B параллельно). Промпты — `prompts/role-prompts.md` (1A Spec, 1B Architecture). **SPEC_FAIL или ARCH_FAIL → фикс → повторить Шаг 1.**

## Шаг 2 — Risk Profiles
После Шага 1, одним сообщением по матрице (S: 2A, +2B если sensitive; M/L: 2A+2B+2C параллельно). Промпты — `prompts/role-prompts.md` (2A Quality, 2B Security, 2C Forward-look).
- **Security-шаг (2B) исполняется по ЗАКОНУ «security-review через 3 ИИ»** из CLAUDE.md: чек-лист прогнать через Claude+ChatGPT+Gemini (разные слепые зоны), объединить находки. Промпты-чек-лист — `.business/processes/vibecoding-playbooks.md` (ход 5).
- **QUALITY/SECURITY/FORWARD_FAIL → фикс → повторить Шаг 2.**

## Шаг 2.5 — Adversarial Skeptic
L всегда; M если ≥5 находок; S пропуск. Не пишет новых находок — фильтрует существующие через project context на РЕАЛЬНО / ПАРАНОЯ. Промпт — `prompts/role-prompts.md`. **Правило: Security CRITICAL/HIGH не может быть параноей даже на 10 юзерах. Параноя → WARN-секция отчёта, не в фиксы.**

## Шаг 3 — Fix (сессия, всегда)
Фиксы только по REAL находкам. Порядок: Security CRITICAL/HIGH → Arch блокер → Quality критично → Forward критично → Security medium → Quality средне → Forward средне. Правила: одно изменение = одна проблема; запрещён рефакторинг «пока уже здесь»; для security-фикса — негативный тест если есть тест-инфра. 0 фиксов → сразу Шаг 4.

## Шаг 3.5 — Regression Sweep
Свежий ревьюер смотрит ТОЛЬКО diff фиксов (не полное ревью): что нового затащили под видом фикса · регрессии в соседнем коде (импорты/вызывающие) · фиктивные фиксы (косметика vs закрыта проблема). Промпт — `prompts/role-prompts.md`. **REGRESSION_FAIL → фикс → повторить 3.5.**

## Шаг 4 — Отчёт (сессия, всегда)
Размер (с обоснованием) · гейты (только запущенные, со статусами) · исправлено REAL (категория/проблема/что сделано/файл:строка) · параноя · не исправлено намеренно (+когда вернуться) · watch-точки из Forward (+горизонт) · затронутые файлы вне фазы · готовность к следующей фазе ДА/НЕТ. **Без Шага 4 со статусами «готово» не говорить.**

## Выбор модели
Все ревьюеры и Skeptic — Opus. Regression Sweep — Sonnet (узкий scope). На S допустим Sonnet для Spec/Quality (экономия).

## Anti-patterns
- Запускать Шаг 2 до прохождения Шага 1 · параллельные шаги последовательно.
- Текущая сессия в роли ревьюера · две роли в одном промпте одному агенту.
- Фиксить параною · игнорировать sensitive-bump · понижать размер без override.
- «Готово» без Шага 4.

## Интеграция и параллели
- **`[[вайбкодинг]]`** — phase-review встаёт review-шагом ВНУТРИ него (не заменяет; размер наследуется от размера задачи вайбкодинга, override в обе стороны). Без вайбкодинга работает на ad-hoc задаче / внешнем коде.
- **ЗАКОН «security-review 3 ИИ»** (CLAUDE.md) — исполняется на Шаге 2B.
- **`.business/processes/vibecoding-playbooks.md`** — плейбук «5 ходов» = ручная лёгкая версия той же идеи; phase-review = автоматизированная многоагентная.
- `/code-review` — для PR/diff (другой scope).
