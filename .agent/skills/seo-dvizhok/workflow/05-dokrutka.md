# Фаза 5. Докрутка: недельный контур по существующим статьям

Движок умеет две вещи: производить новое и чинить существующее. Фазы 1-3 - первое, эта фаза - второе.

**Когда включается.** Как только показы появились у 20-30 страниц. Дальше идёт ЕЖЕНЕДЕЛЬНО и параллельно производству, а не вместо него.

**Почему это дешевле новых статей.** Подъём кликабельности существующих показов даёт результат за дни, новая статья - за месяцы созревания. На живой системе автора кликабельность вдвое ниже нормы означала, что больше половины уже заработанных показов уходит в пустоту: чинить их дешевле, чем добывать новые (урок 2 в `knowledge/uroki-praktiki.md`).

---

## Недельный цикл

```
понедельник, утро     свежий срез 14 дней  →  классификация  →  очередь
понедельник-вторник   отбор волны из очереди: 5-6 единиц, не больше
среда-четверг         исполнение волны + приёмка GET по каждому URL
                      ↓
                      пауза 2-4 недели, руками ничего не мерим
через 2-4 недели      замер «было / стало» по тем же URL, вердикт волне
```

**Почему волна 5-6 единиц.** Вердикт по волне должен быть измерим. Зальёшь двадцать - через месяц не скажешь, что именно сработало.

**Почему вердикт не раньше двух недель.** Два независимых основания: сниппет должен успеть накопить показы, и панель вебмастера добивает уже закрытое окно несколько дней после его конца.

## Шаг 1. Свежий срез

Per-URL выгрузка из вебмастера за окно 14 дней: **URL · клики · показы · CTR · средняя позиция · головной запрос**. Если API доступен - тянуть скриптом; нет доступа - ручная выгрузка из интерфейса тем же составом полей. Ручной путь равноправен, важен состав полей, а не способ.

🔴 **Окно заканчивается позавчера, а не вчера.** Панель досчитывает уже закрытый период несколько дней. Замер на живой системе: одно и то же 14-дневное окно, снятое с разницей в сутки, дало расхождение около 5% по кликам и показам, при этом показы выросли у большинства страниц и **не упали ни у одной**. Значит цифра, снятая сразу после закрытия окна, занижена системно. Практический след: «стало» снимается с ТОЙ ЖЕ задержкой, что и «было», иначе сравнение врёт в свою пользу.

Срез сохраняется файлом с датами окна в имени. Замеры сравниваются между собой, а не с памятью.

🔴 Источник один на вопрос: показы, клики, CTR и позиция - только панель вебмастера. Визиты - только счётчик аналитики, срез «из поисковых систем». Не смешивать.

## Шаг 2. Склейка адресов

Один материал часто живёт под двумя адресами (`/x/` и `/x.html`, со слэшем и без, с параметром). Без склейки его показы делятся на две строки, кликабельность каждой занижена, и обе улетают в очередь на ретайтл - контур начинает чинить то, что не сломано.

Склейка по слагу:
- клики и показы - суммой
- позиция - средневзвешенная **по показам** (простое среднее уравняет строку с пятью показами и строку с пятью сотнями)
- головной запрос - от того адреса, который дал больше показов

Побочный эффект правильный: пара «страница плюс её же `.html`-двойник» после склейки не может попасть в каннибализацию. Два адреса одной страницы в миграции - это переезд, а не конкуренция.

## Шаг 3. Нормы кликабельности - из СВОИХ медиан по полосам позиций

🔴 **Отраслевые таблички «CTR по позициям» здесь не годятся.** Они собраны на чужой выдаче, чужих сниппетах и чужой доле рекламы. На твоём домене они не значат ничего. Норма считается из твоего же среза.

Как считается (пороги - параметры `config.md`, значения по умолчанию совпадают с дефолтом конфига):

1. Разбить страницы на полосы позиций: **`dokrutka_polosy`, по умолчанию 3-5, 5-7, 7-9, 9-11, 11-16**
2. В расчёт нормы брать только страницы с показами от **`dokrutka_min_pokazov_norma`, по умолчанию 30** за окно. Ниже - шум: один случайный клик на 30 показах даёт 3.3%
3. Норма полосы = **медиана** кликабельности страниц этой полосы (не среднее: одна страница-выброс перекосит среднее)
4. **Порог достоверности полосы: `dokrutka_min_n_polosy`, по умолчанию 20 наблюдений.** Меньше - полоса нормы не даёт, берётся норма соседней полосы, и в отчёте прямым текстом пишется, что значение запасное. Наберётся порог - норма сама перейдёт на живой расчёт, править ничего не надо
5. **Порог дыры = `dokrutka_koeff_dyry` от нормы полосы, по умолчанию 60%.** Почему не 100%: ниже медианы по построению лежит половина корпуса, «ниже нормы» это не диагноз, а описание половины страниц. Дыра начинается там, где страница отстаёт от соседей ПО ТОЙ ЖЕ ПОЗИЦИИ существенно
6. **Порог показов держится отдельно от кликабельности: `dokrutka_min_pokazov`, по умолчанию от 100 за окно.** На 30 показах разница между 0% и 2% - это один клик, вердикт по такой странице не стоит волны

**Как откалибровать коэффициент 0.6 под свой корпус.** Отбери 20-50 страниц глазами, как «явные дыры». Прогони классификацию с коэффициентами 0.4, 0.5, 0.6, 0.7, 1.0 и посмотри, при каком машина ловит твой ручной список целиком и не тащит лишнего. На живой системе сошлось ровно на 0.6, причём на самой населённой полосе полосовой порог совпал с тем значением, которое до этого стояло на глаз. Ручное правило и выведенное из данных должны сойтись - если не сходятся, разбирайся, а не подгоняй.

Пересчёт норм воспроизводится одной командой по файлу среза:

```bash
python3 - <<'PY'
import json, statistics
d = json.load(open('srez.json'))   # список: url, clicks, impressions, avgpos

# пороги - из config.md, значения ниже совпадают с дефолтом конфига
dokrutka_polosy = [3, 5, 7, 9, 11, 16]        # config.md: dokrutka_polosy
dokrutka_min_pokazov_norma = 30                # config.md: dokrutka_min_pokazov_norma
dokrutka_min_n_polosy = 20                     # config.md: dokrutka_min_n_polosy

def slug(u):
    s = u.rstrip('/')
    return (s[:-5] if s.endswith('.html') else s) or '/'
agg = {}
for r in d:
    a = agg.setdefault(slug(r['url']), {'c': 0., 'i': 0., 'pw': 0.})
    a['c'] += r['clicks']; a['i'] += r['impressions']; a['pw'] += r['avgpos'] * r['impressions']
for a in agg.values():
    if a['i']:
        a['pos'] = a['pw'] / a['i']; a['ctr'] = 100 * a['c'] / a['i']
    else:
        a['pos'] = None; a['ctr'] = 0.0   # SUDBA: нулевые показы - это данные, не сбой, делить не на что
for lo, hi in zip(dokrutka_polosy[:-1], dokrutka_polosy[1:]):
    rows = [a for a in agg.values() if a['i'] >= dokrutka_min_pokazov_norma and a['pos'] is not None and lo <= a['pos'] < hi]
    if len(rows) < dokrutka_min_n_polosy:
        print(lo, hi, 'n=%d' % len(rows), 'НОРМЫ НЕТ, берём соседнюю полосу (запасная)')
    else:
        print(lo, hi, 'n=%d' % len(rows), 'норма=%.2f%%' % statistics.median([a['ctr'] for a in rows]))
PY
```

## Шаг 4. Классы

Классы **взаимоисключающие**: страница получает ровно один. Но все сработавшие признаки пишутся рядом отдельным полем - страница бывает одновременно каннибалом и дырой по кликабельности, и это надо видеть.

Приоритет сверху вниз, порядок не случайный:

| # | Класс | Признак | Чем лечится |
|---|---|---|---|
| 1 | **KANNIBAL** | один головной запрос у двух и более URL | развод: одна страница остаётся владельцем интента, вторая переписывается под другой интент или склеивается редиректом |
| 2 | **NAVIG** | головной запрос навигационный (ищут чужой бренд или официальный сайт продукта) | ретайтлом НЕ лечится, лечится только позицией или сменой запроса-цели |
| 3 | **SUDBA** | ноль показов в коротком окне И ноль в длинном окне-подтверждении, страница при этом не молодая | решение владельца: обновить / объединить / закрыть от индексации |
| 4 | **REFRESH** | не правилась 180+ дней И позиция просела против длинного окна не меньше чем на 1.0 | переработка по факту: меняем факт в заголовке или теле, URL сохраняем |
| 5 | **RETITLE** | позиция 3-10.99, показов от порога, кликабельность ниже полосного порога, интент НЕ навигационный | переписывание title и description под точную формулировку запроса, тело не трогаем |
| 6 | **BOOST** | позиция 11-16 при живых показах | перелинковка (3-5 входящих контекстных из статей кластера) плюс доработка раздела под запрос |
| 7 | **OK** | всё остальное | ничего |

**Почему такой порядок.**

- **KANNIBAL первым**, потому что чинится ДО ретайтла: пока две твои страницы делят один запрос, непонятно, какой из них вообще переписывать заголовок
- **NAVIG выше RETITLE**, потому что иначе он съедает слоты ретайтл-волны. По навигационному запросу к чужому бренду в топ не выйти: показы уходят на официальный сайт, сколько сниппет ни переписывай. Такая страница может держать тысячу показов и один клик и выглядеть самой аппетитной дырой корпуса - это ловушка
- **BOOST отделён от RETITLE**, потому что на второй странице выдачи сниппет почти не видят. Ретайтл там бесполезен по механике, а не по качеству текста

**Две поправки, без которых классы врут:**

🔴 **Возраст для SUDBA берётся из даты публикации на самой странице, а не из `lastmod`.** Любая массовая правка шаблона (метаданные, стили) переставляет `lastmod` практически всему корпусу, и корпус выглядит новорождённым - класс молча даёт ноль кандидатов. Даты нет вовсе - страница считается молодой и в SUDBA не едет: ошибиться в сторону «не трогать» дешевле.

🔴 **Нулевая кликабельность молодой страницы - не приговор теме.** У неё просто нет истории. Поэтому SUDBA требует ДВА окна: короткое и длинное подтверждающее. Ноль за две недели бывает у страницы, которая просела, а не умерла.

🔴 **Границы RETITLE и BOOST покрывают диапазон 3-16 без дыр, синхронно с полосами норм (`dokrutka_polosy`, Шаг 3).** Страница на позиции 3.5, 10.5 или 15.5 раньше не попадала ни в один класс и молча падала в OK - контур не предлагал её чинить, хотя дыра в кликабельности у неё та же, что у соседей. RETITLE берёт весь низ диапазона (3-10.99), BOOST - весь верх (11-16): ровно та же непрерывная лестница, что у полос, которыми считается сама норма.

**Пустой класс - это тоже результат, а не поломка.** На молодом корпусе REFRESH пуст по арифметике возраста (условие «180+ дней без правки» физически невыполнимо, пока корпусу пара месяцев), а BOOST пуст, если весь корпус сидит выше одиннадцатой позиции. Классы включаются заранее сознательно: когда корпус дорастёт, контур не придётся переписывать. Но в отчёте пустота объясняется причиной, а не молчанием.

## Шаг 5. Гейт дверей

Страница-дверь под код-слово из соцсетей несёт заголовок, связанный с воронкой: правка title ломает вход по слову. Правило действует с фазы 4 и здесь становится машинным.

- держи список дверей отдельным файлом и сверяйся с ним при классификации
- дверь не выкидывается из отчёта молча: приоритет ей роняется в самый низ, а в поле действия пишется СТОП вместо инструкции
- в отчёте двери печатаются **отдельным блоком над таблицей**: «заперто столько-то недополученных кликов, вот поимённо». Невидимый запрет хуже запрета: через месяц никто не вспомнит, почему самая большая дыра корпуса не чинится
- правка двери - только руками и осознанно, вместе с владельцем воронки

На живой системе четверть страниц ретайтл-класса оказалась дверьми, и они держали больше трети недополученных кликов класса. Это не редкий случай.

## Шаг 6. Очередь и приоритет

Очередь - два файла одного и того же: машинный (json, для скриптов) и человеческий (markdown с датой, для чтения глазами).

Приоритет считается как **ICE = I × C × E**, каждая шкала 1-10.

**I (отдача) считается ПО-РАЗНОМУ у разных классов, и это сознательно:**

| Класс | Откуда I |
|---|---|
| RETITLE, REFRESH | недополученные клики за окно: `показы × (норма − CTR) / 100` |
| KANNIBAL | суммарные показы пары |
| BOOST | собственные показы страницы |
| NAVIG | всегда низкая: потолок класса ограничен не нами |
| SUDBA | всегда низкая: показов нет, ценность решения - гигиена корпуса, а не клики |

Почему у каннибала отдача не через недополученные клики: крупнейшая пара может конвертить отлично, то есть по кликабельности она здорова. Болезнь у неё другая - один запрос размазан по двум URL, и формула недополученных кликов такую болезнь не видит вовсе.

**C (уверенность)** = объём показов, придавленный **потолком класса**. Потолок и есть честность движка: ретайтл - механика проверенная, у неё потолок высокий; гипотеза про перелинковку выше среднего не поднимается никогда.

**E (лёгкость)** фиксирована классом: ретайтл легче всего, переработка тяжелее всего, дверь принудительно 1.

## Шаг 7. Исполнение волны

1. Взять из очереди 5-6 верхних единиц. Больше - нельзя
2. Снять «до»: показы, клики, кликабельность, позиция по этим URL за окно. Записать в журнал ДО правки
3. Сделать правку своего класса. Для RETITLE - **только title и description, тело не трогать**: иначе через месяц не отделить эффект сниппета от эффекта контента. Для BOOST - только перелинковка и целевой раздел. Один класс - одна волна, не смешивать
4. Залить и проверить **каждый** URL живым GET (ожидание 200). Файлы недоезжают молча
5. Пингануть IndexNow по правленным URL (это обновление, а не новая страница - протокол ждёт именно такие)
6. Записать волну в журнал: дата · URL · класс · что изменено · значения «до»

## Шаг 8. Замер «было / стало»

- вердикт **не раньше 2-4 недель** после заливки
- «стало» снимается тем же инструментом, окном той же длины и с той же задержкой, что «было». Иначе сравниваешь не правку, а два разных способа замера
- **кликабельность и позиция смотрятся отдельно.** Выросла кликабельность при той же позиции - сработал сниппет, вердикт чистый. Выросла позиция - эффекты смешались, вердикт по сниппету не выносится, страница возвращается в наблюдение
- если есть дневной ряд - дельту считать по ряду с датами, а не по двум снимкам: два снимка ловят случайный день
- сработало - следующая волна тем же классом. Не сработало - разбор причины, а не вторая такая же волна

## Когда контур не отработал

Не падать молча и не рапортовать зелёным:

- канал данных не ответил - взять самый свежий имеющийся срез, **проставить возраст данных в шапку отчёта**, и если он старше недели - напечатать громкое предупреждение, что вердикты по ним слабые
- нет длинного окна-подтверждения или нет дат публикации - класс, который на них стоит, остаётся пустым, и в лог уходит ПРИЧИНА, а не тишина
- молчаливый пропуск обязательного шага - зелёная ложь. Пропуск здесь всегда громкий

Отдельно: ни один шаг этого контура не ходит на сам сайт. Единственная сеть - API панели вебмастера. Живой прод трогаем только на шаге заливки волны.

## Известные ограничения (знать заранее)

- **позиция усреднена по окну.** Страница, вылетевшая с 5-й на 20-ю в середине окна, покажет среднее 12 и попадёт в BOOST, хотя история у неё другая. Разбор траектории - отдельная работа по дневному ряду
- **головной запрос приходит сырым**, вместе с мусором панели (числовые хвосты, обрывки). Чужие данные не правим, но при ретайтле формулировку чистим глазами
- **длинное окно-подтверждение стареет.** Пересобирать раз в месяц, иначе SUDBA начнёт ловить новичков
- **длинный срез из того же API может оказаться копией короткого.** Прежде чем считать его независимым подтверждением, сверь состав URL: совпадение один в один означает, что подтверждения у тебя нет

Файла нет - это норма, ничего не сломано: всё нужное для сборки контура лежит в этом файле, а конкретные пороги всё равно считаются из твоего собственного среза, а не берутся у кого-то готовыми.

## Докрутка СУЩЕСТВУЮЩЕГО корпуса: шесть осей и fan-out

Раздел про другую задачу, чем всё выше. Выше - регулярный цикл по свежему срезу.
Здесь - что делать, когда статей уже сотни, они написаны по СТАРОМУ стандарту, а
поднять надо клики на них, не выпуская ни одной новой страницы.

### Шесть осей, у каждой свой судья

| Ось | Что чинит | Кто судит |
|---|---|---|
| О1 соответствие канону | страница собрана по устаревшему стандарту | гейты стадии `page` в режиме ревизии |
| О2 сниппет | title и description не несут формулировку живого запроса | классификатор очереди, класс RETITLE, плюс гейт формулы сниппета |
| О3 интент и каннибализация | две страницы делят один запрос | классификатор, класс KANNIBAL |
| О4 тело под живой запрос | показы есть, раздела под запрос в теле нет | классификатор, класс BOOST |
| О5 связки | внутренних ссылок меньше порога | инструмент перелинковки плюс гейт числа внутренних ссылок |
| О6 отражения | правка не доехала в карту сайта, каталог, ленту, хабы | гейт цепочки публикации плюс гейт членства в хабе |

### Ось, которой в списке НЕТ, и почему

«Долить текста, H2, таблиц, FAQ» - самое частое предложение и самое бесполезное,
если его не проверить замером. Проверь на СВОЁМ корпусе: возьми 20-25 пар «чужая
страница в топ-3 против твоей ниже по тому же запросу» и сравни их по объёму
текста, числу H2, таблицам, FAQ, разметке. Очень вероятно, что ты уже впереди по
большинству факторов и всё равно стоишь ниже - тогда доливка объёма не ведёт к
цели, и ось в работу не берётся. Дельту в ИХ пользу обычно дают один-два фактора,
их и чини

### Что считается целевым изменением

Целевое изменение обязано менять СЧЁТНУЮ величину: байты title, байты
description, множество H2, число внутренних ссылок в теле, закрепление владельца
интента, появление страницы в поверхности, где её не было.

Не засчитывается: обновление даты, правка стилей, перестановка блоков, замена
слов синонимами, вода. Проверяется машинно - страница с переставленным абзацем
даёт нулевую дельту по всем счётным величинам

### Цена оси, чтобы выбирать работу числом

1. свежий поюрльный срез из панели вебмастера
2. склеить адреса по слагу: клики и показы суммой, позиция средневзвешенная по показам
3. популяция оси сниппета = позиция 3-10.99 И показов не меньше 100 за окно
4. норма CTR полосы позиций считается из ТВОЕГО ЖЕ среза, не берётся готовой
5. недобор страницы = `показы × (норма − CTR) / 100`, коэффициент 1.0
6. сумму разделить на число дней ФАКТИЧЕСКОГО окна

🔴 Шаг 6 - главная ловушка. Панель вебмастера умеет молча сузить запрошенное окно
и вернуть данные за меньший срок, не сказав об этом ни строкой. Если поделить
клики короткого окна на число дней длинного, отдача на страницу занижается
кратно, и весь приоритет работ едет. Проверяй окно ПО ДАННЫМ: собери набор дат,
реально пришедших в ответе, сравни с запрошенным и печатай громкую строку при
расхождении

### Ложные кандидаты: сверка заголовка с живой страницей

Очередь меряет CTR по заголовкам на момент своего среза. Часть заголовков ты уже
переписал прошлыми волнами, но окно замера этого ещё не видит - и страница
возвращается в работу с предложением переписать то, что уже переписано.

Лечится сверкой ПЕРЕД присвоением класса: снимаешь живой заголовок страницы и
смотришь, несёт ли он уже слова головного запроса. Сравнивай по ОСНОВАМ слов, а
не по точным формам, и выброси служебные слова - иначе падеж запроса объявит
выровненный заголовок мисматчем, а предлог «для» насчитает лишнее совпадение.

Ходить за живым заголовком - только по кандидатам класса, единицами, серийно, с
паузой. Не по всему корпусу: это залп, за который хостинг банит адрес.

🔴 Канал сверки недоступен - класс НЕ присваивается, и в отчёт уходит громкая
строка «сверка не выполнена». Тихо присвоить класс вслепую нельзя: молча
выключенный барьер хуже отсутствующего

### Ветки несобираемой волны, объявляются ЗАРАНЕЕ

- **5 и больше** чистых мисматчей - штатная волна 5-6 единиц, вердикт измерим
- **2-4** - волна идёт этим числом с пометкой «вердикт по волне неизмерим», берётся верх по приоритету
- **0-1** - ось закрывается уликой невозможности: прикладывается вывод сверки по КАЖДОМУ кандидату

Ветку называешь до сверки. Иначе задним числом любое число объявляется нормальным

### След правки: без него дефект возвращается завтра

После записи нового заголовка инструмент обязан САМ оставить след правки с датой
в имени. Гейт «грязного окна замера» читает эти следы и не пускает страницу
обратно в работу, пока замер не дозреет. Если след ставится руками волны, он
рано или поздно не поставится - и страница вернётся в очередь на следующий день
после собственной правки.

Следы нужны ДВУХ видов, границы у них разные: правка ВНУТРИ окна замера (замер
описывает мёртвый заголовок) и правка ПОСЛЕ конца окна (замер описывает
заголовок, которого на сайте уже нет). Второй случай легко забыть, а ловится он
тем же механизмом

### Заголовок и H1: где твои судьи могут спорить

Гейт формулы сниппета обычно требует совпадения title и H1. Канон волны ретайтла
может требовать обратного - развода, чтобы страница отвечала на два разных
запроса. Это НЕ баг: два судьи, два правила, и решить их спор должен владелец
контура, а не инструмент. Пока спор не решён - синхронизация H1 держится за
явным флагом и по умолчанию выключена, а в отчёт волны идёт строка о том, какое
именно замечание гейта появится после правки.

Похожая пара - имя страницы в разметке хлебных крошек и видимая крошка в теле.
Если волна не трогает тело, обновлять имя в разметке НЕЛЬЗЯ: разметка начнёт
описывать текст, которого на странице нет

### Страницы-двери: их не трогают вообще

Дверь - страница, на которую человек приходит по код-слову из твоей дистрибуции.
Её заголовок обещан человеку, и переписать его значит порвать вход в воронку.

Двери исключаются из ВСЕХ волн целиком: ни заголовок, ни описание, ни тело.
Признаков должно быть ДВА независимых, и дверью считается страница по ЛЮБОМУ из
них: адрес в реестре дверей ЛИБО слаг встречается в реестре дистрибуции. Одного
признака мало, потому что реестр дверей собирается ПО реестру дистрибуции и
отстаёт от него: в окне между появлением новой пары и пересборкой дверь
выглядит обычной страницей и уезжает в волну

### Fan-out: как довести корпус единицами

- источник единицы - очередь аудита, верх по цене хвоста; строки без показов в
  окне в fan-out не берутся, по ним вердикт неизмерим
- потолок деплоя в сутки ОДИН на все прогоны дня: перед своей первой заливкой
  считаешь, сколько уже залито сегодня, и берёшь остаток
- класс без измеренного вердикта идёт волной 5-6 единиц
- легаси не пересобирается из источника: правится живая копия страницы
- единица закрыта по четырём фактам: страница отдаёт 200 и гейт цепочки печатает
  полную цепочку · карточка каталога несёт новый заголовок · item ленты обновлён
  либо страница честно вытеснена окном ленты · запись реестра сдвинута и
  переобход запрошен

### Две даты вердикта вместо одной

Ранняя дата (2-3 дня после подтверждённого запроса переобхода) - по ней решают,
тиражировать ли правку на остальной корпус. Контрольная (14 дней) - фоновый
замер, который подтверждает или снимает раннее решение. Обе пишутся в файл «до»
в момент заливки. От переобхода считают только тогда, когда он реально запрошен
